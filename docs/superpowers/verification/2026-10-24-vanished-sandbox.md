# 容器被外部删掉的沙箱可以清理；测试的 controller 只扫自己的容器

日期 2026-10-24。分支 `fix/vanished-sandbox`。由 2 小时长任务压测发现。

## 发生了什么

- 压测进行到第 139 轮时，本机同时在跑集成测试。测试里的 controller 和本机 Compose 栈共用同一个
  Docker，它的清扫按「平台标签」列出整台机器的容器，在测试数据库里找不到压测沙箱的记录，就把它连同
  数据卷一起删了。
- 压测的 Run 租约过期，被打断（`run_interrupted: lease_expired`）。
- scheduler 之后每次清理这个沙箱，都因为 Docker 返回 404（容器不存在）失败，20 分钟里失败了 246 次，
  预留一直停在 `isolated / cleanup_unconfirmed`，Run 永远恢复不了。

## 改了什么

1. 清理时容器或数据卷已经不在，算作删除成功（`remove_if_present` / `remove_volume_if_present`）。其他
   Docker 错误照样抛出。
2. DockerEngine 如果带了自己的标签（只有测试这么做），列容器、网络、卷时都加上这个标签过滤，建卷时也
   打上这个标签。生产的 engine 不带额外标签，仍然清扫整台主机。

## 测试过了

- 真 Docker：容器和数据卷都被外部删掉后，`cleanup` 成功，实例变为 `destroyed`，Run 不再占着沙箱（**改之前
  失败，第一次只修了容器时，又在卷的 404 上失败**）。
- 真 Docker：带自己标签的 controller 清扫时，不碰别人建的平台容器（**改之前失败，容器被删**）。
- 沙箱集成测试 209 passed、1 skipped；后端单元 2755 passed（两条断言「调用了严格删除」的单元测试改成了
  新的方法名）。
- **在卡住的压测上验证**：把修好的 controller 部署到本机栈，约 30 秒后预留被清理，Run 自动恢复
  （`recovery_attempts=1`），继续从第 139 轮往下跑；修好后又在本机跑了一遍沙箱集成测试，压测的沙箱
  没有被动到。

## 这一遍没能证明什么

- 只覆盖了「容器和卷都不在」的情况；只删了容器、或者 Docker 返回其他错误时，代码路径没有单独构造。
- 压测 Run 断掉时，worker 报的错是 `stream_frame_too_large`，而不是「容器不存在」。看起来是 controller
  在流式执行中途出错时回了一行 JSON 错误，客户端把它当成数据帧头读了。这次没有查实，也没有改。

## 不声称什么

- 不声称生产上会出现「容器被外部删除」：这次是本机测试和栈共用 Docker 造成的。修复让平台在这种情况下
  能自己恢复，而不是永远卡住。
