# 自动续跑让位于中途到达的消息 — 2026-08-31

> 产品：v2.9.2 §12.1、§12.3。
> 起因：一个有常驻任务的 Agent，收到「你好」也会回去重跑那个任务。查下去发现两层
> 问题：任务被写在「人格」里每轮当作身份注入（Agent 配置问题），以及**平台没有任何
> 规则让常驻任务在用户说话时让位**（平台问题）。本分支只解决后者。

## 1. 测试过了

unit             2281 passed
integration       944 passed, 2 failed（见 §2）

chat-web          53 passed

## 2. 那 2 条失败是环境

`shared/config.py:11` 的 `SettingsConfigDict(env_file=".env")` 会读到本机仓库根为
compose 准备的 `.env`，其中的 `EGRESS_PROXY_URL` 让「没有出口边界」这个前提在本机
不成立。CI 上没有那个文件。已单独立卡，不属于这条分支。

## 3. 这条路走得通

真实飞书应用、部署的那套栈，2026-08-31 01:01。

```
01:01:05  seq 15 创建（「在 /workspace/data 下建三个文件…」）
01:01:06  seq 15 开始
01:01:09  seq 16 创建（用户发「等一下」）      ← 中途到达
01:01:13  seq 15 第 1 轮判 continue → 让位，completed
01:01:13  seq 16 立刻开始                     ← 同一秒，没有等
01:01:17  seq 16 结束
```

| 要证的 | 观察到的 |
|---|---|
| 判 `continue` 时让位 | `{"round": 1, "outcome": "continue", "preempted": true}` |
| Run 以 `completed` 结束 | seq 15 `completed` |
| **排队那条立刻被处理** | seq 16 在 01:01:13 同一秒开始 |
| 记录说明了原因 | `preempted: true` 在 `goal_verdict` 事件里 |
| **不是任何 `continue` 都让位** | 01:01:15 另一条 round 1 `continue` 的 `preempted` 是 `false`——那时 seq 16 后面没人排着 |

最后一行是这一遍最值钱的：**同一批数据里既有让位的也有不让位的**，说明判据真的在区分，
不是无条件触发。聊天记录也对得上——seq 15 只说了 "I'll create the three files, then read
each one back." 就被打断，seq 16 接着把三个文件建完读完。

**走查前踩到的坑记在这里**：前两次走查失败，我以为是用户手速不够，真实原因是
**跑着的 worker 根本不是这条分支的代码**——`has_waiting_run` 与 `user_waiting` 在镜像里
都是 0。部署脚本 `deploy/compose/redeploy.sh` 存在的全部理由就是防这个，而我没用它。
判据不是「我改了代码」，是「跑着的东西真的换了」。

## 4. 这一遍最值得留下的：三次「修一个洞开一个新洞」

三次都是**第二轮**评审才发现，第一轮评审加全套测试都放过了：

1. 「计入 `max_model_calls`」只加了累加没加预检 → 一个精确的上限变成会超一次。
2. 判据从「非终态」收窄到「queued」时**只改了问的那一边**——`_terminalize` 挑继任者
   仍用「非终态」→ 让位把队首交给一个没有 Worker 会领的 Run，会话停住。
3. 修第 2 条时把两个不同 Run 的两个问题压到一行（继任者可领取 / 存在中途到达的消息）
   → 用户连发两条后再插话，反而**不**让位了。

**两次全绿掩盖了 MAJOR**：3269 条测试绿着时藏着「`goal_preempted` 没人读」和第 2 条；
3511 条绿着时藏着第 3 条。

**「注释不得声称代码没有的保护」在这条分支上被违反四次**：`queued` 与非终态的措辞、
`ports/store.py` 那句「会不会真的让消息被处理」、race 注释里的「not a stall」、
以及调用方那句「而不是问后面有没有 queued 的 Run」（那正是它现在做的事）。第五次是
§12.1 的措辞与实现不符，判定为 spec 该改（v2.9.2）。

结构性的收尾：`has_waiting_run` 与 `_terminalize` 现在共用同一个 `_successor_candidates`
查询，第 2 条那种「两边判据漂移」在结构上不可能重新长出来——不是靠注释约定。

## 5. 这一遍没能证明什么

- **`compose-e2e` 绿了，但它一条让位都没测。** run `33343173587`（PR 触发那次），
  `18 passed (2.7m)`，已用 `gh run view --log | grep "^compose-e2e"` 确认是真跑了测试
  而不是只返回 success。但 `tests/e2e/` 里没有任何一条会让一个 Run 续跑到中途再收到
  消息。**它证明的是这条分支没有弄坏别的东西，不是让位能用。**
- **没有任何一个洞是测试发现的。** 三个都是有人逐行追代码追出来的。这个功能的正确性
  目前靠的是评审，不是测试套件。
- **时间戳的竞态没有关闭。** `created_at` 与 `started_at` 都在处理器入口取值而非提交
  时刻；一个刚好在领取前打上 `created_at`、领取后才提交的 POST 会被判成「开始前就
  排着」——一次漏掉的让位。已在代码注释里写明为「接受」而非「已解决」。
- **恢复的 Run 语义没有验证也没有声明。** `started_at` 永不重置，所以一个因预算暂停、
  数小时后恢复的 Run 会把它**没在执行**期间收到的消息当成中途到达，恢复后第一轮就
  让位。可能是对的，但 spec 没说，也没有测试。
- **`goal_preempted` 是推断的**（`signal is COMPLETED and verdict is CONTINUE`）。今天
  成立——这个合取只有一个产生者；将来出现别的 CONTINUE→COMPLETED 分支时它会无声说谎。
- **`repair_session` 里还有第三份手写的「最早非终态」规则**，与共用查询同形不同写法。
  今天正确，但同一个漂移面还在。
- **没有验证过用户连续插话时会不会把一个任务打断到永远做不完。**
- **没有度量过被打断的任务重新「继续」时模型能不能接上。**

## 6. 不声称什么

- **不声称这修好了最初那个抱怨。** 用户抱怨的是「发『你好』也去跑笔记整理」，那是
  `notes-tidier` 把任务和完成判据写进了人格。**即使自动续跑会让位，那个 Agent 收到
  「你好」仍然会跑一遍**——让位管的是「跑到一半时你说话」，不是「你说的话算不算任务」。
  改它需要控制台登录发布新 AgentVersion，本会话做不到最后一步。
- **不声称平台会阻止作者把任务写进人格。** v2.9 §1.6 明确记为不做：写不出「什么算
  任务式内容」的判据，规则要么误伤要么形同虚设。
- **不声称「不打断的注入」已经有了。** `/steer` 那条路 §12.1 记为单列、本版不做。
  默认是抢占，理由是喊停不能取决于模型同不同意。
- **不声称本机跑绿等于可合并。** 判据是 CI 的 compose-e2e。
