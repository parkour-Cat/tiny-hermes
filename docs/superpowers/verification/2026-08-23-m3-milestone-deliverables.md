## 2. 每一项真正缺的是什么

三项里没有一项缺的是「一个新功能」。缺的都是**同一个形状**：数据早就写对了，
只是没有任何人够得着。

**审计导出**：`list_events` 一直在做作用域解析和脱敏，导出没有第二套查询——
它调的就是那一个方法。真正的坑在别处：第一版把 `MAX_EXPORT_ROWS` 传给了
`filter_for`，而 `filter_for` 会夹到 `MAX_PAGE_SIZE`。导出因此在任何行数下
都只返回 200 行，状态码 200，没有任何提示。
**这一版通过了当时文件里的全部测试**，因为没有一条测试种过第二页。

**治理审批队列**：`decided_by`、`decided_at`、`decision_reason` 从 §16.3 落地
那天起就写得好好的，没有任何路由读得到。管理员一答复，「谁答复的、为什么」
就离开了产品。§26 还要求 M2 之后评估**审批负担**——那是一个只有已决行才能
回答的问题。

**示例 Agent**：没有任何示例。

## 3. 做的时候撞到的两件事

**筛选被忽略比筛选报错更坏。** 拼错的 `status=aproved` 如果被悄悄丢掉，调用方
读到的是默认的 pending 队列，标题却是他要的那个——他会据此认为里面每一条都
被批准了。所以是 400，而且回话里不回显他输入的那个词。

**浏览器里过滤分页列表**，回答的是「我取回来的这些行没有匹配的」，而问题是
「这件事到底有没有发生过」。这两句话看起来一模一样。历史筛选一律由服务端做。

## 4. 任务树真正缺的那一半

父 Run 列出子 Run，子 Run 带着 `parent_run_id`——所以**从子 Run 出发，同一批
兄弟隔着两跳**，控制台根本没有办法去问。打开那个失败的子 Run 的管理员，看不到
另外三个成功了。树是一个整体，必须从树上任何一个节点都问得出来。

顺带查出来一件更要紧的事：`budget` 在**每一个** Run 响应上都是整棵树的消耗——
它按 `budget_root_run_id` 读 `run_budget_scopes`（§383、§669）。控制台把它顶在
「预算」这个标题下面，于是子 Run 的页面在告诉管理员「这个子任务调用了 18 次模型」，
而那是整棵树的数。现在树在场时会明说这些数字是谁的。

树锚在 `budget_root_run_id` 上，不是从父节点走下来的：从子节点走要先上再下，
而一个本身是重试的子 Run 有两条向上的边。锚是一列，从哪个节点问都是同一个答案。
代价是树里也包含重试链（§383 的预算范围就是这么定的），所以每个节点带
`relation`（`root`/`child`/`retry`）——不然重试出来的 Run 看起来就像是根委派的。

## 5. 安全阀没有释放阀

做任务树的时候撞出来的：`state_machine.py` 在预算不允许执行时**不给** `resume`
——这是对的，给了也会失败。但加宽上限的路由 `POST /runs/{id}/budget` 从 M2 起
就在，控制台里**没有任何入口**。于是一个被自己上限停住的 Run，在页面上只剩
`cancel`：安全阀存在，没有释放阀。

`available_actions` 是这个代码库回答「我能做什么」的地方，所以答案加在那里，
而不是让控制台另建一套权限判断——控制台根本不知道自己的角色。能力位
`can_hold_budget` 从 `BUDGET_HOLDERS` 这一个常量来，和 `widen_budget` 服务端
检查的是同一个集合：**被提供的按钮和被接受的请求不可能对不上**。

只在预算挡住路的时候出现。挂在每个 Run 上，它读起来就像一个日常控件，而不是
「有个上限把活儿停了」时才去够的东西。

## 6. 示例 Agent 为什么长这样

§21 把它放在向导的第五步。跑到那一步时，部署里只有一个模型别名——所以示例
不能要网络、不能要 HTTP 工具、不能要 MCP 服务器、不能要技能。这不是为了简单，
是**需要这些东西的示例根本创建不出来**，有测试钉住。

值得读的是 `completion.expected_artifacts`：模型说自己做完了不算数，文件必须
真的在（§12.2）。一个「说完了就算完了」的示例会把这个平台最要紧的一条教反。

创建走 `create_agent` → `replace_draft` → `publish` 三个既有方法。直接写一行
已发布版本，就是第二条绕开 `publish` 检查的入口——这个仓库最常出的那种问题。

## 8. 飞书 WS 为什么还是没做

`2026-08-22-feishu-channel.md` 已经判过一次，这一遍**没有推翻它**：可验证的

## 9. 一次绿着跑了零条的 e2e

合 #43 之前按惯例去核 compose-e2e 的日志，看到的是 `Running 17 tests`——而这个
PR 加了 `channels.spec.ts`，应该是 18。**那条 e2e 从来没有被执行过，而 CI 是绿的。**

原因：`tests/e2e/playwright.config.ts` 的 `projects` 是一份显式 `testMatch`
白名单，不在里面的 spec 文件既不会跑，也不会报错。

`Running 17` 和 `Running 18` 在日志里长得一模一样，除非有人去数。所以除了补上
channels 那个 project，还加了一道配置加载期的检查：每个 `*.spec.ts` 都必须被
某个 project 认领，否则直接抛错。这份检查**从 `PROJECTS` 本身推导**，不另立一份
pattern 清单——那份清单会漂移，而漂移看起来正好就是它要防的那个 bug。放了一个
孤儿 spec 进去验过它确实会拦。

CLAUDE.md 里那条「`success` 不等于真的跑过测试」，这次是它自己救的场。

## 10. 这一遍没能证明什么

- **导出的 5 万行上限没有被真实数据量走过**。那条 413 是把上限临时压到 2 才
  测出来的——真实的 5 万行导出有多大、多慢，没有量过。
- **审批历史没有在有真实体量的工作空间里读过**。翻页、`has_more`、
  `created_at DESC, id DESC` 的全序都有测试，但都是几行数据。
- **示例 Agent 从来没有真的跑完一次 Run**。测试证明它能创建、能发布、viewer
  创建不了——没有证明那个模型真的会写出 `summary.md`，因为那需要一个真实模型
  接入点。`expected_artifacts` 的检查逻辑本身是 §12.2 早就测过的。
- **任务树没有在超过两个子节点的树上看过**，也没有在带重试链的树上看过。
  `relation` 的三个取值有测试，深度缩进和排序（`depth, created_at, id`）没有
  在真实形状上肉眼验过。
- **安全阀那个对话框没有在真实的预算耗尽场景里点过**。集成测试证明动作会出现、
  而且 API 会接受它；浏览器里那一步是 msw 桩。
- **本机 17 条 sandbox transport 测试跑不起来**（macOS 的 `AF_UNIX path too
  long`：`/private/var/folders/...` 的临时路径超过 104 字节）。它们在 Linux CI
  上是绿的，但本机的「全绿」这一遍**不包含它们**。
