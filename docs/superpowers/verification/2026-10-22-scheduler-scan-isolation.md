# scheduler：一项扫描失败，不再跳过后面的扫描

日期 2026-10-22。分支 `fix/scheduler-scan-isolation`。
在写[指标与链路追踪设计](../specs/2026-10-22-observability-design.md) §3.3 时读代码发现。

| 改了什么 | 测试 | 实现 |
|---|---|---|
| 每项扫描各自捕获异常，其余照跑；失败在最后一起抛出 | `ec446f1` | `f9cb12f` |

## 为什么有这一遍

`SchedulerRuntime.run_once` 依次执行 14 项扫描：回收租约、隔离沙箱、回收沙箱、恢复中断、
修队首、等待到期、子任务等待、级联取消、审批过期、兼容超时、过期记录、上传垃圾、
产物过期、渠道回复。原来任何一项抛异常，`run_forever` 只记一条 `scheduler cycle failed`，
这一轮剩下的全部跳过。

**如果某一项每次都失败**（比如一行脏数据让它每次都抛），排在它后面的扫描就永远不会再执行。
排在第一的回收租约一旦卡住，恢复、审批过期、清理、飞书回复就都停了，而日志里只有同一条
错误反复出现。

## 怎么改的

- `run_once` 把 14 项扫描列成一张表，逐项执行。某一项抛异常时，按名字记一条
  `scheduler scan failed scan=<名字>`，带堆栈，然后接着跑下一项。
- 全部跑完后，如果有失败，把它们装进一个 `ExceptionGroup` 抛出，每个异常都附上扫描名。
  这样调用方和测试仍然看得到失败，不会因为「吞掉异常」而让一个坏掉的扫描悄悄通过。
- `run_forever` 遇到 `ExceptionGroup` 不再重复记日志（每项失败当时已经记过了），其他异常
  照旧记 `scheduler cycle failed`。
- 顺序不变。原来的顺序里有一条安全相关的考虑：先回收沙箱，再把 Run 放回队列。逐项隔离之后，
  回收沙箱失败了，恢复照样会执行。这仍然安全：`_recover_interrupted` 遇到沙箱预留还活着的
  Run 会直接跳过，所以回收失败只会让恢复推迟到下一轮，不会和清理抢。这一点是读代码确认的，
  见下面「没能证明什么」。

## 这一遍没能证明什么

- **「回收沙箱失败时，恢复照样执行也安全」只读了代码，没有测试。**依据是 `_recover_interrupted`
  里对 `live_for_run` 的检查。没有写一条「回收沙箱失败，同一轮里恢复跳过了这个 Run」的测试。
- 测试里让扫描失败的办法，是在子类里把那一项换成直接抛异常，不是用真实的脏数据。它证明的是
  `run_once` 的控制流，不是任何一项扫描在真实脏数据下的表现。
- 数据库整个连不上时，每轮会记 14 条错误，原来是 1 条。日志会更吵，没有做合并。
- 没有在运行中的 Compose 栈上验证 `run_forever` 的日志输出，只在测试里跑了 `run_once`。

## 不声称什么

- 不声称每项扫描之间完全独立。它们按原来的顺序执行，前一项的结果仍然可能影响后一项这一轮
  能做多少，只是不再能让后一项完全停掉。
- 不声称修好了任何一项会反复失败的扫描。这一遍只保证一项失败不会拖垮其他的。
