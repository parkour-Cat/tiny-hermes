### 断言 4：补了执行层那一半

规划器拒绝有单元测试（`http_call_of` 对未绑定的名字抛 `tool_not_authorized`）。
它证明不了的是 **Worker 没有第二条通往实现的路**——规划器拒绝，只说明规划器拒绝。

补了一条集成测试：驱动一个真实 Run，模型对**注册文档上存在、但这个 Agent 没绑定**的
操作发出 `tool_call`，断言桩服务器**什么都没收到**。绕过规划器的路径会在这里显形，
而在这个仓库的其他任何地方都不会。

顺带钉住一件事：这种情况**不是** `waiting_approval`。请人批准一个 Agent 本来就无权
发起的调用，等于把一个不属于他的决定递给他。

## 2. 找到的三个缺口，都已修

三条的形状完全一样：**断言的前半句有，后半句没有**，而后半句恰好都是
**事后能不能查得出来**的那一半。

### 断言 2 — 终端用户越权：拒绝有，审计没有

原文「服务端**拒绝并写安全审计事件**」。拒绝自终端用户入口起就有测试；审计事件
**既无测试也无实现**——`ForbiddenRunAction` 映射到 `forbidden()`，后者
`audited=False`，一行不写。

差别在有人问「那个账号是不是在试探」的时候显出来：**一次不留痕的拒绝，和一个从未
发生过的请求无法区分**。平台能说「他没进来」，说不出「他试过」。

写在服务层而不是 HTTP 边界，因为只有那一层同时握着两个身份：谁伸的手、伸向谁的
会话。`forbidden()` 两个都没有。

### 断言 3 — 委派交集：零测试覆盖

`delegated_scope` 在**所有测试文件里出现 0 次**。集成套件里每一个子 Agent 都
「什么都不绑」（fixture 自己写了这一点），所以这个交集**只在它无事可做的那一格
被走过**。

补了单元测试，并用两种典型错误实现验证它们不是空过的。其中「**空即无限制**」——
最可能的那个错误写法——**会通过仓库里现有的每一条测试**，同时把父 Agent 的整个
工具箱交给每一个子 Agent。

### 断言 14 — 未批准目标：拒绝有，审计没有

同一个形状，但**原因不同，值得单独记**：这次审计行**写进去了又被回滚**，因为路由的
`except AgentCatalogError` 抢在依赖之前把异常转成了 `AppError`。

在那个 `AppError` 上设 `audited`（断言 2 的做法）**在这里来不及**：服务抛出 →
依赖的 `except` 先跑 → 路由**之后**才映射，那时事务已经没了。

而 `AuditedDenial` 这个机制**早就存在且从未被 raise 过**——`resources.py` 里四处
等着捕获它，全代码库没有一处抛。用多重继承接上：少了 `AuditedDenial` 那半，
记录被回滚；少了领域异常那半，调用方拿不到列出违规条目的 422。

## 3. 找到但**没有修**的一个：断言 7

原文：「Secret 值经过**提示词、日志和 RunEvent** 序列化路径时均被拦截或脱敏；
M2 引入 **MemoryItem 和 SkillProposal** 后，对新增路径执行同样测试。」

查到的：

- **日志路径有测试**（`test_service.py` 里 `assert "gamma" not in caplog.text`）。
- **其余四条路径一条测试都没有**：提示词、RunEvent、MemoryItem、SkillProposal。
- **平台里没有任何擦洗机制。** `mask_plaintext` 只在 secrets 服务内部用来写掩码列，
  没有任何序列化路径调用它。

这**不必然**是缺陷：Secret 的设计是只在出站调用那一刻解析、注入请求头，从不进入
模型上下文——那是结构性保证，比擦洗更强。**但它没有被证明。** 而且有一条真实路径
绕过它：一个工具的**响应体**如果带回了密钥，模型就看见了，然后可以把它写进一条记忆
提案。那条路上没有任何东西拦。

**没有在这一轮修，因为它不是补一条测试的事**——要在四条序列化路径上建拦截层，
是一个功能而不是一个补丁。**明确记为未完成，等一个决定：** 是建拦截层，还是证明
结构性保证成立（后者更便宜，也可能更真实）。
