# `/compact` 改成发完就压 — 2026-09-02

> 由来：`/compact` 上线后第一次真机走查，用户发了一条，回的是「记下了」。
> 原话：「`/compact` 的回复难道不应该是『上下文已压缩』吗？『记下了』是什么鬼」。

## 1. 之前为什么是「记下了」

压缩要调一次模型生成摘要。而 `/compact` 这条消息到达的地方是**入站投递路径**
——飞书在等响应，模型一超时就是投递失败 + 重投六小时。所以第一版做成了
「打标记、下一轮真正压」，回执只能说一句还没发生的事。

**参照实现不是这么做的。**`NousResearch/hermes-agent` @ `3f83297` 的
`gateway/slash_commands.py` 里，`/compress` 在网关中**当场做完整件事**：建一个
临时压缩 agent、等摘要出来、替换历史，然后回一段带具体数字的结果。它的网关是
自己的进程，慢一点没人催——这个理由对飞书的投递路径不成立，但**躲开的方式让
体验变差了**，而那不是必须付的代价。

## 2. 真正的卡点是记账，不是「压缩要不要单独一个 agent」

压缩**本来就是**单独一次调用：`personality=""`、专门的压缩提示词、只喂要压的
那段历史。它干活不需要主 Agent 的 Run。

需要 Run 的是**钱**：

```python
record_summary_usage(workspace_id=..., run_id=claimed.run.id, root_run_id=...)
```

`run_id` 非空，而 §12.4 的额度顺着 `budget_root_run_id` 累加。**这个平台里的每
一分钱都欠在某个 Run 头上。**一次没有 Run 的压缩，账没有主。

三条路里选了「给它一个 Run」：
- 挂在会话最近那个 Run 上 —— 账是假的，那一轮已经结束了。
- 让 `run_id` 可空 —— 动这个系统最核心的记账假设，§12.4 的额度树要重想。
- **新建一个只做压缩的 Run** —— 钱有主，额度照管，上下文和模型客户端全现成。

## 3. 这推翻了一条写下来的决定

`Delivered` 的 docstring 原来写着：

> `run` 是 `None` 恰好当 `receipt` 不是：一条命令占用了这次认领，所以没有 Run
> 可挂、也没有东西会被阻塞。

「命令永远不产生 Run」当初成立的理由是**命令是纯数据操作、不花钱**。`/compact`
是第一条不成立的——所以它是第一个例外，而例外很窄：`runs.purpose` 只有
`answer` 和 `compaction` 两个值，只有后者跳过回答。

## 4. 五层，任何一层断了都是「写进去了没人够得着」

| 层 | 做什么 |
| --- | --- |
| migration 0054 + `RunPurpose` | `runs.purpose`，默认 `answer` |
| `RunSnapshot` | 带上 `purpose`，Worker 才看得见 |
| **Worker** | `purpose is COMPACTION` → 压完就结束，**不调模型回答** |
| 入站 | 打标记 **并** 提交一个 `COMPACTION` 的 Run；这一刻**不发回执** |
| 出站 | 压缩 Run 完成后，把 `covered`/`freed_estimate` 渲染成给人看的话 |

## 5. 测试的判据

- Worker 那条断言**只发生了一次模型调用**（那次摘要）。只断言「压了」的话，
  一个压完又顺手答一句的实现也会通过——而多那一次调用正是白花钱。
- 回执那条断言**不含「记下」**：不许把已经做完的事说成计划。
- 另一条守「压缩失败时说什么」：不报「已压缩」（假话），也不报「省了 0」
  （读起来像成功）。
- 入站那条断言**回执这一刻是 `None`**：压完之后才知道省了多少，那时才有话可说。

```
pytest packages/backend/tests/unit           2301 passed
pytest packages/backend/tests/integration    （见 PR）
ruff / pyright                               干净
alembic check                                No new upgrade operations detected
```

## 6. 这一遍没能证明什么

- ~~没有量过那个数字准不准~~ — **量过了，偏高约一倍，那个数已经不再报给用户。**
  见 §6.1 第四次走查。
- **没有验证过压缩 Run 撞上队首忙的情况。**`/compact` 提交 Run 走的是普通入口，
  队首在跑时它会排队——排队时用户看到什么，没测过。
- **没有验证过并发两条 `/compact`。**标记的读+清是单语句，但两个 Run 都建出来
  之后的行为没测。

## 6.1 真机走查（2026-09-03 补记）

这份记录原来在这一节写着「**没有真机走查**」。当天走了三次，三次都在同一个飞书
群、同一段会话上发 `/compact`，隧道全程关着（走的是长连接，不是 webhook）。

**第一次（12:51）——功能通了，同时暴露了一个产品缺陷。**

```
context_summary_billed : input 355 + output 1372 = 1727 token
context_compacted      : covered 2, source "model", freed_estimate 0
回执                   : 「已压缩。合并了 2 条旧消息。」
```

链路是通的（`channel_events.run_id` → `runs.purpose='compaction'` →
`status='completed'` → `replied_at`/`reply_note='sent'`），但那次压缩**花了 1,727 个
token，把上下文变大了一点，并且回执说它成功了**。修在
`fix(runs): 不让上下文变大的压缩不算压缩`（PR #77），spec §7.4.2 随之补了一条
（v2.9.3）。

**这里要说清楚的是：把它抓出来的不是测试。**当时后端全绿——`_honestly_widens`
查装得下、查边界、查有没有压到东西，三条都过，因为它从来没查过「省没省」。抓到它
的是这一次真机走查里那两行并排的数字。

**第二次——`IdempotencyKeyRequired`，一条消息都没留下。**

在第一次之前还有一次：`/compact` 提交压缩 Run 时幂等键传了 `None`，
`submit_end_user_run` 第一句就抛，**整个投递回滚**——`channel_events` 连行都没有，
用户看到的是「发出去了但没反应」。原因是单元测试里那个假的 `RunEntry` 照单全收空
键，而集成里 `/compact` 只走过网页那条入口（它自己带键）：**渠道这条路从来没有被真
的 `RunCoordination` 走过一次。**修在 PR #76，同时补了一条从长连接进来的集成测试。

**第三次（15:06）——修完之后的样子。**

```
context_compaction_skipped : reason "no_gain", covered 2
context_summary_billed     : 无
回执                       : 「这段对话压不动：能合并的历史比摘要本身还短，压了反而更长。历史原样保留。」
```

同一段对话、同一条命令，从「花 1,727 买负收益还报成功」变成「一个 token 不花、说
实话」。

**第四次（17:55）——带数字那句终于出现了，然后那个数字被证伪。**

```
context_summary_billed : input 1605 + output 3851
context_compacted      : covered 23, freed_estimate 3089, source "model"
回执                   : 「已压缩。合并了 23 条旧消息。每一轮大约少发 3089 个 token。」
```

`covered 23` 是对的：那段会话现存 25 条，减掉 `PROTECTED_RECENT_MESSAGES`（2）
正好 23——这是 `fix(runs): /compact 在诚实的前提下尽量多压` 之后的样子，在此之前
它只拿最老的 2 条。

**但 `3089` 是错的。**拿真实数据对了一遍：

| | 我们估的 | provider 数的 |
| --- | --- | --- |
| 被压的 23 条 | ~3,785 | ≤1,605（这个数还**包含**摘要提示词本身） |
| 那份摘要 | 692 | — |
| 报给用户的差值 | **3,089** | 实际约 **1,200–1,300** |

原因不是算错，是尺子拿错：`estimate_tokens` 的第一句 docstring 就是「An upper
bound... A bound rather than a count」。那段文本 6,838 个 ASCII 字符按 3 字符/token
估，provider 实际约 4.6 字符/token。确认过不是缓存造成的假象——`input_tokens` 是
整个提示词的大小，缓存部分在 `pricing.py` 里单独扣（`cached_input_tokens`）。

处理：回执不再报这个数（`fix(channels): 压缩回执用人话说，并且不报估算出来的数`）。
`freed_estimate` 保留在事件里，它仍然是「压了会不会更大」那道闸的判据——**用作
布尔判断（> 0）时上界是安全的，用作报给人看的量时不是。**

同一次走查还证实了一件好事：这次压缩一次性花 5,456 token（1,605 进 + 3,851 出），
按真实值每轮省约 1,300，**大约四轮回本**。

**第五次——用户说「我真没看懂」。**

那句回执写的是「每一轮大约少发 3089 个 token」。「一轮」和「token」都是这套系统
内部的词，而它要解释的事其实很朴素：模型不记事，每次说话都要把整段历史重发一遍。
三句回执随之全部重写，并加了一条测试守着「回执里不许出现内部词汇」。

## 7. 不声称什么

- **不声称压缩一定成功。**摘要模型不可用时 Run 照样完成，回执说的是
  「这次没能压缩成功，历史原样保留」——那句话有测试守着。
- **不声称这次压缩不花钱。**它和普通对话一样计费、一样受 §12.4 管。压缩是为省钱
  做的，但它自己要花一次摘要调用的钱。唯一的例外是「主动没压」那一条路
  （`context_compaction_skipped`）：那时一次调用都不发，2026-09-03 的第三次走查
  验的正是这一点（那个 Run 的事件流里没有 `context_summary_billed`）。
- **不声称长对话上的压缩验过了。**三次走查压的都是同一段短对话，`covered` 都是 2。
  「合并了 N 条、每轮少发 M 个 token」那句带数字的回执，**从没在真机上出现过**——
  测试里有，线上没有。
- **不声称「命令不产生 Run」这条规矩还成立。**它现在有一个例外，理由写在
  `RunPurpose` 和 `ingestion.py` 的注释里。
