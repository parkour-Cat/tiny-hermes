# 沙箱按需获取：只回文字的消息不再排队等沙箱

日期 2026-10-21。分支 `feat/lazy-sandbox-allocation`（PR #113）。规格 v2.15（`46438aa`）。
测试 `c9a6b4f`、`5fb9709`，实现 `018d85e`，测试和实现分开提交。

## 为什么有这一遍

容量路线图 P1 第 16 项。以前只要 Agent 绑定了沙箱工具，Worker 在每个时间片调模型**之前**就先
建沙箱，哪怕用户只说一句「你好」。§21.3 的准入按实例上限算，这台 VM 的预算只够 3 个实例，于是
只回文字的消息和真正要跑命令的长任务抢同一批名额。

## 改了什么

- 规格 v2.15（§1.15、§16）：沙箱在「某一轮第一次需要时」获取。
- Worker：模型这一轮要调用沙箱里的工具，或声称完成而 Agent 声明了要在沙箱里检查的完成条件，
  才 acquire。只回文字、只调平台工具 / HTTP / MCP 的轮不占沙箱。
- 拿不到沙箱时：这次模型调用照实记账，回复不进历史，Run 照旧回到 `queued`（内存不够时等 10 秒）
  或 `failed`。
- 探针加了 `--short-tool`：给短消息的 Agent 绑定工具，但场景本身不调用。没有它，探针的短消息
  从来不带工具，测不出这个问题（[单机档验收](2026-09-30-tier-a-acceptance.md)「没能证明什么」第 3 条）。

## 测试过了

- 后端单元测试 2507 条通过；集成测试（含 sandbox）1143 条：第一遍 1 条失败，是靠「打招呼也建沙箱」
  拿沙箱的夹具，改成跑一轮命令后该文件 10 条通过。ruff、pyright 0 errors。
- PR #113 的 CI 全绿；compose-e2e 按日志确认 24 条用例真的跑了、全部通过。
- 红测试先提交，确认失败原因是「打招呼时调用了 acquire」「提示出现在第一次请求」等，而不是别的。

## 走通了什么

同一台 8 核 / 7.8 GiB 的 OrbStack VM，先用 main（`fe089f6`）、再用本分支，负载完全相同：

- 2 个 Worker 容器 × `WORKER_CONCURRENCY=16`，确定性模型延迟 2 秒；
- 沙箱预算取默认（主机内存一半，约 3 个 1 GiB 的实例）；
- 6 个长任务，各 15 轮（每轮一条写工作区的命令），先启动；
- 5 秒后每秒 1 条短消息，共 120 条，发给**绑了 `shell.exec`、场景只回文字**的 Agent。

```bash
DETERMINISTIC_MODEL_DELAY_MS=2000 WORKER_CONCURRENCY=16 \
  docker compose --env-file ../../.env up -d --force-recreate --scale worker=2 --wait
uv run --no-sync python scripts/concurrency_probe.py --rate 1 --seconds 120 \
  --long-tasks 6 --rounds 15 --short-tool shell.exec --label after-lazy
```

每一遍之前都确认了两个 Worker 容器里的代码（main 里没有 `_needs_sandbox`，分支里有）和环境变量。

| | main（调模型前就建） | 本分支（按需） |
|---|---:|---:|
| 完成 / 失败 | 126 / 0 | 126 / 0 |
| **短消息端到端 P50 / P95 / 最大** | 33.7 / **140.3** / 192.0 s | 2.07 / **2.10** / 2.13 s |
| 长任务端到端 P50 / P95 | 73.4 / 182.6 s | 52.0 / 68.1 s |
| 整体吞吐 | 0.58 Run/s | 0.98 Run/s |
| 排队最多 | 52 | 4 |
| `run_lease_acquired`（领取次数） | 704 | 138 |
| `sandbox_cache_reset`（新建沙箱） | 127 | 6 |
| 同一时刻沙箱最多 | 3 | 3 |
| 模型调用 / 工具调用 | 216 / 90 | 216 / 81 |
| Worker 报错栈 | —— | 0 |

- 短消息只要一次 2 秒的模型调用。分支上端到端 P95 是 2.10 秒，也就是**几乎不排队**；main 上
  P95 是它的约 67 倍。
- main 上 120 条短消息每条都新建了一个沙箱（127 = 120 + 6 + 1），并在预算被长任务占满时被拒、
  等 10 秒、再领取：领取次数 704，比分支多约 570 次。
- 分支上只有 6 个长任务建了沙箱，短消息一个都没建。
- 长任务也快了：不再和 120 条短消息抢那 3 个名额。

## 发现

1. **探针的「排队时间」测不到这个问题。**两遍的短消息排队 P95 都是 0.0 秒。探针用的是 Run 行上的
   `started_at`，那是**第一次**被领取的时间；之后被拒、回到队列、再被领取的时间全算在「执行时间」
   里。所以 main 上 140 秒的等待只出现在端到端时间里。以后看沙箱相关的场景，要看端到端，或者
   改探针去数领取次数。这一遍没有改探针的口径。
2. **规格 §1.15 的代价 1 实测到了：9 次。**分支这一遍，Worker 日志有 9 条
   `no sandbox yet ... reason=memory_budget_exhausted`，都是长任务「模型已经要了命令、却拿不到
   沙箱」。这 9 次调用记了账，回复被丢弃。
   - 确定性的 `long_task` 场景按 `round_index`（已消耗的调用次数）数轮次，所以它把这 9 轮当作做过了：
     长任务一共只跑了 81 条命令（应为 90），模型调用数却和 main 一样是 216。
   - **换成真实模型，就是重新问一遍：多 9 次调用，每个长任务的调用上限也提前用掉相应的次数。**
     main 上被拒发生在调模型之前，所以没有这笔浪费。
   - 规模：6 个长任务抢 3 个名额，每个长任务平均 1.5 次。名额越紧，这笔浪费越大。

## 这一遍没能证明什么

- 模型是确定性的，工具只是 `printf`，沙箱合计最多 7 MiB。真实工具的内存、真实模型的流式解析
  都没有测。
- 第 2 条发现里，「真实模型会多调 9 次」是推算，不是实测：确定性模型不会重新回答同一轮。
- 冷启动的沙箱创建和工作区恢复从调模型之前挪到了模型回复之后，这一遍的工作区几乎是空的，
  恢复开销没有测到。
- 「缓存重置提示在时间片结束前没送到」这种情况，只在规格里写明，没有在现场统计发生了多少次。
- 每种代码各跑一遍，每遍 120 秒的提交窗口。

## 不声称什么

- 不声称短消息在任何负载下都不排队：这一遍 32 条通道远多于同时执行的 Run，通道没有成为瓶颈。
- 不声称「拿不到沙箱就丢掉回复、重问一次」在名额很紧时仍然划算；那时应当考虑别的做法（例如
  拿不到沙箱的 Run 优先排队）。这是规格层面的决定，这里不做。
- 不声称 main 上 140 秒的数字适用于别的预算或别的长任务数：它取决于被长任务占满的时间。

测完之后，栈已恢复成 1 个 Worker、`WORKER_CONCURRENCY=1`、模型延迟 50 ms、调用上限 20，没有
遗留的沙箱。**镜像是本分支的代码**（main 上的镜像在第一遍之后被覆盖了）。
