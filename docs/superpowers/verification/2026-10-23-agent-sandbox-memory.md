# 沙箱内存按 Agent 配置

日期 2026-10-23。分支 `feat/agent-sandbox-memory`。[设计](../specs/2026-10-23-agent-sandbox-memory-design.md)，
产品设计 v2.22（§21.3）。

## 做了什么

| 部分 | 内容 |
|---|---|
| Agent | spec 新增可选的 `sandbox.memory_mb`，最小 256，没有上限字面量；没写时规范化后不带这个键，已发布版本的哈希不变 |
| 上限 | 新配置 `SANDBOX_CEILING_MEMORY_MB`（默认 4096），不能小于 `SANDBOX_MEMORY_MB`；保存草稿和发布时超过上限返回 422 `sandbox_memory_ceiling_exceeded`，同时给出两个数字 |
| 传递 | worker 从已发布版本取值，`acquire` 里带上；不声明就不带这个键，所以发给 controller 的请求和以前一样 |
| controller | 按请求的值预约、设容器内存上限、记录到 `sandbox_instances.memory_mb`；不在 [256, 上限] 内，或比整个预算还大，拒绝 `memory_out_of_range`，Run 失败，不排队 |
| 控制台 | Agent 详情页「安全阀」里加「沙箱内存（MB）」，可以留空；清空后草稿里不再带这个键 |
| 运维 | Compose 加了 `SANDBOX_CEILING_MEMORY_MB`；运维手册 §8.4 写了准入怎么算、什么时候该先看这个值 |

## 测试过了

- 后端单元测试：新增 Agent 侧 8 条、配置 2 条、传输层 4 条；全量 2709 passed。
- 后端集成测试全量：1296 passed、1 skipped（比 main 多 11 条，就是下面这些）。
- 集成测试（真 Docker、真数据库）：
  - Agent 声明 384 时，容器的 `HostConfig.Memory` 确实是 384 MiB，`sandbox_instances.memory_mb` 也是 384；
  - 预算 512 时，默认 512 的沙箱只放得下 1 个，声明 256 的放得下 2 个；
  - 超过上限、低于 256、比整个预算还大，三种都被拒绝为 `memory_out_of_range`，而且什么都没有留下；
  - worker 把已发布版本里声明的值传给了 acquire，没声明时传的是空；
  - 经过 HTTP：保存 256 能读回来；8192 返回 422，详情里有 8192 和 4096；128 返回 422。
- 前端：4 条新测试（输入值进入草稿、加载的值保存后保留、留空不带键、清空后去掉键），前端全量
  399/399，tsc 和 eslint 通过。
- 先写测试、看它失败、再实现，提交顺序是测试在前。两处例外：经过 HTTP 的那 3 条是实现之后补的，
  没有见过它们失败（提交说明里写了）；前端「加载的值保存后保留」那条一开始就通过，因为表单会把
  不认识的字段原样带过去。正因为这样，又补了「清空后去掉键」那一条，它确实失败过。

### 端到端：用真实模型再跑一次

用新代码重建镜像，实例默认值保持 1024（controller 启动日志：`sandbox_memory_mb=1024
sandbox_memory_budget_mb=4002`），同一个栈上先后跑两组，各 20 个[长任务压测](2026-10-23-real-task-probe.md)
里的编程任务：

| | Agent 声明 256 | Agent 不声明（默认 1024） |
|---|---:|---:|
| 数据库里记录的沙箱大小 | 20 个全是 256 | 20 个全是 1024 |
| 同时存在的沙箱 | 14 | 3 |
| 每个任务执行 P50 / P95 | **11.0 / 32.1 s** | 42.6 / 77.2 s |
| 其他（排队等沙箱和平台处理）P50 / P95 | **3.2 / 15.7 s** | 35.9 / 71.7 s |
| 完成 | 19，另有 1 个暂停 | 20 |
| 总耗时 | 75 s | 81 s |

- 值从 Agent 一路传到了容器：数据库里的大小和声明的一致，并发的沙箱数从 3 个变成 14 个。
- 暂停的那 1 个和这次改动无关：模型在原地打转，调了 39 次模型，撞到每个任务 40 次的预算，
  按设计暂停（`run_limit_reached`）。总耗时 75 秒是被它拖长的；其他 19 个的执行中位数是 11 秒。
  上一次实例默认值直接设 256 时是 25 秒，那次没有出现打转的任务。

## 这一遍没能证明什么

- **真的写满 256 MB 会怎样，没有测。**这次的任务每个只用几 MiB。进程被内存上限杀掉时，模型看到
  的输出是什么、会不会知道该怎么办，都没有验证。
- **控制台没有在浏览器里打开过**，只有组件测试。
- 前端不知道平台上限，输入框不拦超过上限的值，靠服务器返回 422。
- 端到端每组只跑了一次。
- 调低上限后，已发布的大版本在拿沙箱时失败，这一条只有集成测试，没有在真栈上走过。

## 不声称什么

- 不声称 256 是合适的值。它只适合这一种轻量任务；默认值仍是 1024。
- 不声称这解决了沙箱主机的容量问题。它只是让轻量 Agent 不再白占名额；一台主机的总预算没变。
