# 真实模型压测：DeepSeek

日期 2026-10-23。分支 `feat/probe-real-model`。[容量方案](../plans/2026-09-29-enterprise-capacity.md)
§2 一直写着「真实模型每路要多少 CPU 还不知道」，这一遍第一次用真实模型量了。

## 怎么测的

- 模型：DeepSeek `deepseek-chat`，作为平台级的 OpenAI 兼容端点注册。Key 存在平台的加密密钥库
  里，出站经过 egress-proxy。
- 压测探针新增 `--endpoint`：短消息用这个端点回答，人设是「用一句话回答」，控制回复长度和费用。
  再加 `--channels`：每条短消息是不同的终端用户（交互），不受每人上限约束。
- 栈：本机 Compose，2 个 worker × 16 条通道（单机档的配置），开监控栈，trace 采样 10%。
- 负载：每秒 1、2、4 条，各持续 60 秒，一共 420 个 Run。
- 本机：macOS 上 8 核 / 7.8 GiB 的 OrbStack 虚拟机，不是 §24.1 的参考机。

## 结果

| 每秒 | Run | 失败 | 端到端 P50 / P95 | 排队 P95 | 同时执行 平均 / 峰值 | worker CPU（两个进程合计） | 每个 Run 的 worker CPU |
|---:|---:|---:|---|---:|---|---:|---:|
| 1 | 60 | 0 | 1.23 / 1.41 s | 0.03 s | 1.2 / 2 | 0.23 核 | 0.24 核·秒 |
| 2 | 120 | 0 | 1.22 / 1.50 s | 0.02 s | 2.4 / 4 | 0.46 核 | 0.23 核·秒 |
| 4 | 240 | 0 | 1.27 / 1.60 s | 0.02 s | 4.9 / 7 | 0.85 核 | 0.22 核·秒 |

- worker CPU 和吞吐成正比：**每个短消息 Run 大约用 0.22 核·秒**（Prometheus 的
  `process_cpu_seconds_total`，按窗口取速率）。api 进程每秒 0.03 到 0.04 核。
- 数据库连接最多 43 个。worker 内存每个进程 120 到 141 MiB。
- 用量：420 个 Run，输入约 4.96 万 token、输出约 0.97 万 token（`tiny_hermes_model_tokens_total`）。

### 时间花在哪：从 trace 看

38 条被采样的 trace（每条是一个 Run）：

| | P50 | P95 |
|---|---:|---:|
| 时间片（`run.slice`） | 1178 ms | 1445 ms |
| 其中模型调用（`model.call`） | 1137 ms | 1407 ms |
| **时间片里除去模型调用的部分** | **44 ms** | **174 ms** |
| 从建 Run 的请求到结束（整条 trace） | 1277 ms | 1616 ms |

**平台自己的开销中位数是 44 毫秒，其余全是在等模型。**每个 Run 都只调了一次模型。

Prometheus 的直方图给的模型调用 P50 是 1.6 秒，比整个 Run 还长。原因是这个值是在 1 秒和 2.5
秒两个分桶之间插值算出来的，分桶太粗。以 trace 为准。之后可以考虑在 1 到 2.5 秒之间加分桶。

## 这对容量意味着什么（推算，不是实测）

- **短对话，worker 的 CPU 不是瓶颈。**每条消息约 0.22 核·秒。比如 6000 人里同时有 600 人在聊、
  每人每 2 分钟发一条，就是每秒 5 条，约需 1.1 核。
- **之前用确定性替身测的「每路 1.3% 到 2.6% 个核」，在真实模型下不成立。**按每路算，这次在每秒
  4 条时约 17%：0.85 核除以平均 4.9 路。替身不走网络、不解析模型返回，所以低估了 CPU。不过
  真实模型的大部分时间在等，所以每路占得多，每条消息却花得少。
- 每路仍然主要是在等模型。并发上限取决于模型那边能接多少（DeepSeek 在每秒 4 条时没有变慢），
  以及带工具的长任务要多少沙箱。

## 这一遍没能证明什么

- **只测了短对话**：一次模型调用，没有工具，没有沙箱。带工具、多轮的长任务没有用真实模型测：
  探针的长任务按固定脚本走，真实模型不会照着走。
- 最高只测到每秒 4 条，没有找到拐点。DeepSeek 在更高并发下会不会限流、变慢，不知道。
- Postgres 的 CPU 这次没有采。
- 只测了一个模型；回复被限制得很短。回复长、上下文长时，每个 Run 的 CPU 会更多（解析、记账、
  写事件）。
- 环境不是参考机；每档只跑了一次。

## 不声称什么

- 不声称「一台机器能撑多少人」。这次证明的是：短对话的平台开销很小，瓶颈不在 worker 的 CPU。
- 这次的 Key 在对话里出现过，建议用完作废。平台里的 `deepseek-probe` 密钥和
  `deepseek-chat-probe` 端点还留在本机库里，没有删。
