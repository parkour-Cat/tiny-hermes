## 为什么有这一遍

第 5 项原文：「现在每个有人看的 Run，每 0.5 秒查一次库，还没测过」。所以先量，再改。

## 怎么改的

- **写的一方**：`SqlRunStore.append_events` 在 session 上记下 Run；SQLAlchemy 的
  `after_commit` 钩子在**提交之后**把它发到 `tiny-hermes:run-events`，回滚的不发。
  写事件的地方有 Worker、Scheduler 和十几条 API 路径，各自在不同地方提交，
  `append_events` 是它们唯一的共同点，提交是别的进程第一次能读到它们的时刻。
  发布失败只记日志，提交照样成功；每次断线只记一条。
- **读的一方**：API 的事件流（`EventStreamHub`）原来每个 Run 一个共享轮询、每 0.5 秒一次。
  现在订阅确认之后，房间收到这个 Run 的通知才读，否则每 5 秒兜底读一次。订阅断了（报错，
  或者 10 秒内连自己的 PING 都没回音）立刻退回 0.5 秒，重连后每个房间补读一次。
- 通知只用来提前读，读的仍是数据库。

## 测试过了

- 后端单元测试 2612 条全部通过；集成测试 1191 passed、1 skipped（skip 的是原有的 TLS
  socket 权限那一条）；ruff、pyright 0 errors。
- 新测试：
  - 单元：有通知时房间不再空读，叫醒才读；没有通知通道时照常轮询；有通道但通知丢了，兜底
    间隔到了照样读到；通道断了立刻改回轮询；通道恢复时每个房间补读一次；读到一半来的通知
    不丢；叫醒一个没人看的 Run 不出错。Worker、Scheduler、API 的 session 工厂只在配了
    Redis 时带上通知。
  - 集成（真 Postgres、真 Redis、真 uvicorn）：提交后才通知、回滚不通知、没写事件不通知、
    通知抛错不影响提交；通知能到监听方；连不上 Redis 时监听不报健康、不抛错；
    **有通知的事件 1 秒内到达订阅者；没通知的事件 1 秒内不到、10 秒内到**——后一条证明
    API 真的不再每 0.5 秒查；`REDIS_URL` 指向不存在的端口时，事件 1.5 秒内到达。
  - 本地把 `REDIS_URL` 指向空端口跑了事件流相关的两个文件：要 Redis 的 3 条 skip，其余通过。
    CI 的降级那一轮也是这样跑的。

## 走通了什么

单机栈，确定性模型，延迟 50 ms，`WORKER_CONCURRENCY=1`。镜像同上一份记录，是在已有镜像上
覆盖 `packages/backend/src` 得到的。

做法：先停 Worker，建 N 个 Run（它们会一直排队，没有新事件），每个开一个 SSE 订阅；看
`pg_stat_database` 的事务数和返回行数。然后启动 Worker，每个 Run 跑 3 轮，比较每条事件的
`occurred_at` 和订阅方收到的时间。基线是同一时段没有订阅者时的读数，后面的「多出」都减掉了它。

| | 在看的 Run | 多出的事务/秒 | 多出的返回行/秒 | 提交到收到 p50 / p95 / 最大 |
|---|---:|---:|---:|---|
| 改之前 | 50 | 175 | 46,800 | 320 / 834 / 1202 ms |
| 改之后 | 50 | 29 | 8,000 | 10 / 67 / 583 ms |
| 改之后，Redis 一直停着 | 20 | 74 | 17,000 | 292 / 585 / 655 ms |
| Redis 恢复后，API 没重启 | 20 | 6 | 0 以下（噪声） | 24 / 39 / 67 ms |

- 改之前每个空等的 Run 每秒约 3.5 个事务、940 行；改之后约 0.6 个事务。
- Redis 停着时回到改之前的水平，延迟也一样，说明退回轮询是生效的。Worker 日志只有一条
  `run event publish failed; subscribers will poll`，API 日志有一条 `run event push lost`。
- **第一次做 Redis 停机这一轮时测错了**：脚本用 `docker compose start worker` 重新拉起
  Worker，Compose 顺带把它依赖的 Redis 也启动了，于是「停机」那一轮的延迟实际是有 Redis 时的
  10 ms。空等那段是真停机。改用 `docker start` 只拉起 Worker 容器后重测，才是上表那一行。

## 这一遍没能证明什么

- **只测到 50 个同时在看的 Run，一个 API 进程。**§24.1 要求 500 个连接，没有在新代码上重跑
  `benchmark_m1.py` 的 SSE 门槛。
- 所有 API 进程订阅同一个频道，每个进程收全部 Run 的通知，然后丢掉没人看的。通知多到什么
  程度这会成为瓶颈，没有测。
- 没有测「Redis 半开」：TCP 连接还在但对面不回。代码按 10 秒没回音判断断开，这个判断只有
  单元层面的逻辑，没有真构造过半开的连接。
- 没有测只有 Worker 连不上 Redis、API 连得上的情况。按设计这时事件最多晚 5 秒；手册里写了。
- 改之前和改之后的两次测量相隔约一小时，没有交替多次。基线（没有订阅者）的读数本身在
  28–33 事务/秒、3,000–13,000 行/秒之间跳，行数那一列只能看数量级。

## 不声称什么

- 不声称 Redis 不重要了。它停机时数据库压力回到原来的样子，有几百个人在看时很明显。
- 不声称事件一定在 5 秒内到达。兜底间隔是 5 秒，但 API 自己的读（每次带一批 200 条）、
  数据库慢的时候都另算。
- 不声称这解决了 6000 用户规模下的 SSE。那要多个 API 进程，频道怎么分是另一件事。
