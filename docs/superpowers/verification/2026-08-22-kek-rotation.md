# Secret KEK 轮换 — 验收记录 2026-08-22

> 产品：v2.5 §374、§376、§1154 场景 11、§27.3 第 5 条。
> 前置：M1 已交付「Secret 信封加密、KEK 标识和可恢复轮换基础流程」（§1274）。

## 1. 这一条的验收是什么

「执行 Secret KEK 轮换，在中断后恢复并完成全部重包。」

M1 的基础流程已经在：按旧 `key_id` 迭代、`UnwrapFailed` 记为不可恢复而不是静默跳过、
审计带 `processed`/`remaining`/`unrecoverable`。**这一遍补的是两个洞。**

## 2. 洞一：§376 说的是三件事，实现只做了两件

原话是「重包、**校验**和审计完成前不能删除」。实现做了重包和审计，**没有校验**。

后果很具体，而且是丢密钥那一类：审计里的 `processed` 说的是「我改写了这些行」，
而运维**正是拿这条审计决定能不能销毁旧 KEK**。这两句话不是一回事。

**修之前的实测**：一个损坏的重包报 `processed=1, remaining=0`——审计说「完成」，
下一步就是销毁那把唯一还能打开它的钥匙。

修法上的两个判断：

- **读回验证，不是验证刚算出来的那个值。** 要防的不是密码学——AES-GCM 不会静默
  损坏——而是它周围的管道：nonce 落错列、`key_id` 和封装时的 AAD 不一致、写了一半。
  这几种都产生「看起来轮换过、其实打不开」的行，而验证内存里那个信封**一个都发现
  不了**。
- **比对明文，不是「能不能解开」。** 一个解开后得到错误 DEK 的包，和根本打不开一样
  是丢了，只有比对能区分。

失败时把旧包放回去：那一刻旧 KEK 还在，**恢复是可回滚的结果，留一个轮换过但读不出
来的行不是**。该行仍计入 `remaining`，不会有人把审计读成完成。

## 3. 洞二：校验结果到不了线上

`unverifiable` 加进了领域结果，**没有加进响应模型**，于是它停在服务边界。

这是本分支上 `RunResponse` 丢字段的同一个形状，只是这次丢的偏偏是**运维销毁旧 KEK
之前要看的那个数字**。所有服务层测试自始至终都是绿的——这类洞只有 HTTP 边界的测试
才看得见，所以那条测试先写、先红。

## 4. 中断恢复：对着真实数据库

单元套件早就用内存 store 证明了可恢复。它证明不了的是**恢复所读的那份状态挺过了
进程结束**——而中断按定义就是「内存里什么都没留下」。

新测试先把一行改成已轮换（模拟中断前已提交的工作），再起一个**全新的 app**：
不共享服务、不共享 session，只剩已提交的东西。

它顺带说明了一件设计上的好事：**`key_id` 本身就是进度记录**。§1154 写的是「从审计
记录的最后进度继续」，而这里比读检查点更强——**没有第二个地方可以和真相脱节**。
已经在新 key 上的行不会被再选中，所以恢复不重做已完成的工作，也就不浪费「两把钥匙
必须同时存在」的那个窗口。

## 5. 场景 11 的前半

「只取得数据库备份而没有部署侧 KEK 时，无法解密 Secret。」

这是架构主张（§374 要求 KEK 不能和数据库放一起），值得一条测试，因为**它正是那种会
悄悄失效的性质：加一个图方便的列、一个调试字段，备份就变成泄露**。

断言的是：表里没有 `plaintext`/`value` 列、密文里搜不到明文、换一把不是 KEK 的钥匙
解不开。

## 6. 这一遍没能证明什么

- **没有在真实部署上跑过一次完整轮换。** 全部是对着测试数据库的。规模、耗时、
  长事务的影响都没有测量——一个有十万条 Secret 的工作空间会怎样，这里答不了。
- **没有做「旧 KEK 真的被销毁之后」的演练。** 测试里两把钥匙始终都在。§376 关心的
  正是销毁那一刻，而证明那一刻安全需要真的删掉一把钥匙再验证，这一遍没做。
- **`unverifiable > 0` 时没有自动化的补救路径。** 实现把旧包放了回去并计数，
  但接下来该怎么办（重试？换一把新 KEK？逐条排查？）没有写成流程，只有日志。
- **没有并发轮换的防护。** 两个管理员同时点 rewrap 会各自迭代同一批行。
  单行的写入是安全的（各自读到的 `key_id` 决定它是否被选中），但**没有测过**，
  也没有锁。
- **撤销与工作空间范围控制（§376 末句）不在这一条里**，没有做。
