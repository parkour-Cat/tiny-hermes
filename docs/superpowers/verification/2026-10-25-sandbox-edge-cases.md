# 两处边界：沙箱反复消失，流式传输被硬断开

日期 2026-10-25。分支 `test/sandbox-edge-cases`。**只加了测试，没有改代码。**两条测试都是在行为已经存在之后写的，
第一次断言写对时就通过了，留下来是为了守住这个行为。

## 一、沙箱一直消失

#155 之后，沙箱没了就立刻打断 Run，然后由 scheduler 恢复。要确认的是：如果沙箱每次都没了，Run 不会在
「打断」和「排队」之间无限循环。

测试：假沙箱每次执行都报 `SandboxGone`，恢复次数上限是 2，循环「worker 跑一片 → scheduler 扫一次」。

结果：打断 3 次之后，事件流以 `run_recovery_failed` 结尾，Run 变成 `failed`。工具执行一共调用了 3 次。

写测试时，我先以为失败的事件叫 `run_failed`，看了实际的事件流才改过来。

## 二、流式传输发到一半被掐断

controller 在发送途中崩溃时，既不会发 `ERROR` 帧，也不会写回答行。

测试：服务端发出一部分数据后，直接中止 socket。unix 和 TLS 两种传输都测了。

结果：客户端立刻报 `ControllerClient.Unreachable`（意思是「什么都没决定」），没有等到超时。服务端随后的一次正常
调用完整收到了全部数据。

## 测试过了

- 这两个测试文件：50 passed。

## 这一遍没能证明什么

- 第一条用的是假沙箱和单个进程，没有在真实栈上反复删容器；恢复次数上限是测试里设的 2，生产用的值没有单独测。
- 第二条中止的是测试服务端自己的 socket，不是真的杀掉 controller 进程。

## 不声称什么

- 不声称流式协议的所有失败情况都覆盖了：目前测过的是发送途中出错（#151）和发送途中被掐断（这次）。
