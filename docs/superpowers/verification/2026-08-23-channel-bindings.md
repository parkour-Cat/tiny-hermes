# 渠道绑定：让整条渠道第一次有人够得着 — 2026-08-23

> 产品：v2.5 §20.1（Channels 是 M3 导航项）、§4.6「密钥、安全策略与渠道」。
> 起因：`2026-08-23-m3-milestone-deliverables.md` §7 那次路由可达性普查。

## 1. 之前是什么状态

飞书渠道的每一块都做完了而且能用——验签、解密、`ON CONFLICT` 去重、摄入成
Run、阻塞通知，加上迁移 0036/0037/0038。

**唯一往 `channel_bindings` 插过行的地方是测试。** 没有路由、没有服务方法、
没有页面。整条渠道只有手工往 Postgres 里写一行才够得着。

上一份渠道验收记录写着「Webhook 那一侧完整可用」。那句话**在后端是对的，
在产品上是假的**——这正是这个仓库反复栽的那个跟头，而且这次是最大的一次。

## 2. §4.6 那一行逐字落地

| 主体 | 规格 | 实现 |
|---|---|---|
| 平台/工作空间管理员 | 管理元数据，不查看明文 | 建、列、停用；响应里**没有能装密钥的字段** |
| 开发者 | 使用已授权绑定 | 能列，不能建 |
| 查看者 | **否** | 403，不是空列表 |

查看者那一条是最容易做错的：整个控制台大多数资源给查看者「只读」，这里是
「否」。而且一个空列表会说「这个工作空间什么都没发布」——那是另一句话，
而且是假的。所以前端把 403 渲染成一句话，不是渲染成空表。

「不查看明文」不是靠记得不返回某个字段做到的，是**结构性的**：
`ChannelBindingView` 里没有那个字段，`_view()` 也没地方放。断言写成
「整个响应体里不出现那串明文」，而不是逐字段查——逐字段的检查会在有人加新
字段的那天照样通过，而那正是它该失败的时候。

## 3. 两个「早点说」的拒绝

- **`channel_key_required`**：飞书绑定没有密钥引用。迁移 0037 的 CHECK 也拦，
  但拦在数据库里就变成一条完整性错误，而不是一句人能照着改的话。
- **`channel_key_unknown`**：引用指向一个不存在的密钥。这条**必须**在这里拦：
  这样的绑定会接受它永远解不开的投递，然后在几小时后的一个 webhook 里失败，
  而犯错的人根本没在看那里。

密钥是**选**出来的，不是填出来的：自由文本的引用正是产生上面那种绑定的方式。

## 4. 停用而不是删除

`channel_events` 外键指向绑定，那些行是这条渠道已经投递过什么的记录。而且
页面照样列出已停用的绑定——藏起来会让「曾经开过的渠道」看起来像「从来没开过」。

## 5. 那条 e2e 第一次是白跑的

第一版 `channels.spec.ts` 进 CI 时是绿的，而且**执行了零条**：
`playwright.config.ts` 的 `projects` 是显式白名单，没被任何 project 匹配的
spec 既不跑也不报错，日志里只是 `Running 17 tests` 而不是 18。

补了 channels 那个 project，并加了一道配置加载期的检查（见
`2026-08-23-m3-milestone-deliverables.md` §9）。合并前的那一次日志是
`Running 18 tests`，channels 那条 4.1 秒通过。

## 6. 这一遍没能证明什么

- **没有证明这个绑定能真的收下一次投递。** 用未签名的请求去探 webhook 是没有
  意义的：未知绑定、已停用绑定、签名错的真绑定，三者**故意**都回 401
  （`feishu_service.UnknownChannelBinding` 的注释写了为什么）。要证明它需要一个
  正确加密的信封**加上**一个已发布的 Agent 让 Run 落地，那是另一条路。
  e2e 的 docstring 里明写了这一点，没有拿半个证明冒充整个。
- **没有真实飞书租户。** §929 的断线补投演练、WS 长连接、卡片 JSON 渲染，
  状态和 `2026-08-22-feishu-channel.md` 里一样，没有变。
- **`app_id` 没有被校验过格式。** 它是元数据，写错了要到投递时才看得出来。
