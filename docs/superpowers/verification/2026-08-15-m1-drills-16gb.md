## 3. The failure: a 100 MiB checkpoint dies under the 20 s lease

`704b05d` lowered the default `worker_lease_seconds` from 30 to 20 (and the
Scheduler scan from 5 s to 1 s) so §24.1's "killed Worker requeues a
retry-safe Run within 30 s" cell could pass. The lease is not a §24.1
number, so lowering it was legitimate. **It also breaks the drill's large
commit.**

### 3.1 Reproduction

Same stack, same tree, only `WORKER_LEASE_SECONDS` differs:

| Lease | Result |
|---|---|
| 20 s (this branch's default) | **FAIL** — 3 runs out of 3, the large-commit Run ends `failed` |
| 30 s (the previous default) | **PASS** — large commit `files=501 bytes=~100MiB took=8.1s`, `worker_rss=104MiB`, leftovers 0 |

The work itself takes 8.1 s. It is not "the commit is slower than a 20 s
lease".

### 3.2 What the Run did

```
14:22:50  run_created
14:22:50  run_lease_acquired
14:22:50  sandbox_cache_reset
14:23:17  run_interrupted        {"reason": "lease_expired"}
14:23:17  run_recovery_approved  {"replay_safe": true}
...  the same 27-second shape three more times ...
14:24:38  run_recovery_failed
```

Four attempts, each exactly 27 s, then the recovery budget is spent. No
`run_step` event, no `workspace checkpoint decided` line in the Worker log,
and no exception anywhere.

### 3.3 What the lease row did

Sampling `worker_leases` once a second through a failing attempt:

```
14:41:04  version=7  expires=14:41:23   lease acquired
14:41:11  version=8  expires=14:41:30   one renewal, +7s ≈ lease_seconds/3
14:41:18             (a second renewal is due here and never happens)
14:41:30                                 lease expires; the Scheduler takes the Run
```

**Exactly one renewal lands, then the renewal stops for the rest of the
slice.** Every failing attempt has this shape, which is where the 27 s comes
from: 20 s of lease, extended once at +7 s.

### 3.4 Why the lease length decides it

`_renew_until_done` renews every `lease_seconds / 3`: 6.7 s at a 20 s lease,
10 s at a 30 s lease. The large commit's slice lives about 8 s. At 30 s the
first renewal is never due before the slice ends, so the renewal path is
never exercised and the Run completes. At 20 s the slice outlives the first
renewal, and the second one never arrives.

Facts about that path, all in `worker.py`:

- `handle.version` is written in exactly one place: after a successful
  renewal.
- When `renew_lease` matches no row, the task sets `handle.lost = True` and
  **returns silently** — no log, no event, no failure. The slice keeps
  working on a lease nobody is extending.
- `record_slice` does not bump the lease version; it releases the lease.

**Root cause is not pinned yet.** The two candidates are the renewal task
being starved of the event loop while the ~100 MiB checkpoint runs, and its
predicate ceasing to match. Distinguishing them needs one instrumented run
of the renewal task, which this record does not have.

### 3.5 Why §24.1 cannot see this

The benchmark's `workspace_large` cell measured 2.43 s and 2.38 s. Both are
shorter than the 6.7 s renewal interval, so no §24.1 cell ever reaches a
second renewal. A green §24.1 table and this failure are consistent; the
table does not cover it.

## 4. Repository change made for this

`deploy/compose/compose.yaml` now passes `WORKER_LEASE_SECONDS`, the way it
already passes `WORKSPACE_MAX_BYTES` and `DETERMINISTIC_MODEL_DELAY_MS`.
Without it the two configurations above cannot be compared without editing
the source. The default is unchanged.

## 5. Explicitly not claimed

- That the lease should go back to 30 s. That would re-break §24.1's 30 s
  worker-recovery cell, which is why it was lowered. Both cannot be true
  until the renewal path is fixed.
- A root cause for §3.4.
- `0.1 Technical Preview`, CI green, or local SSD — unchanged from
  `2026-08-15-m1-benchmark-16gb.md`.
- A generated-secret Compose stack; this run used the Compose defaults.
