# scheduler 的扫描并发执行

日期 2026-10-24。分支 `perf/scheduler-concurrent-scans`。[设计](../specs/2026-10-24-scheduler-concurrent-scans-design.md)。

## 做了什么

- 恢复链（回收过期租约 → 隔离沙箱 → 回收沙箱 → 恢复中断的 Run）作为一组按原顺序执行，其余扫描和它
  同时执行。
- 每项扫描有超时 `SCHEDULER_SCAN_TIMEOUT_SECONDS`（默认 120 秒），超时的扫描被取消，像其他失败一样
  计数、写日志、进入 `ExceptionGroup`，带着扫描名。

## 测试过了

- 真 Postgres：两项各要 1 秒的扫描，一轮总耗时小于 1.8 秒（**改之前 2.14 秒，失败**）。
- 恢复链的四项按原顺序执行（这一条在原来的串行实现上也通过，是为了保证改成并发后顺序不变）。
- 一项挂住的扫描（超时设成 0.5 秒）：一轮在 3 秒内结束，另外两项被观察的扫描都执行了，失败是一个
  `TimeoutError`，备注里有扫描名（**改之前没有超时这个设置，失败**）。
- 原有的 scheduler 和 scheduler 沙箱回收测试全部通过。
- 全量（本地）：后端单元 2755 passed；集成 1340 passed、1 skipped。
- 这个版本的 scheduler 在本机栈上跑了一个约 1.4 小时的长任务压测（见 PR 描述），期间没有扫描失败。

## 这一遍没能证明什么

- 并发只在测试和一个单任务的长压测里跑过，没有在多任务、多扫描同时有活干的负载下观察过锁等待。
- 超时取消对卡在数据库锁上的扫描有效（事务回滚）；对卡在不响应取消的调用上的扫描，任务会留在后台。
  没有构造这种情况。

## 不声称什么

- 不声称 scheduler 已经可以多副本运行：每项扫描的锁是为多副本准备的，但多副本没有测过。
