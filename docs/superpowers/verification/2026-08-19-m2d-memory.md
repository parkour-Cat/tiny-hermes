## 1. Scope

This record covers all of M2D, planned in
`docs/superpowers/plans/2026-08-18-m2d-memory-and-search.md` against product
design §4.5, §4.6, §7.4.2, §14 and §16.3, and the M2 roadmap §7.

## 4. The six exit criteria

**1. A subject's private memory does not appear in another subject's session
with the same Agent.**

Decided in the domain and enforced by four columns, but asserted where it would
actually fail: in the bytes sent to the model.
`tests/integration/runs/test_memory_isolation.py` gives two subjects one Agent
and one memory each, and checks that the request built for one carries its own
line and not the other's. The query is not where this would go wrong — one
missing filter in the read path looks like nothing at all.

Underneath it, `MemoryScope` cannot be constructed without a subject and there
is no argument, default or combination meaning "every subject's memory".
`tests/unit/memory/test_scope.py` pins that as a `TypeError` and a `ValueError`
rather than as a convention.

**2. With the policy set to "everything awaits approval", nothing bypasses it.**

`tests/integration/runs/test_memory_write.py` runs an Agent that proposes a
memory, finds it `pending`, runs a second Run with the same Agent and subject
and confirms the model was not told, then approves it through the API and
confirms the third Run was. The rejected path is the same walk with the other
button, and `off` is asserted as **no row at all** rather than a refused one.

**3. A raw user message does not automatically become shared memory.**

Asserted as "there is no such path" rather than "the path is refused":
`SqlMemoryCandidates` writes only `kind=private`, and the integration suite runs
an Agent twice and counts zero shared rows in the workspace afterwards. §14.2's
two doors are an administrator's own edit and an approved proposal, and
`MemoryService.create_shared` is the only code that opens either.

**4. When the memory segment is over budget, low-relevance memories go first and
nothing incompressible is touched.**

`tests/unit/runs/test_memory_segment.py`. Memories arrive highest-relevance
first, so trimming from the tail *is* trimming low relevance; the segment is
capped once against its own ceiling and again by exactly the round's overage;
and a large memory makes a Run lose memories rather than reach
`paused(context_overflow)`, because every memory is subtracted from the floor
the way unhit skill summaries are. A separate test asserts that safety rules and
personality are never among the trimmed segments.

**5. Session search returns only sessions the requester may read.**

`tests/integration/runs/test_session_search.py`. Same workspace, same Agent,
two subjects: one of them says something and the other cannot find it, getting
"No past message matched" rather than a hit. The tool takes no scope argument at
all — the subject is read off the Run — so the guarantee is a property of the
adapter rather than of a caller narrowing correctly.

**6. After erasure, private memories, sessions, files and identity information
are no longer retrievable, and the erasure itself is audited.**

`tests/integration/runs/test_subject_erasure.py` counts memories, sessions and
messages by direct SQL before and after, confirms all three fall to zero,
confirms the subject's words are no longer findable by search, and confirms an
`subject.erased` audit record exists carrying the counts and **not** the text.
An already-erased subject exports empty rather than erroring.

## 5. What this run does not prove

**Two console walks could not run here, for the reason the M2C record gives.**
`console.spec.ts` binds `shell.exec`, and this stack has no
`SANDBOX_IMAGE_DIGEST`; both failures carry `failure_reason:
sandbox_not_configured` in their Run events. The `memory`, `skills` and `tools`
walks all passed. Nothing in M2D needs a sandbox, so this says nothing about the
stage either way — it is an environment gap, recorded so a reader does not read
"2 failed" as a regression.

**The Windows sandbox test failed, and it is still not this branch's.**
`test_engine_workspace.py::test_execute_feeds_stdin_and_the_helper_writes_
atomically` raises `TypeError: 'NpipeSocket' object does not support the context
manager protocol`. Same failure as the M2C record, same cause, same line from
2026-08-13, and this branch does not touch the file.

**"Identity information" is read narrowly.** The sixth criterion names identity
information; what erasure removes is the subject's memories, sessions, messages
and the artifacts those sessions produced. It does **not** delete the `users`
row — that is a platform account with memberships and audit history attached,
and removing it is an account-deletion procedure this phase did not design. For
a `caller_type=user` subject the two are the same person, so the gap is real and
is stated here rather than implied by the passing test.

**Runs survive erasure.** A Run row is the platform's record that work happened
and is referenced by budget and lease rows; the content it produced is deleted
and its session pointer goes with the session. That is a deliberate reading of
"会话、文件" and not an oversight, but a reviewer expecting zero rows anywhere
will find Run rows.

**The scenario picker in the Agent builder is no longer reliably clickable, and
this run worked around it rather than fixing it.** M2D added two scenarios and
two tools to lists the console renders; the scenario list is now long enough
that rc-select virtualizes it, and an option near the bottom cannot be clicked —
a wheel event recycles the element under the cursor, and keyboard selection did
not take either. The walk published `remember_once` through the API instead, and
says so in its own docstring. `AgentDetailPage.test.tsx` still covers the
builder's behaviour with a short list, so what is unproven is specifically that
a person can pick a scenario near the end of the list in a browser. It needs a
searchable select, and that is a console change this stage did not make.

**The browser walk covers one subject, not two.** `memory.spec.ts` proposes,
waits, approves, withdraws and erases — but the cross-subject half of the plan's
walk needs a second signed-in person, and the console has no user-creation path
in this phase. Isolation between subjects is proven at the integration level
(`test_memory_isolation.py`, `test_session_search.py`) and nowhere in a browser.

**No console pages were built.** M2D's routes exist and are exercised by the
API-level walk; there is no memory review page, no shared-memory editor and no
self-service screen. The plan did not ask for them and the roadmap puts the
governance queue in M3, but "an administrator can review a candidate" is
currently true through the API and not through a browser.

**The `low_risk_auto` rules are a heuristic and this run does not show them
holding against an adversarial candidate.** Every unit test in
`tests/unit/memory/test_risk.py` is a case somebody thought of. The default is
high risk, so an unthought-of case waits rather than passes — that is the
property being relied on, not coverage.

**Relevance was not measured, only ordered.** No test asserts that the most
useful memory is ranked first, because "useful" is not something `ts_rank`
answers. What is asserted is that the order the library produces is the order
the planner keeps, and that trimming takes the tail.

## 6. What this stage does not claim

**Memory is keyword-matched, never understood.** §14.3 excludes vector memory
and knowledge graphs, and nothing here infers meaning. A memory that does not
share words with the current request ranks low and may be trimmed, even if a
person would call it relevant. The field is named for what it does.

**A pending memory is not a memory.** It never reaches a model, and the platform
does not act on it. Until somebody approves it, the only thing that exists is a
record that an Agent suggested something.

**The subject is the caller, for now.** Private memory is keyed on M1's
`CallerIdentity`, so in this phase an "end user" is a signed-in platform user.
§4.5's separate end-user identity adds a third `CallerType` and does not change
this table's shape — that is the roadmap's one product assumption, carried here
deliberately and written down where the read happens.

**Erasure covers what this platform stores.** It does not reach content that has
already been sent to a model provider, and it makes no claim about their
retention.

**Shared memory has no proposal flow yet.** §14.2's second door — an approved
proposal — is served by the same `pending` queue an Agent's private candidate
uses, but nothing in M2D produces a shared candidate, so that door has been
built and never walked through.
