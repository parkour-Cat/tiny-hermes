## 2. §929 那个开放问题仍然开放

M1 笔记明确拒绝预设结论：官方文档描述的是**推送失败后**的重试，不是"断线期间漏掉的
事件会被重放"，而那次断线演练（停客户端 → 发 N 条 → 起客户端 → 数 `event_id`）
**没有做过**。§929 说：补投保证不了、企业又不接受丢事件，Webhook 在 M3 生产部署就是
**必需兜底**。

**这一遍没有改变这个状态。** 演练仍然需要真实租户。

但这一遍**为两种结论都做好了准备**：摄入路径与传输解耦，Webhook 那一侧完整可用。
如果演练最后显示会丢事件，补的是最外面那一层，不是动传输层。这是计划 §7 第一条决定
的实际收益。

## 3. 去重：为什么那条测试重写过一次

§574 要求按 `channel_binding_id + channel_event_id` 去重。飞书自称 at-least-once，
且重试是队列驱动的——**并发**。

**第一版测试是错的，而且是绿的。** 它用 `asyncio.gather` 跑两次投递、断言只有一个
认领，四条全过；然后我把实现换成"先查后写"，**它还是全过**。`gather` 只调度协程，
不保证它们的数据库往返重叠，那两次被串行化了。

一条对着错误实现也能过的测试不是证据。改成**构造**那个交错：第一次投递认领后
**挂住事务不提交**，第二次在这期间整个跑完——READ COMMITTED 下它看不见那一行，正是
`SELECT` 会误读成"没人认领过"的状态；它的 `INSERT` 卡在唯一索引上直到第一个提交。

现在：对"先查后写"是 **IntegrityError 红**，对 `ON CONFLICT DO NOTHING RETURNING`
是绿。

**认领发生在 Run 存在之前**，`run_id` 可空正是因为这个：先建 Run 再认领，那个 Run
就是这张表要防的重复。

## 4. Webhook：三个不能凭记忆写的地方

**密码学是查官方文档写的。** M1 笔记一个字都没记这部分。AES-256-CBC、密钥
`SHA256(encrypt_key)`、IV 是 base64 解码后前 16 字节、PKCS7；签名是
`SHA256(timestamp + nonce + encrypt_key + 原始body)`。写错就是洞，不是 bug。

**顺序是设计。** 验签必须在解密和解析之前：先解密等于拿平台的密码学跑攻击者的输入；
先解析等于让攻击者挑一个 `event_id`、**抢先认领、把真实投递压掉**。测试断言的是
"没有发生认领"，这才让顺序可见。

**`url_verification` 必须答。** 飞书不保存握手失败的回调地址——只处理事件的端点是个
**没人能启用**的端点。

**没有时间窗防重放，这是决定不是遗漏**：body 在签名里，重放的请求逐字节相同 → 同一个
`event_id` → §574 的认领已经精确拒了它。

## 5. 跨路径的那个洞：抹除

**抹除守卫住在服务层（`EndUserIdentityService.exchange`），不在
`upsert_external_identity` 里。** 所以飞书这条路必须自己再检查一次——否则**飞书就是
绕过 §344 抹除的门**：同一个人换扇门走进来就复活了。

一条测试钉住，并且断言**既没有 Run 也没有 Session**——先建了 Session 就已经把主体
重新挂上了。

## 6. 两个计划没做、这一遍替产品做的建模决定

**一、会话按参与者存，不按飞书的 `chat_id`。** 主体是人，§282 已经把
`(workspace, channel, external_user_id)` 定为身份；用 `chat_id` 会让同一个人在群聊和
私聊里有两个线程，那是没人做过的产品决定。

**二、`channel_conversations` 单独一张表，不塞进 `channel_events`。** 生命周期是
**故意**不同的：§574 七天扫掉投递记录，会话必须活得更久，否则安静两周等于把人重新
开始。

## 7. §497：我在计划里写反了一句

计划 §5 我写的是"没有偷偷建一个 pending Run"。**§497 的原文是"可以保存新的 pending
Run，但必须立即返回 `session_blocked`……不得静默排队"——排队是允许的，静默才是禁的。**

所以 `Delivered` 同时带 Run 和通知，不是二选一：联合类型会让传输层处理了 Run 而忘掉
通知，那正是这条规则要防的沉默。

聊天界面上这条比别处更严：控制台用户能去看队列，聊天用户不能，所以**一条只是被排队的
消息，看起来和一条丢失的消息一模一样**，人会再发一遍。

- **断线补投演练没做**（见 §2）。在它做出来之前，**"WS 就够了"和"Webhook 是必需的"
  都不是结论**——这是 M1 笔记的原话，M3 没有权力把它悄悄变成前者。
- **飞书卡片的 JSON schema 没有核实过**，所以没写渲染。文档页是 JS 渲染的，取不到。
- **附件没做。** §19.2 首版列了"基本附件"，这一遍只做了文本。
- **`ChannelBinding` 没有管理接口。** 表和约束建好了，创建/停用绑定的路由没有写，
  所以今天只能靠直接写库来配置一个绑定。

## 10. 补记：HTTP 路由（同日）

§8 原本记着「`FeishuWebhookService` 可调用、被测过，但没有人从网络那一侧打进来过」。
这正是本仓库已经犯过五次、并且在自己的验收记录里点过名的那个形状，所以它当天就补上了：
`POST /api/v1/channels/feishu/{binding_id}/webhook`。

**它不在 `_CONSOLE_ONLY` 下面**，这是对的而不是遗漏：那个守卫拦的是带终端用户 cookie
的请求，而飞书**不带任何 cookie**——它手里没有这个平台的任何凭据。所以这扇门是公开的，
**body 上的签名是它和整个互联网之间唯一的东西**。这也正是 0037 那条 CHECK 的意义：
一个没有 `encrypt_key_ref` 的飞书绑定会把这条路由变成一扇敞开的门。

五条集成测试**从 HTTP 打进来**，覆盖单元测试在结构上看不到的部分：

- 一条签名消息变成一个 Run，**归属从数据库断言**（`sessions.caller_type='end_user'`
  且 `caller_id` 等于 `external_identities` 映射出的那个人，§122）。响应可以说任何话，
  要紧的是平台认为这份工作属于谁。
- **握手也走 HTTP 验了**：飞书不保存握手失败的回调地址，不答这一下后面全都不可达，
  而任何单元测试都看不出这一点。
- 伪造签名被拒，**并断言什么都没启动**——一个已经开工的 401 是名义上的 401。
- 同一条投递两次只起一个 Run，**两次都是 200**：第二次返回别的会让飞书重试六小时。
- 未知绑定与坏签名**返回一模一样的 401**：区分开来会让任何拿到 URL 的人枚举出哪些绑定
  存在、哪些被停用。

**仍然没做的没有变**：真正的 WebSocket 传输、`lark-oapi` 依赖、飞书卡片 JSON 渲染、
断线补投演练——四样都需要真实租户，理由见 §1 与 §2。

数字更新为：unit 2004、integration 667。
