## 1. 这份审计的方法，以及它的边界

**必须先说清楚方法，否则这份记录会被当成比它更强的东西。**

§23 列了 15 条可证伪断言。我**逐条读代码验证的只有第 8 条**，因为关键词扫描先把它标成
了「零覆盖」。其余 14 条我做的是关键词扫描，确认每一条都有名字对得上的测试文件。

**关键词命中不是覆盖的证据。** 这个项目已经栽过一次：§27.2 场景 6 曾经被记成绿的，
而它的 `USER_CONFIRMATION` 根本没有生产者。所以这份记录只声称：

- 第 8 条：**读过代码，找到并补上了一个真实缺口**（见 §2）。
- 其余 14 条：**有名字对得上的测试，没有逐条读过**。

要把这 14 条也变成结论，需要一条一条读，那是一次独立的工作。

**过程中我自己也犯了两次错，都写在这里，因为它们说明这个方法有多脆：**

- 第一次扫描时我把 `\|` 写进了 `grep -E`，在 ERE 里那是字面竖线，于是 13 条全报「零
  覆盖」。我知道 egress 有 29 个测试文件，才没有把这个结果写下去。
- 我 grep `is_still_valid` 时加了 `head -6`，把生产代码里唯一的调用点截掉了，据此
  一度得出「只有测试在调用它」的结论。是重新完整跑一遍才纠正的。

## 2. 第 8 条：行为在，名字不在，执行层没测

断言原文：「审批后的工具名、参数、工作目录、目标资源或权限任一发生变化时，执行层
返回 `approval_mismatch`。」

查出来三件事：

**一、行为存在且可达。** `is_still_valid`（`runs/domain/approval.py:179`）比较
`content_hash`，由 `SqlApprovalGate.check`（`runs/infrastructure/sql_approvals.py:69`）
在执行路径上调用。那里的注释写得很清楚：「§16.3 的失效规则完全在哈希比较里：改任何一个
参数，它就不再匹配。」

**二、`approval_mismatch` 这个错误码在代码里不存在。** 实现的做法不是返回一个错误，
而是**再问一次**——改过的调用找不到覆盖它的审批，于是 Run 第二次为一个人停下。

安全性质是同一个，形状不同。**我没有为了让字符串对上规格而发明一个错误码**：记录
哪一个是真的，比让文档和代码看起来一致更重要。

**三、执行层原本没有测试。** 单元层有
（`test_an_approval_for_a_different_call_covers_nothing`），证明的是一个函数返回
`False`；执行层要证明的是**守着写操作的那个存储真的拿手上这个调用去问那个函数**，
而不是拿 Run 去问。这是两个不同的断言。

已补 `test_an_approval_does_not_carry_over_to_a_call_with_different_arguments`：
真跑一个 Run 到 `waiting_approval`、真批准、然后拿一个改了参数的调用去问同一个 Run。

**并且验证过它不是空过的**：把参数改回一致，它变红。

## 4. 许可证清单

`scripts/license_inventory.py` 生成，读的是**已安装**的依赖而不是 `pyproject.toml`
声明的——两者相差的正是传递依赖，而意外通常出在传递依赖上。

56 个第三方依赖，全部宽松许可。**一个 MPL-2.0（`certifi`）被单独点名**：它不阻塞
发布，列出来是因为「全都是宽松许可」这句话会有人说出口，而它应该被知情地说。

生成而非手写，理由是手写的清单在写下那天是对的，下一次 `uv sync` 之后就不是了。
提交生成结果之后，`THIRD_PARTY_LICENSES.md` 的 diff 就成了一次评审提示。

  由仓库所有者指定。写的是公开使用的名字而不是法律全名——**这是一个知情的选择，
  不是一个疏漏**：版权本来就归作者，这份通知只是标识他，但真名在主张权利时更硬。
  换成全名是一行的事，记在这里是为了那天有人知道该改哪儿。
- **没有做法律审查。** §28 最后一句要求发布前由合格的人审阅许可证结论，这一遍没有，
  也不可能由这一遍完成。
- **§28 的 FastClaw 与 Hermes Agent 条款：已核对（2026-08-23），结论是不适用。**

  §28 要求两件事——不复制 FastClaw 受附加条款约束的源码；复用 Hermes Agent 的 MIT
  代码要保留原始版权与许可证声明，并记录复用文件清单。

  仓库里的证据：

  - 提到这两个项目的**只有一份研究文档**（`docs/research/2026-08-09-fastclaw-hermes-analysis.md`），
    而它自己的结论第 4 条就是「若目标是一个无此类附加限制的开源项目，应**独立实现，
    只借鉴思想**」，第 5 条给的组合方案也是独立控制面 + 精简内核，不是搬运。
  - **全仓库没有任何外部版权声明**（`git grep "Copyright (c)"` 只命中生成的第三方清单）。
    复用了别人的 MIT 代码却一条声明都没留，是不可能的；一条都没有，最合理的解释是
    没有复用。
  - 第一个提交是 `docs: establish tiny-hermes design baseline`，**不是一次 fork**，
    也没有把别人的代码作为起点。

  **这个结论建立在仓库自身的记录上，不是逐行比对上。** 我没有把两个上游仓库拉下来
  做相似度对比——那是另一种工作，需要的证据也不同。如果将来有人主张此事，逐行比对
  才是回答它的东西。
