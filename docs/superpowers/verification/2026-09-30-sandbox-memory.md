# 沙箱内存：每个沙箱常驻多少就占多少，而总和没有任何上限

日期 2026-09-30。分支 `feat/capacity-acceptance`，未推送。栈用 `f323fe7` 重建；探针的
`889ab8d` 是测完之后才改的，只影响它怎么报告。

## 为什么有这一遍

[单机档验收](2026-09-30-tier-a-acceptance.md) 的工具只是 `printf`，沙箱几乎不占内存，
所以「内存低于 70%」那一条的「过」不能外推。这一遍让沙箱真的占内存，看会怎样。

## 怎么测

- `long_task` 场景加了 `cache=M`：每个沙箱第一次执行时，往 `/workspace/cache` 写 M MiB
  随机数据，之后一直留着。
  - `/workspace/cache` 是 tmpfs（默认 512 MiB）。容器策略里写明它是放重建依赖的地方，
    它的页算在沙箱的内存上限里。
  - 所以这些数据就是沙箱在两轮之间、以及冻结期间一直占着的内存。
  - 用随机数据，是因为这台 VM 的 swap 是 zram，全零的数据会被压缩到几乎不占内存。
- 探针用 `--cache-mb M` 传这个值。
- 负载：和单机档验收第 2 档一样。2 × 16 条通道，24 个长任务（每个 60 轮），再加每秒 3 条
  短消息，持续 150 秒。模型延迟 2 秒。
- 采样：
  - 探针本身；
  - 每 2 秒对所有容器跑一次 `docker stats`，沙箱按标签识别；
  - VM 的 `/proc/meminfo`：`MemAvailable`、swap、`Shmem`。
- 冒烟：先用 2 个长任务、每个 64 MiB 试了一次。最大的沙箱是 68 MiB，两个任务都完成了。
  这说明这条命令在真实的沙箱里（只读根文件系统、无网络、非 root）能执行，而且这部分内存
  确实算在沙箱头上。

## 结果

|---|---:|---:|---:|
| 完成 / 失败 | 474 / 0 | 474 / 0 | 474 / 0 |
| 短消息排队 P95 / 最大（秒） | 0.02 / 0.08 | 0.02 / 0.06 | 0.05 / 1.19 |
| 长任务端到端 P95（秒） | 175 | 174 | 185 |
| 同一时刻的沙箱最多 | 24 | 24 | 24 |
| 最大的单个沙箱 | — | 54 MiB | 105 MiB |
| 所有沙箱合计 | 约 0 | 1212 MiB | 2414 MiB |
| 容器合计（占 VM 8005 MiB 的比例） | 1642 MiB（21%）¹ | 2828 MiB（35%） | 4102 MiB（51%） |
| VM 实际占用峰值（1 − MemAvailable / MemTotal） | 没测 | 48% | 65% |
| 期间 swap 增加 | 没测 | 0 | 7 MiB |

| Postgres CPU P90（%） | 87 | 117 | 124 |

¹ 那一遍的采样器把一个测试用的 Postgres（约 38 MiB）也算了进去。

栈空闲时 VM 占用是 24%，这是 50 MiB 那一轮开始前的采样。

## 读法

1. **沙箱常驻多少，主机就少多少，比例是一比一。** 每个沙箱多放 50 MiB，24 个沙箱合计就多
   1.2 GiB，VM 占用多 17 个百分点。冻结的沙箱也照样占着。
2. **同一时刻的沙箱数，等于正在推进、并且用过工具的 Run 数。**
   - 只有时间片到期会冻结并保留沙箱；结束、暂停、等待都会把它销毁，所以一个 Run 最多一个沙箱。
   - 冻结的沙箱最多保留 `SANDBOX_IDLE_TTL_SECONDS`（300 秒）。
   - 另外要注意：每轮提交工作区时都会短暂冻结沙箱。所以探针报的「paused」峰值大多是提交时的
     冻结，不只是时间片之间的冻结。
3. **这台 VM 留给沙箱的预算约 2.9 GiB（推算）。**
   - 栈空闲时 VM 占用 24%。负载本身（不算沙箱）再加约 10 个百分点：两轮里，VM 占用减去沙箱
     合计后，都剩下约 9–11 个百分点。
   - 要守住 70%，留给所有沙箱的约是 70% − 24% − 10% = 36%，约 2.9 GiB。
   - 按这个预算：24 个沙箱每个 120 MiB，32 个每个 90 MiB，或 60 个每个 48 MiB。
4. **在 65% 时平台照常工作**：没有失败，短消息不受影响，swap 几乎没动。

## 发现

### 沙箱内存的总和没有任何上限

- 每个沙箱的上限是 1 GiB（`DEFAULT_PROFILE`），其中 tmpfs 最多 768 MiB（`/tmp` 256 +
  `/workspace/cache` 512）。
- 没有设 `memswap_limit`。按 Docker 的默认规则（只设内存上限时，swap 可以再用同样多），每个沙箱还能再用 1 GiB swap。
- controller 不限制沙箱的个数，也不看主机还剩多少内存。我在 `sandbox` 包里查过，没有这类检查。
- 沙箱的个数只受「正在推进、用过工具的 Run 数」限制。
- 所以在这台 VM 上：32 条通道全部用上、每个沙箱都用到上限时，需要 32 GiB；而 70% 线只给沙箱
  留了约 2.9 GiB。**只要有 3 个沙箱用到它们各自的上限，就会超过这条线。**
- 超过物理内存之后会发生什么，这一遍没有测，见下。

### 沙箱销毁后，内存还会滞留十几秒

- 24 个沙箱一起销毁后，它们的容器已经从 `docker ps -a` 里消失，但内存又停留了约 15 秒才
  一次性释放。复现了两次（50 MiB 那一轮结束时；又专门跑了一次 24 个任务）。
- 纯 Docker 一次删 24 个带 50 MiB tmpfs 的容器，约 1 秒就释放了。加上 `--init`、只读根
  文件系统，再暂停、恢复过一次后，约 4 秒。
- 8 个任务、1 个 Worker 容器那次，在 6 秒一次的采样精度内没有看到滞留。
- 原因没有查清。它对容量的影响可以推算：频繁建、删沙箱时（比如每条都用工具的短消息），
  额外占用约等于「每秒销毁的沙箱数 × 滞留秒数 × 每个沙箱的占用」。这一点没有测。

### Postgres 日志里有一行 ERROR

50 MiB 那一轮有一行 `canceling statement due to user request`：一条 `SELECT … FROM runs …
FOR UPDATE` 在等行锁时被客户端取消了，时间是开始后约 35 秒，也就是第一批时间片到期的时候。
- 最可能的解释：时间片结束时 Worker 会取消续期任务（`worker.py` 里的
  `finally: renewal.cancel()`），而续期先锁 `runs` 行，当时正在排队等这把锁。
- 这只是解释，没有证实：日志里看不出发起取消的连接是谁。
- 那一轮 474 个 Run 全部完成。单机档验收的 4 轮、100 MiB 那一轮和几次冒烟里都没有再出现。

## 这一遍没能证明什么

- **没有测超过物理内存的情况**：swap 用满以后会怎样，OOM killer 杀的是谁。
- 常驻内存用的是 tmpfs 里的文件，不是进程内存。两者在 OOM 时的表现不同：进程内存可以靠杀掉
  那个进程释放，tmpfs 里的页不属于任何进程，杀进程释放不了。
- 命令运行期间的临时内存没有测：每个沙箱只写一次，之后每轮都只跑 `printf`。
- 真实的 Agent 会在沙箱里常驻多少，这一遍给不出，要看它做什么。这一遍只证明了「常驻多少就
  占多少」，以及总和没有上限。
- 空闲时 24% 和负载本身约 10% 这两个数，只在这台 OrbStack VM 上测过。
- 销毁后内存滞留的原因没有查清，也只在 OrbStack 上观察过。
- 每档只跑了一次，每次 150 秒。

## 不声称什么

- 不声称任何「每个沙箱多少 MiB」是真实 Agent 的值。
- 不声称内存耗尽时 OOM killer 会杀某个具体的服务。一个说得通的猜测是：它会去杀最大的进程，
  这台机器上是 seaweedfs（约 640 MiB），因为 tmpfs 里的页不属于任何进程。但这没有测过。
- 不声称销毁后的内存滞留在 Linux 主机上也存在。

测完之后，栈已经恢复成 1 个 Worker、`WORKER_CONCURRENCY=1`、模型延迟 50 ms、调用上限 20，
没有遗留的沙箱或测试容器，`Shmem` 回到了 124 MiB。库里留下了 `probe-*` 工作区的测试数据。
