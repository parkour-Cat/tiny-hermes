| 改了什么 | 测试 | 实现 |
|---|---|---|
| 31 张表开 RLS；应用改用不能绕过它的角色；请求确定工作空间后，事务带上它 | `21da743` | `f7d679b`、`959f58f` |

## 为什么有这一遍

工作空间隔离全靠代码里的 `WHERE workspace_id = ...`。哪一处漏写，一个租户就能读到另一个的
数据，而这种 bug 测试未必覆盖得到。

## 怎么做的

- **角色**：迁移创建 `tiny_hermes_app`：不是超级用户、没有 BYPASSRLS、不拥有表。这三种身份
  RLS 都管不住，而 Compose 用的登录 `tiny_hermes` 三样全占。应用的每个连接打开后
  `SET ROLE tiny_hermes_app`。
- **策略**：31 张带 `workspace_id` 的表，每张一条 `workspace_isolation`，读写都按它判断：
  - 事务里有 `app.workspace_id` 时，只看得到、只写得进这个工作空间的行。
  - 5 张 `workspace_id` 可以为空的表（平台审计、平台密钥、平台技能、技能提议、平台出站范围），
    平台级的行也看得到：它们不属于任何别的租户。
  - 没有这个设置时不限制。
- **谁带上工作空间**：
  - `require_workspace_id`：控制台 81 处由请求头选工作空间的地方都经过它。
  - API Key 的两个解析点。
  - 终端用户会话的解析点。
  - 之后每个事务开始时（SQLAlchemy 的 `after_begin`），用 `set_config(..., true)` 写进
    事务级设置。值放在 context variable 里，随请求结束。

## 测试过了

- 后端单元测试 2682 passed；集成测试（含 sandbox 目录）**1253 passed、1 skipped**，**全部以
  `tiny_hermes_app` 运行**；pyright 0 errors；`ruff check` 通过；新迁移 `alembic check` 无差异，
  降级再升级通过。
- 新测试：
  - 每张带 `workspace_id` 的表都开了 RLS 并有策略。表的清单从模型元数据里取，以后新加的表
    没写策略，这条测试会失败；
  - 应用角色不是超级用户、没有 BYPASSRLS、不拥有表；
  - 应用连接的 `current_user` 是它；
  - 在工作空间 A 里，**不带任何条件**的 `SELECT` 只返回 A 的行；不在任何工作空间里时看得到
    全部；
  - 在 A 里写 B 的行，被数据库以 row-level security 拒绝；
  - 平台级的审计行在 A 里看得到；
  - **一个真实的 API 请求**：把 Agent 列表查询的 `WHERE workspace_id` 去掉，用 A 的身份请求，
    返回的仍然只有 A 的 Agent；
  - 同一个连接先在 A 里用过，下一个不受限的事务照常工作。

### 第一次全量跑红了 120 条

策略原来写的是 `设置为空 OR workspace_id = 设置::uuid`。事务级设置结束后，连接上留下的是空字
符串，而 Postgres 不保证 `OR` 从左往右算，会把 `''::uuid` 当常量先折叠，于是报 `invalid input
syntax for type uuid`。改成 `nullif(设置, '')::uuid` 之后全绿。

我写的 RLS 测试没有抓到这个问题：每条测试都用新连接，碰不上「同一个连接先被限过」这种情况。
抓到它的是**全量测试改用新角色跑**这件事本身。补的那条回归测试写在修复之后，没有先看它变红。

## 走通了什么

本机的 Compose 栈重建到这个分支，`migrate` 跑到 `20261023_0075`，31 张表开了 RLS：

- api、worker、scheduler、controller、egress-proxy 五个进程各自连上数据库，`current_user`
  都是 `tiny_hermes_app`。
- 压测脚本跑 17 个 Run，其中 2 个是带工具的长任务（会建沙箱、提交工作区），17 个全部完成，
  没有失败。

## 这一遍没能证明什么

- **不受限的路径比受限的多。**
  - Worker、Scheduler、controller、出站代理、登录、平台管理都不受限。
  - 用路径参数而不是请求头指定工作空间的接口也不受限，比如 `/workspaces/{id}/members`。
  - 这些地方漏了 `WHERE` 仍然会串租户。
- **在请求确定工作空间之前就已经开始的事务，到它结束都不受限。**同一个请求里，用来做鉴权的
  那个会话就属于这种情况。没有逐个路由核对哪些查询落在这样的事务里。
- **挡不住 SQL 注入。**能执行任意 SQL 的人可以 `set_config` 改设置，或者 `RESET ROLE` 回到
  超级用户。后者在生产环境用独立登录角色可以消除（运维手册 §14），Compose 没有这样做。
- 没有测性能。每行多一次 `current_setting` 和比较，带 `workspace_id` 的索引还在，没有用
  `EXPLAIN` 核对过计划是否变化。
- 终端用户、API Key 两类请求只靠现有测试全绿来证明没被弄坏，没有专门写「漏了 WHERE」的
  测试。

## 不声称什么

- 不声称工作空间隔离现在由数据库保证。它是代码出错时的第二道防线，只覆盖上面说的那部分事务。
- 不声称 RLS 让 SQL 注入变得无害。
