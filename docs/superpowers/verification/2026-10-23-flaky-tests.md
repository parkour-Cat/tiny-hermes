## 为什么有这一遍

PR #126 到 #132 的 CI 和本地全量里，下面四条各红过一次，重跑都通过：

| 测试 | 在哪红的 | 改动和它有关吗 |
|---|---|---|
| web `SkillsPage.test.tsx` 上传目录的两条 | #131 的一次 CI | 无关：#131 没改前端 |
| `test_event_push.py::test_an_announced_event_reaches_a_subscriber_at_once` | #126 的一次 CI；main 上 #125 合并前也红过 | 无关 |
| `sandbox/test_controller.py` 超时命令的两条 | #128 本地全量 | 无关：直接调 controller，不经过改动的传输层 |
| `test_waiting_run.py::test_a_terminal_run_behind_it_is_not_waiting` | #131 本地全量，出错阶段是 setup 或 teardown | 未知 |

它们每次红都要有人去判断「是不是真的坏了」，而这个判断很难从输出里验证。原因都和计时有关。

## 改了什么

- **SkillsPage 的两条**：
  - antd 的弹窗和提示是从透明度 0 淡入的，`toBeVisible` 会读透明度；
  - 第一次检查落在动画中间就会失败。在今天这台负载很高的开发机上，main 的版本 2 条都是每次必红；
  - 改成 `waitFor` 等到可见再判断，连跑 5 次都是 7/7，全量前端连跑两次都是 395/395；
  - 同样写法的 `toBeVisible` 在别的测试文件里还有，没见它们红过，这一遍没改。
- **test_event_push**：
  - 原来固定等 1 秒就认定订阅已经建好，再要求 1 秒内收到；
  - 改成先问 Redis 这个频道有没有订阅者，再在「兜底读之前」的窗口里等。兜底读在房间打开 5 秒
    后，窗口是 4.5 秒减去已经过去的时间；
  - 在这个窗口里收到，仍然证明是推送送到的，不是轮询；
  - 订阅数是整个频道的。CI 上这个 Redis 只给测试用，本机如果同时跑着 Compose 栈，它的 API 也
    会被算进去，那时这一步检查证明得更少。注释里写了。
- **controller 超时那两条**：
  - 原来是固定等 1 秒后检查一次进程还在不在；
  - 改成每 0.25 秒查一次，直到进程消失，最多 10 秒；
  - 真的停不掉时仍然会失败。
- **test_waiting_run**：**没有改。**
  - 只在本地出现过一次，CI 上没有；
  - 当时的输出只留下了测试名，没有留下错误内容；
  - 之后连跑 10 次都是 9/9 通过；
  - 不知道原因就不改。以后本地全量用 `-rfE`，让错误内容留在汇总里。
