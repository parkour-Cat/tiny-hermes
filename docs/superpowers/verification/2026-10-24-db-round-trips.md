# 减少数据库来回：三处确定的浪费

日期 2026-10-24。分支 `perf/db-round-trips`。[设计](../specs/2026-10-24-db-round-trips-design.md)。

## 做了什么

| 改动 | 内容 |
|---|---|
| scheduler | 4 项整理类扫描（删过期记录、清上传垃圾、过期产物、取消 24 小时兼容超时）改成每 `SCHEDULER_HOUSEKEEPING_SECONDS`（默认 60，最大 180）秒一次；进程启动后第一轮照常做 |
| 告警 | `SchedulerScanStalled`（超过 60 秒没成功）不再管这 4 项；新增 `SchedulerHousekeepingStalled`，它们 4 分钟没成功才告警 |
| controller | 一次调用只读一次 reservation 和实例，「是不是本机的沙箱」和「是不是这个 Run 的」都用这一次读到的结果 |
| worker | 已发布的 Agent 版本按编号缓存在进程里（上限 1024，最久未用的先淘汰），连同解析好的 spec 和所属 Agent |

**改的时候发现的一个问题**：原来的「扫描停滞」告警是任何扫描超过 60 秒没成功就告警。整理类扫描改成
每分钟一次后，它们在两次执行之间就会超过 60 秒，**上线后会不停地误报**。所以把这 4 项单独拿出来，
另设一条 4 分钟的规则；整理类扫描的名单在代码里只写一次（`HOUSEKEEPING_SCANS`），有测试检查告警
文件和它一致。

## 测试过了

- scheduler（真 Postgres，注入时钟）：连续两轮里 4 项整理只执行一次，恢复、审批过期两轮都执行；时钟
  走过 61 秒后整理再执行一次。
- controller（单元测试）：freeze、扫描工作区、thaw 各只读一次实例。**改之前 freeze 读 2 次。**
- worker（真 Postgres）：同一个 Run 连续读两次上下文，第二次不查 `agent_versions`。**改之前第二次查了
  2 次。**
- 告警：每个整理类扫描都被排除在 60 秒规则之外，并且有自己的规则，阈值不小于 3 分钟。
- 原有的「别的主机名下的沙箱拒绝」集成测试（真 Docker）全部通过，说明合并读取没有丢掉这项检查。
- 先写测试、看它失败、再实现。告警的测试是改完 scheduler 之后、发现告警问题时补的，单独提交，也先
  看到了失败。
- 全量（本地）：后端单元 2754 passed；集成 1335 passed、1 skipped。

### 改动前后（本机 Compose，确定性模型，一个 11 轮的长任务）

| | 改之前 | 改之后 |
|---|---:|---:|
| 一个任务里 `sandbox_instances` 的读取 | 124 | **73** |
| 一个任务里 `agent_versions` 的读取 | 52 | **3** |
| scheduler 空闲时每秒的语句数（只算 scheduler 进程） | 52.3 | **38.1** |
| scheduler 空闲时每秒的事务数 | 16.2 | **11.9** |

前两行数的是具体的那条语句，不受别的东西影响。后两行来自逐条语句日志里 scheduler 所在容器的地址，
只算它一个进程。

**一个任务的语句总数没有测出可信的下降。**改之后测了三次，分别是 2254、2008、2177（扣掉空闲时的
背景之后），改之前测了一次是 2202。按上面两行，预计少 100 条左右，这比三次之间的波动（约 250）还小。
空闲时所有进程合计的语句数也一样：改之后三次分别是每分钟 5046、5691、6144，波动比改动大。

## 这一遍没能证明什么

- 一个任务的总语句数是否下降，在这种测法下分辨不出来，原因见上。
- 只测了确定性模型的短任务（每轮一条 `printf`），真实工具、真实模型下每轮的读写比例不同。
- 版本缓存是进程内的。已发布版本按约定不会改，如果有人绕过 API 直接改了数据库里的版本行，worker
  在重启之前会继续用旧的。没有为这种情况做失效机制。
- 每个事务前的连接池探测（`BEGIN; ROLLBACK;`）和每轮第二次读上下文都没有改，理由见设计。

## 不声称什么

- 不声称数据库的瓶颈被推后了多少。这次没有重跑高并发的压测。
