# 管理员视图 — 验收记录 2026-08-22

> 计划：`docs/superpowers/plans/2026-08-22-admin-visibility.md`（§27.3 第 4 条）。
> 产品：v2.5 §4.6 审计记录一行、§190、§422 第 8 条。

## 1. 这一条的真实缺口

路线图那句话列了五样东西，但其中四样**数据都在、界面也基本都在**：Approvals 有页面，
任务树在 Run 详情里（M2E 的 `children.spec.ts` 已经走过），用量在 Run 详情里连
`cost_quality` 一起显示，失败原因一直在 `RunResponse` 上。

真正一条读路径都没有的是**审计**：`audit/` 模块只有 `tables.py`。每一层都在写
`audit_events`，**没有任何代码读它**。

这是这个项目反复出现的同一个形状——上一阶段的 `user_confirmation` 消费者、返回空文件的
导出按钮、没有调用方的 `forgetAllSessionIds`，这一阶段的 `failure_reason`。
**写进去了不等于有人够得着。**

## 2. §4.6 那一行是五格，不是一个开关

| 主体 | 范围 | 落地 |
|---|---|---|
| 平台管理员 | 跨空间只读**并留痕** | `AuditScope.full` + 一条 `audit.cross_workspace_read` |
| 工作空间管理员 | 本空间只读 | `AuditScope.full`，不留痕 |
| 开发者 | **与自己资源相关的**只读 | `AuditScope.own_resources` |
| 查看者 | **脱敏**只读 | `AuditScope.redacted` |
| 终端用户 | 否 | `_CONSOLE_ONLY`，403 |

**五格里有三格是「部分可见」。** 把它做成布尔是这一条最容易犯的错，其次是「对所有人
脱敏」——那会让工作空间管理员查不了事故，而事故正是审计存在的理由。

`AuditScope` **表达不出「所有工作空间的全部记录」**。不是禁止，是写不出来，沿用
`MemoryScope`（M2D）的做法与理由：能被构造出来的最宽范围，就是有人终将拿到的范围。
平台管理员的跨空间能力是应用层一次问一个工作空间，不是一个更宽的 scope。

## 3. 脱敏：白名单，且默认是空的

作用在 `context` 上——其余列都是标识符或固定词表。**只对查看者**。

白名单默认**空集**，这是决定不是占位：今天代码里 `append_audit` 传过的键
（`reason`、`channel`、`url`、`entry`、`prefix`……）没有一个被它们的调用方审查并声明
「给脱敏读者看是安全的」。猜哪些「大概只是元数据」正是会变成下个季度泄漏的那条捷径。

黑名单的失败方式是静默的：下一个往 `context` 里塞键的人没有理由想起这个文件，而那一天
不会有任何测试变红。白名单的失败方式是显式的：没登记的键根本不出现。

## 4. 一个计划没写、但做的时候才看见的缺口

**响应里原本没有任何东西告诉客户端「你看到的是脱敏的」。** 两个 page 模型都是
`{items, has_more}`，而脱敏后的 `context` 是 `{}`——这和一行本来就没有 `context`
**是同样的字节**。

这两者的含义相反：「这里什么都没记」与「这里记了但不给你看」。而会被误导的恰恰是
正在查事故的人，他有充分理由把短列表和空细节读成「没发生过」。所以 `visibility`
上了线，两种 page 都带，控制台据此显示横幅。

一条测试钉住**完整视图不显示这个横幅**——否则横幅会变成墙纸，不再承载信息。

## 5. 出口检查对证据

- 五种主体五种结果：`tests/unit/audit/test_service.py` + `tests/integration/audit/`。
- `AuditScope` 写不出「全部」：构造器本身没有这个入口，单元测试覆盖三种可构造的范围。
- 未登记的 `context` 键查看者读不到：`test_viewer_context_is_stripped_of_every_unregistered_key`，
  断言的是**整个响应体里搜不到那个字符串**，不只是键不在。
- 跨空间读留痕、本空间读不留痕：两条测试，两个方向。
- 脱敏视图会承认自己是脱敏的：`test_a_redacted_page_says_so_rather_than_looking_like_a_full_one`
  + 三条控制台测试。
- 失败原因出现在列表里：`test(web)` 两条，含「没失败的行不显示原因」那一半。

## 6. 这一遍没能证明什么

- **e2e 只证明了「读到的是真写的」，没证明五种主体在浏览器里各看到什么。**
  `tests/e2e/audit.spec.ts` 里管理员建一个 Agent、打开审计页、看见**那一个 Agent 的
  id**——不是「表格非空」，那种断言对着别人的历史也会过。但走查只有管理员这一种身份；
  查看者与开发者的可见范围是后端与组件测试证明的，**没有人在浏览器里以那两种身份走过**。
- **保留期与清理没有做，也没有计划。** 审计只增不删。这个部署跑得够久，
  `audit_events` 就会成为问题——不是正确性问题，是运维问题，而现在没有任何东西在管它。
- **开发者的「与自己资源相关的」是一个折中**：判据是 `actor_id` 是他，或者
  `resource_id` 出现在某条他是操作者的记录上。因为**没有任何资源表有 owner 列**，
  这是 `audit_events` 自己支持得起的唯一归属事实。它会漏掉「他的资源、但别人操作」
  的记录。这是已知的、写进 docstring 的取舍，不是遗漏。
- **跨空间读的留痕没有压过量。** 一次调用一行，翻页也是一行——如果有人写脚本翻一千页，
  就是一千行。没有限流。

**为什么值得单开一条 e2e：** 下面每一条测试要么直接往 `audit_events` 里塞行，要么
孤立地测读路径。**写路径和读路径如果漂移到了不同的 action、不同的 resource_type 或
不同的工作空间上，它们全都还是绿的。** 这条走查什么都不塞，所以它是唯一能说
「管理员读到的审计就是平台真正写下的那条」的地方。

## 7. 这一阶段不声称什么

- 不声称 §27.3 第 4 条**全部**完成——见下一节。
- 不声称审计能回答「谁读了谁的对话」以外的取证问题。它是一条动作流水，不是关联分析。
- 不声称脱敏白名单是「配好的」。它是空的，这是有意的起点，不是配置完成的状态。
- **不声称用量页的 `run_count` 是「跑过的 Run 数」。** 新建 Run 的预算行显式写的是
  `cost_quality=provider`、`consumed_cost=0`（`sql_store.py` 的 `_new_budget`：没调过
  模型的 Run 确实一分没花，是个**已知的零**）。所以从没执行过的 Run 落在 `provider`
  这一桶里，金额为 0。对预算阀门那是对的，对一张用量报表就容易被读成
  「这一桶的 1432 个 Run 花了这些钱」——**它们不是同一批 Run**。
  这一遍没有改这个语义，因为改的是产品口径而不是缺陷；但读这张表的人需要知道。
- **不声称用量的可见范围是想清楚过的。** 它沿用了 `list_runs` 的 `READERS`
  （工作空间管理员、开发者、查看者），因为「不要自己发明权限规则」是这次的约束。
  结果是**查看者能看到整个工作空间的花费**。§4.6 没有这一行，§6 也没写。
  如果这对查看者太宽，那是一条需要有人拍板的新规则，不是这里能顺手定的。
