# 一张卡片,原地改写 — 2026-08-25

> 产品:v2.5 §19.2(飞书渠道)、§19.1(不向终端用户暴露内部状态)。
> 起因:真租户发了一条要跑 17 秒的消息,**全程屏幕上什么都没有**,然后
> 才蹦出结果。原话是「需要立即知道 agent 正在处理」。

## 1. 为什么不是「机器人正在输入」

那是首先被问的方案,也是最好的方案——**飞书没有**。查了官方 FAQ,机器人只有
发消息的能力,没有 typing indicator、没有临时状态显示。

所以退而求其次:**发一条能被收回的消息**。`PATCH /im/v1/messages/{message_id}`
可以改写已经发出去的卡片,这是「先说话、后改口」的唯一途径。

## 2. 一条投递 = 一张卡片

| 时刻 | 卡片 |
|---|---|
| 消息到达约 1 秒后 | 蓝色「正在处理」 |
| 被前面的任务挡住 | **直接**是橙色「消息已排队」,不先说「正在处理」 |
| 超过 8 秒 | 原地变成「还在处理」 |
| 完成 | 原地变成绿色「回复」+ 内容 |
| 失败 | 原地变成红色「运行失败」+ 原因 |

聊天记录里**只有一条消息**。之前是卡片/文本堆叠最多三条。

阻塞的消息不先说「正在处理」——**没有任何东西在处理它**,它在排队,那句话是
平台明知为假的陈述。

## 3. 两个必须这样做的决定

**扫描发,不在入站路径发。** 在 webhook 事务里发会让入站投递依赖
`open.feishu.cn` 可达;超时飞书就重投一个**claim 已经拿掉**的投递,消息丢失
且不留痕迹。scheduler 每秒扫一次,1 秒延迟换这个风险,不划算的是后者。

**`config.update_multi: true` 必须在发送时和更新时都带。** 这是飞书的硬要求。
漏了它,所有 patch 在真租户上必然被拒——而**单元测试完全看不出来**。所以它放
在共享的卡片外壳里,并且有一条参数化测试盖住每一种卡片:新加一张卡片忘了带,
测试会挂,而不是等到真租户上才发现。

**`card_attempted_at` 和 `card_message_id` 分开。** 一次没拿到 id 的发送必须也
能离开开场扫描,否则那条投递会**每秒重发一张开场卡片**,直到七天后被清理。

**卡片开不出来时,答案仍然作为新消息发出。** 只能靠卡片说话的设计,会在卡片
不可达时彻底沉默——那比它取代的两条消息版本更糟。

## 4. 老测试是重写的,不是改绿的

20 多条老测试挂了,其中一部分**描述的东西已经不存在**:

- 「队列通知只发一次」——队列通知现在**就是**开场卡片,没有独立的第二条
- 「通知和回复不共享去重键」——patch **不带**收件人和去重键,它是对同一条消息
  的第二次写入,不是第二条消息

这些逐条重写成它们本来要守的东西。过程中犯了两次错并自己发现:一次把
`asked_for` 挤成了 `return` 之后的死代码(于是 `__call__` 抛
AttributeError,被 `_open_card` 的 except 吞掉,卡片发不出去);一次在修
pyright 时把 `opening` 属性整段切掉了。

**两次都是先看到"测试挂了"再回头找原因,不是靠读代码发现的。**

## 5. 破坏性验证

| 打掉什么 | 挂了几条 |
|---|---|
| 开场卡片整段 | 11 |
| 「无卡片时回退发新消息」 | 1 |
| `update_multi` | 4(每种卡片各一) |

## 6. 真租户验过什么

发「hi你是什么模型」,收到**一条**绿色「回复」卡片。数据库:

```
card_message_id = om_x100b67e0e8d7acbcb1b994e27efc4fd
opened=t  progressed=f  answered=t  reply_note=sent
```

`opened` 和 `answered` 同时为真且 `card_message_id` 有值——开场卡片发出去了,
然后被 patch 成了回复。同一张。

## 7. 这一遍没能证明什么

- **compose-e2e 还没在 CI 上取得绿色**,本地跑过的栈不算数。
- **`progressed` 那一档没在真租户上走到。** 那次 Run 不到 8 秒。「开场卡片 →
  还在处理 → 回复」的三段式端到端**没验过**,只验了两段。
- **失败卡片和排队卡片的 patch 没在真租户上验过。** 只有「正在处理 → 回复」
  这一条路径走通了。
- **14 天窗口、30 KB 上限、5 QPS 都没碰过。** 都是飞书文档写的约束,这一遍的
  消息离任何一条都很远。一个超长回复会不会撞 30 KB,不知道。
- **卡片开不出来时的回退路径没在真租户上走过。** 只有集成测试覆盖。
- 打字机效果(CardKit 的 `streaming_mode`)**没做**,也没假装做了。这一版是
  「立即出现 + 原地变成结果」,不是逐字流式。
