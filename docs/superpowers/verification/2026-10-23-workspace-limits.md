## 为什么有这一遍

单个 Run 的执行时间写死最多 900 秒：这个上限是 Agent 规格模型字段上的 `le=900`，哪个工作空间
都改不了。上一遍加的并发上限也只能用 SQL 设。

## 怎么做的

- 去掉规格模型里的 `le=900`。执行时间改成和模型调用次数一样：保存草稿和发布时，对照上限检查。
  去掉字段约束不改变任何已发布版本的内容哈希。
- 工作空间有四个上限设置。不设时就是原来的值（900 秒、20 次、每人 3 个、整体不限），所以已有
  的工作空间行为不变：

  | 设置 | 不设时 | 最多 |
  |---|---|---|
  | 单个任务最长执行时间 | 900 秒 | 7200 秒 |
  | 单个任务最多调用模型次数 | 20 次 | 200 次 |
  | 每人同时执行 | 3 个 | 1000 个 |
  | 整个工作空间同时执行 | 不限 | 10000 个 |

- 接口：
  - 成员都能读；
  - 只有工作空间管理员和平台管理员能改；
  - 超出范围返回 422，并说出允许的范围；
  - 每次改动写审计 `workspace.limits_changed`；
  - 请求里没带的字段保持不变，带 `null` 表示恢复默认。
- 控制台：「设置」最后一段「运行上限」：
  - 留空的输入框里提示「默认 900」，下方写「最多 7200」；
  - 不是管理员时只能看，不能改。
- Agent 编辑页：执行时间输入框的最大值从 900 改成平台的硬上限 7200，和模型调用次数的处理方式
  一样。超过工作空间上限的，由服务端拒绝，并说出两个数字。

## 测试过了

- 后端单元测试 2690 passed；集成测试（含 sandbox 目录）1285 passed、1 skipped；pyright
  0 errors；`ruff check` 通过；新迁移 `alembic check` 无差异。
- web：395 passed，`lint`、`build`、`tsc` 通过。
- 新测试：
  - 没设时读到的是平台默认值和上限；
  - 管理员设置后能读回来，数据库里的列（领取 Run 时读的就是这几列）对得上，并写了审计；
  - `null` 恢复默认；超出范围的四种值都返回 422；
  - 开发者能读、不能改（403）；
  - 1800 秒的 Agent 在默认上限下被拒（`execution_ceiling_exceeded`，信息里有 900），工作空间
    调到 3600 之后通过；模型调用次数同理；
  - 页面：留空时显示默认值和上限；管理员保存时只发数字或 null；非管理员是禁用状态，没有保存按钮。
- 改了两处旧测试：
  - 规格模型的测试原来断言 901 秒非法，现在改成 0 秒。上限检查搬到了写入时，由集成测试覆盖；
  - 导航测试固定了设置里各段的顺序，加上了新的一段。
- `tenancy` 测试目录加了 `__init__.py`，好让新测试能相对导入。原有 16 条照常通过。

## 走通了什么

本机 Compose 栈重建到这个分支，迁移到 `20261023_0077`。经控制台的 nginx（3000 端口）：

- 新工作空间读到的上限全是空，默认 900、最多 7200；
- 一个要 1800 秒的 Agent，保存草稿时被拒：`execution_ceiling_exceeded`，「这个工作空间允许 900，
  工作空间管理员可以调高」；
- 把上限设成 9000，被拒：`limit_out_of_range`，「最多 7200」；
- 设成 3600 秒、每人 5 个：返回 200；同一个草稿再保存，通过；
- web 容器里打包好的前端有「运行上限」这段文案。

## 这一遍没能证明什么

- **没有在浏览器里打开过这个页面。**页面只有组件测试（jsdom 加 msw）。
- 一个跑满 2 小时的 Run 没有真的跑过。长任务涉及时间片、租约续期、工作区提交，原来都是在
  15 分钟以内测的。
- 调低上限之后，已发布的版本照常运行。这一点是沿用 `max_model_calls` 原有的做法，没有为执行
  时间单独写测试。
- 每人上限和工作空间上限从界面改了之后，领取 Run 时怎么生效，由上一遍的领取测试覆盖
  （它们读的是同一组列），没有从界面一路测到领取。

## 不声称什么

- 不声称长任务现在能稳定跑 2 小时。允许申请到 2 小时，不等于 2 小时的任务验证过。
