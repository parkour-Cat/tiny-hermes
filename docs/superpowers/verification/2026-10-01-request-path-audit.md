# Worker 和 API 请求路径审查：领取从 1.1 秒到 4.5 毫秒

日期 2026-10-01。分支 `perf/request-path-audit`，未推送。
- 索引：测试 `322279a`，实现 `f542acb`（迁移 0071）；
- 快照：测试 `47ea48a`，实现 `10ce044`。

## 为什么有这一遍

[调度器扫描审查](2026-09-30-scheduler-scan-audit.md) 顺带发现，每次读取 Run 快照都会按一个没有
索引的列去扫描会话消息。那份记录没有审查 Worker 和 API 的路径，这一遍补上。

## 怎么审查

- api 跑在 uvicorn 里，没法从外面挂执行事件。所以改为临时打开 Postgres 的语句日志
  （`log_min_duration_statement = 0`）：各服务发出的每条语句、绑定参数和耗时都能记下来，走的
  是真实路径。测完已用 `ALTER SYSTEM RESET` 恢复成默认值。
- 负载：端到端 Playwright 测试（覆盖控制台和聊天界面的大部分 API），加上一个带工具长任务的
  小探针（覆盖 Worker 的完整生命周期）。
- 共记下 273 种不同的语句、52573 次执行。把参数作为字面量代回语句，在本机库上看执行计划：
  查询做 `EXPLAIN ANALYZE`，写操作只做 `EXPLAIN`。
- 判定分两步：
  1. 找出含全表扫描的语句；
  2. 在 `SET enable_seqscan = off` 下重新看计划。仍然只能全表扫描的，才是真的没有可用的索引；
     其余只是表小、规划器自己选的。
- 另外按「每执行一次实际读了多少行」排序，专门找那种「只用工作空间或会话索引缩小范围、再逐行
  过滤」的查询。本机的数据分散在很多个很小的工作空间里，这类查询在这里看起来很便宜。

**审查工具本身两次骗过我**，记下来，免得下次再踩：
- 第一次分析结果是「0 处全表扫描」，其实 273 条里有 268 条 `EXPLAIN` 失败了：日志里写的是
  `Parameters:`，脚本找的是小写的 `parameters:`，参数一个都没代进去。失败被静默跳过，看起来就
  成了「一切正常」。
- 修复后第一次「有索引」的计时，是在一个几乎空的库上做的：中间跑的一条集成测试会先清空整个
  测试库，把我造的大数据量也一起清掉了。那组数字作废，重新造数据后，在同一份数据上分别量了
  有索引和没索引两种情况。

## 发现

禁用全表扫描后，仍然只能全表扫描的有 6 条：

| 语句 | 执行次数 | 判断 |
|---|---:|---|
| API 每个请求的登录会话校验：按 `user_id` 取用户最早的身份 | 959 | **缺索引**，表随用户数增长 |
| Worker 领取：排除持有有效租约的 Run（`released_at IS NULL`） | 227 | **缺索引**，每个 Run 一行，随历史增长 |
| 列出全部工作空间 | 51 | 本来就要返回所有行，工作空间很少 |
| 是否已有平台管理员 | 5 | 只在初始化状态检查时调用 |
| OIDC 配置 | 3 | 配置表，几乎是空的 |
| 按 Run 统计技能提议 | 1 | 只在 Run 提议技能时调用 |

拆开 Worker 领取的每条语句时，又发现了第三个问题：
- **每个 Run 快照都会读出同一会话里的全部 Run**，只为了算排队位置，而真正需要的只有未结束的
  那些。
- 快照在每次 API 读 Run、每次领取、每次记录时间片时都会生成。
- 一个长期存在的会话（比如某个员工和飞书机器人的私聊）每发一条消息就多一个 Run。

## 改了什么

- 索引（迁移 0071）：
  - `ix_auth_identities_user`：`(user_id, created_at)`；
  - `ix_worker_leases_live`：`(expires_at, run_id)`，只收录 `released_at IS NULL` 的行。
- 快照只读未结束的同会话 Run。终态值以字面量写进 SQL，这样缓存下来的通用计划也能用上
  `ix_runs_live_by_session`。
- 测试：
  - 两个索引存在，条件正确（修复前红）；
  - 一个会话里放 60 个已结束、2 个未结束的 Run，读一次快照时，从 `runs` 返回的行数不超过 5。
    修复前是 63 行。这条测试看的是返回的行数，不依赖规划器怎么选。

## 走通了什么

**测试库**：一个会话里放了 30 万个已结束的 Run，每个都配一个已释放的租约；另有 10 万个用户，各有
一条身份记录。

| | 修复前 | 只加索引 | 索引 + 快照修复 |
|---|---:|---:|---:|
| Worker 领取一个 Run | 1139 ms（其中 SQL 120 ms） | 1014 ms | **4.5 ms** |
| API 登录会话校验 | 5.6 ms | 0.6 ms | 0.5 ms |

- 只加索引时领取几乎没变：租约子查询已经改走索引，但快照仍然把那个会话的 30 万个 Run 全部
  取回，并在 Python 里逐个处理，这一项占了约 1 秒。
- 「修复前」和「只加索引」两组，是在同一份数据上临时删掉、再恢复索引量的。

**本机栈**（重建后迁移到 0071）：
- 用同一份语句日志对新的库结构重新分析，「怎么都只能全表扫描」的语句从 6 条降到 4 条，剩下的
  正是上表里判断为影响不大的 4 条；
- 小探针：23 个 Run 全部完成，其中 3 个是带工具的长任务。

## 这一遍没能证明什么

- 负载只覆盖了端到端测试和探针用到的路径：
  - 端到端测试里「注册 HTTP 工具并调用」那条在本机失败（出口网段的环境问题），它后面的路径
    没有走到；
  - 渠道（飞书）收消息的路径没有走到。
- 「每次执行读了多少行」是在本机数据分布下量的；大工作空间、长会话的分布没有逐条造数据验证，
  只验证了上面这三处。
- 快照修复的测试只断言了返回的行数，没有断言排队位置的值。排队位置由已有的 API 测试覆盖，
  `runs` 集成测试 542 条都通过了。
- 只跑了一遍负载。

## 不声称什么

- 不声称 API 和 Worker 再没有随历史变慢的查询，只声称这一遍记下的 273 种语句里，剩下的全表
  扫描都已判断过原因。
- 不声称这两个索引和快照的改动对写入没有影响，写入开销没有测量。
