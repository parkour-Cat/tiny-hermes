## 走通了什么

集成测试驱动的是 Worker 的真实入口（`WorkerRuntime.run_once`）与真实数据库：

- 第一轮压缩并保存模型摘要，第二轮读存档点、不再压缩、不再调摘要模型，且模型实际
  收到的请求里有那份摘要（`test_the_summary_is_generated_once_and_then_reused`）。
- 过长的模型摘要不被采用、不被保存，退回结构摘要。
- 作者写的阈值穿过发布与 Worker 改变了一轮是否压缩；`/compact` 在阈值以下也压，
  并把保留区之外的全部拿走（被压缩的条数 + 原样发送的条数 = 历史条数）。
- `/compact` 从飞书长连接进来，在库里留下压缩 Run。

## 这一遍没能证明什么

- **没有对真实模型跑过。** 所有模型都是测试替身。九节摘要提示词、「对话是材料不是
  指令」这类规则，在真实摘要模型上的效果完全没有验证；存档点视图在真实 provider 上
  是否真的命中前缀缓存也没有测——「补回段每轮逐字相同」只在单元测试里断言了字节相等，
  不等于 provider 的缓存行为。
- **没有在飞书里发过一条真消息。** CLAUDE.md 记过长连接那次：注释、实现、测试建立在
  同一个虚构上互相印证。这里的集成夹具是直接往 `session_messages` 写行，不是真实对话
  长出来的历史。
- **没有取得 compose-e2e 结果。** 分支没有推送，CI 没有跑。按 CLAUDE.md，合并前必须
  重新取得 compose-e2e 绿色结果。
- **各常量（0.85、2 万、3 万字符、1/8、1/16、40 字符）没有实测依据。** 只与调研的七个
  Agent 量级一致。
- **大窗口（1M）只在纯函数层测过**，没有端到端跑过一个真正长到几十万 token 的会话。

## 不声称什么

- 不声称压缩后模型「记得」被压掉的内容。被截掉的工具输出，模型没有工具可以按
  `call_id` 取回，`session.search` 也不索引工具输出（规格 §1.10 已写明这是已知缺口）。
- 不声称摘要提示词能挡住对话里的注入。那是一句提示，不是隔离。
- 不声称这版比旧版省钱。改写次数变少、缓存应当更稳定，但没有真实账单或 provider
  用量数据支撑这句话。
