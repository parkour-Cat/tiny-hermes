# 调度器扫描审查：再找到 3 处随历史增长的全表扫描

日期 2026-09-30。分支 `fix/log-fields`，未推送。测试 `d5825ff`，实现 `f6d3d2b`（迁移 0070）。

## 为什么有这一遍

[会话队首巡检](2026-09-30-head-scan.md) 每秒对全部历史做平方级扫描，修好之后，还要确认调度器
每秒做的其他事里，有没有同一类问题。

## 怎么审查

- 在调度器容器里，按 `_scheduler()` 同样的方式构造调度器，挂上 SQLAlchemy 的执行事件，跑一轮
  `run_once()`，记下发出的每条语句、耗时和参数。
- 对每条语句看执行计划：查询做 `EXPLAIN ANALYZE`；写操作只做 `EXPLAIN`，不让它真的执行第二遍。
  记下每个计划节点读的是哪张表、用的哪个索引、过滤掉了多少行。
- 找的是「全表扫描一张会随历史增长的表」。

审查脚本在本机的临时目录里，没有提交进仓库。

## 结果

一轮 33 条语句。大部分已经走索引：按状态查 Run（`ix_runs_status`）、沙箱预留、审批过期、上传
垃圾回收，以及刚修好的队首巡检。全表扫描有 5 处：

| 扫描 | 表 | 判断 |
|---|---|---|
| 清理过期的幂等记录（按 `expires_at`） | `idempotency_records` | **缺索引** |
| 清理保留期外的事件（按 `occurred_at`） | `run_events`（最大的表） | **缺索引** |
| 派发渠道回复时找回复内容（按 `source_run_id`） | `session_messages` | **缺索引**，每条待回复的消息扫一遍 |
| 渠道消息的 5 类待办 | `channel_events` | 误报：每一类都有对应的部分索引，只是本机只有 72 行 |
| 过期的产物 | `artifacts` | 误报：有 `expires_at` 索引，只是表几乎是空的 |

两处误报的确认方法：在本机库上临时 `SET enable_seqscan = off` 再看计划，`channel_events` 的几条
查询和 `artifacts` 那条都改走了已有的索引。这说明这些索引能用于这些查询，数据量大起来以后，
规划器自然会选它们。

`source_run_id` 没有索引，还影响到调度器之外：
- 每次读取 Run 的快照（`_snapshot`：每次 API 读 Run、每次记录时间片）都按它去找这个 Run 的第一条
  用户消息。同时按 `workspace_id` 过滤，但那只能缩到整个工作空间。
- Run 列表的全文搜索也按它找。

## 改了什么

三个索引，迁移 0070：
- `ix_idempotency_records_expiry`：`expires_at`，只收录 `expires_at IS NOT NULL` 的行；
- `ix_run_events_occurred_at`：`occurred_at`；
- `ix_session_messages_source_run`：`(source_run_id, sequence)`，只收录 `source_run_id IS NOT NULL`
  的行。

测试：三个索引都存在，列和条件都正确。修复前 3 条都是红的。

## 走通了什么

**测试库里放大数据量**：100 万个事件（都在保留期内，所以没有一行该删），30 万条消息，30 万条
还没过期的幂等记录。每个调用跑 12 次，取第 3 次之后的中位数：

| 查询 | 频率 | 没有索引 | 有索引 | 计划 |
|---|---|---:|---:|---|
| 清理过期幂等记录 | 每秒 | 79.8 ms | 0.8 ms | 全表扫描 → 新索引 |
| 清理保留期外事件 | 每秒 | 46.9 ms | 1.1 ms | 全表扫描 → 新索引 |
| Run 快照（`get_run`） | 每次读 Run | 16.9 ms | 2.5 ms | 并行全表扫描 → 新索引 |

在这个数据量上，迁移建这三个索引一共约 2 秒。

**本机栈**（重建后迁移到 0070）：
- 派发回复的那条查询改走 `ix_session_messages_source_run`（禁用全表扫描之后确认）；
- 一轮调度约 54 ms，其中 SQL 一共 14 ms，最慢的一条 3.3 ms，都走索引；
- 空闲时 Postgres CPU 1–3%。

## 这一遍没能证明什么

- **只审查了调度器。**Worker 每个时间片发出的语句、API 的请求路径，都没有逐条审查过。
  `source_run_id` 那个问题就是顺着调度器发现的；别的路径上可能还有同类问题。
- 只审查了「什么都没找到」的那一轮：本机调度器空闲，大部分扫描查不到待办，所以只走了「查」
  那一步，「处理」那一步发出的语句没有出现。
- 两处误报是用 `enable_seqscan = off` 确认的：它证明索引能用，但没有在大数据量下实测规划器真的
  会选它。
- 大数据量是从一个模板克隆出来的，分布和真实数据不同。
- 一轮调度里约 40 ms 是 Python 和事务开销，没有分析。

## 不声称什么

- 不声称调度器没有别的随历史增长的开销，只声称这一轮发出的语句都走了索引。
- 不声称这三个索引不会拖慢写入，写入开销没有测量。
