# 主动裁剪：不花钱的那几级不等压缩线 — 2026-09-02

> 由来：讨论 `MIN/MAX_COMPACTION_THRESHOLD` 该定多少时，发现问题不在那几个数上。
> 使用者的原话：「模型支持多少上下文就是多少，要限制直接限制额度不好吗」——顺着这句
> 查下去，缺口不是阈值，是**四级级联共用一个触发点**。

## 1. 为什么改

`plan_context` 里是这样：

```python
if spent <= trigger:
    return ...        # 没超线，四级一级都不做
```

四级里前三级不花钱（裁剪），第四级要一次模型调用（结构化摘要）。绑在一起的后果在
大窗口上很具体：**1M 窗口、阈值 0.50，要攒到 500K 才开始清理**，而那之前每一轮都在
把早已无用的工具输出逐字重发。

参照实现 `NousResearch/hermes-agent` @ `3f83297` 的
`agent/context_compressor.py::prune_tool_results_only` 的 docstring 描述的是同一件事：

> On large-window models `should_compress()` (≈50% of the window) rarely fires, so old
> tool outputs otherwise ride in history and are re-sent verbatim on every subsequent turn.

## 2. 做了什么

`_prune_proactively`，三遍确定性处理，**都不调模型**：

1. **去重**字节完全相同的工具结果——最新的留完整，更早的改成回指。**无损，因此不受
   尾部保护限制**。
2. **打存根**：尾部之外、超过 `PRUNE_MIN_RESULT_CHARS` 的工具结果。
3. **截断**尾部之外过大的工具调用参数——一次贴进去的长脚本此后每一轮都在再付一遍钱。

两道闸门在调用处（它们决定「采不采纳」，不是「结果长什么样」）：

- 历史小于 `PROACTIVE_PRUNE_TOKENS`（8,000）不动
- 三遍合计回收不到 `PRUNE_MIN_RECLAIM_TOKENS`（4,096）**整体丢弃，原样返回**

尾部保护按**条数**（`PRUNE_PROTECTED_RECENT_MESSAGES = 20`）而不是 Token——参照实现
专门点了这个陷阱：按 Token 会在 1M 窗口上护住约 100K，等于护住整个会话，什么也裁不掉。

## 3. 和参照实现的一处架构差异，是有意的

Hermes 的裁剪**有状态、提交进会话库**，所以它需要「解除武装」：提交之后禁用自己，
直到历史重新长出一整个触发线那么长的跑道。

我们的 `plan_context` 是**纯函数、每轮重算**（§7.4.2 明确要求）。所以改成
**一次裁完所有够格的内容**：稳态下够格的早已裁完，新增的改写只落在刚离开尾部的
那一条，缓存失效范围因此有上界。每轮啃一点会把失效点一路往前推——那正是这套闸门
要避免的事。

## 4. 测试

五条，各守一面：大结果在压缩线之前就被裁、尾部按条数保护、去重在尾部内也生效、
尾部之外的参数被截断、回收不够时一个字不改。

**最后那条断言的是「历史逐条相同」而不是「没有 trimmed 记录」**：后者一个改了内容
却忘了记录的实现也满足。

写测试时有两条先红了，查下去是**夹具太小没跨过闸门**（两段 8K 字符只回收约 2K Token，
低于 4,096，实现正确地放弃了），以及我把断言写成了「短于阈值」——截断后是「阈值长度 +
一句说明去哪儿取全文」，本来就比阈值长。两处都改了测试并把原因写进注释：**实现是对的。**

## 5. 这一遍没能证明什么

- **没有量过真实收益。**没有一条测试、也没有一次线上观察，回答「这实际省了多少 Token /
  多少钱」。闸门的数（8,000 / 4,096 / 20 / 8,000 字符）**全部照抄参照实现的量级**，
  没有针对本平台测过。
- **缓存那半边完全没有证据。**「稳态下失效点落在尾部边界」是从纯函数的确定性推出来的，
  不是观测到的。provider 侧真实的缓存命中率变化没有测量。
- **没有验过它和结构化压缩同时发生时的相互作用。**两者现在一前一后跑在同一个函数里，
  测试各自覆盖，没有一条同时触发。
- 没有真机走查——这条改动在模型调用路径上，本机 compose 栈用的是确定性模型。

## 6. 不声称什么

- **不声称那几个常量是对的数。**它们是参照实现的量级，不是本平台的测量结果。第一件
  该做的后续是量真实数据，而不是继续调它们。
- **不声称这解决了「阈值该定多少」。**`DEFAULT_COMPACTION_THRESHOLD = 0.50` 一个字没动。
  这次改的是「不花钱的那几级不再被它挡住」，那个数管的仍然是唯一花钱的一级。
- **不声称段预算表里「旧工具结果 2,048」被执行了。**它明确**不**作为这条路径的判据，
  理由写在 §7.4.2：按它每轮裁到 2K 等于每轮改写历史、每轮打断缓存。
