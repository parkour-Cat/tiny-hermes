# gVisor 兼容：冻结的沙箱能删掉，沙箱能找到出网代理

日期 2026-10-24。分支 `fix/gvisor-compat`。修的是 [gVisor 试装](2026-10-24-gvisor-trial.md)发现的第 1、2 条。

## 改了什么

1. **删除前先恢复暂停的容器。** gVisor 下对已暂停的容器 `docker rm -f` 会失败（`is zombie and can not be
   killed`）。`DockerEngine.remove` 先查一下状态，暂停的先恢复再删。runc 下没必要这样做，代价是每次删除多一次查询。
2. **沙箱通过 hosts 记录找到代理。** Docker 内置的名字解析（`127.0.0.11`）在 gVisor 下不工作。现在代理在每个
   沙箱网络里固定占子网的第二个地址（`.2`，`.1` 是网关），建沙箱时写一条 `代理名 -> 这个地址` 进 `/etc/hosts`。
   两种运行时用的是同一套做法。
3. **测试**：所有用真 controller 的沙箱集成测试，现在会在这台 Docker 有的每种运行时下各跑一遍（新的
   `sandbox_runtime` 夹具）。没有 `runsc` 时跳过那一半，CI 现在就是这样。

产品设计 §1.25 补了这两条行为，运维手册 §17 更新了状态。

## 测试过了

- 本机装了 `runsc`：沙箱集成测试 **300 passed、1 skipped**，两种运行时都是全绿。改之前在 runsc 下有 4 条失败：
  3 条是删除冻结的沙箱，1 条是按名字连代理。试装时另有 1 条冻结相关的失败，这次改之前没有复现。
- 后端单元测试 2765 passed。新增的测试检查了容器参数里的 `extra_hosts`，也检查了代理地址和 hosts 记录是不是
  一致。
- 本机栈的 controller 换成这个分支、设成 `runsc`：两次 18 轮长任务和一次大量写文件的命令都完成了。之后改回了
  `runc`。

## 这一遍没能证明什么

- 代理是测试里的一个替身容器。真实的 `egress-proxy` 在 gVisor 下能不能转发请求，没有走过，因为本机栈没有配沙箱
  网络。
- 冻结后回收这条路只在集成测试里走过；本机栈上的这几次 Run 结束后沙箱直接销毁了，没有经过冻结。
- 代理被重建（新容器）后要重新连到已有的沙箱网络，这件事本来就没有人做，和这次改动无关。固定地址让重新连接以后
  地址不变，但这个重连本身没有实现。
- CI 不跑 runsc，这一半的覆盖只在装了 gVisor 的机器上有。

## 不声称什么

- 不声称 gVisor 已经能上生产：缓存目录的 inode 上限在 gVisor 下仍然不生效，通过真实代理出网也还没验过。
