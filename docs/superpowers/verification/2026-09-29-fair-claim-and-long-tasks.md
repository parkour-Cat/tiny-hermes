# 公平领取（v2.13）与长任务负载

分支 `feat/fair-claim`，建在 `feat/worker-concurrency` 之上。未推送、未合并。

## 为什么有这一遍

推演「员工同时跑长任务」时，读代码发现两件事：

- 领取按 `created_at` 排序；
- 时间片结束的 Run 回到队列时，创建时间不变。

两者合起来，Worker 饱和时，新消息要等所有更早创建的长任务都轮完。之前的探针每个
Run 只有一轮、3 秒就结束，测不到这种情况。

## 测试过了

在 `52a1357`（这个分支最后一个代码提交）上：

| 套件 | 结果 |
|---|---|
| 后端单元（全部） | 2464 passed |
| 后端集成（不含 sandbox，全部） | 1011 passed |
| 前端 `@tiny-hermes/web`（在 `6b8d2be`，之后前端没有改动） | 391 passed |
| `alembic check` | 模型与迁移无漂移；`0066` 降级再升级正常 |
| `ruff` / `pyright`（改动文件） | 通过 / 0 errors |

先写测试并看它红：

- `test_a_run_back_from_its_slice_queues_behind_one_that_arrived_meanwhile`：长任务的
  第一个时间片结束时，另一个 Session 来了一条新消息；旧顺序下，下一次领取拿到的是长任务。
- `long_task` 场景的 5 条单元测试。
- 探针的分组与容器计数测试。
- compose 容量旋钮测试：3 条红。

`test_a_run_waiting_behind_its_session_head_keeps_its_place` 从一开始就是绿的，它钉住的
是新顺序不能破坏的旧性质。

第一次跑前端测试时有 2 条失败。当时后台正在跑集成测试，两条单独重跑都通过，机器空闲时
全量重跑 391 条全部通过。

## 走通了什么

本机开发栈重建到这个分支，库迁移到 `20260929_0066`（字段和部分索引都在）。以下都是
确定性模型加真实沙箱：每轮在 SessionWorkspace 里执行一条 `printf >> progress.txt`，
并提交一个工作区版本。

### 公平领取：同一负载，只改领取顺序

- **负载**：4 个 Worker，16 个长任务（每个 18 轮），每轮模型延迟 2 秒。5 秒后开始发短
  消息，每秒 0.5 条，持续 40 秒，共 20 条。
- **做法**：「旧」是把领取查询那一行临时改回 `created_at` 后重建的栈。这个改动只在工作
  区里做，没有提交；测完用 `git checkout` 恢复，再重建，并在容器里核对过代码。

| 指标 | 旧（`created_at`） | 新（`queued_at`） |
|---|---:|---:|
| 短消息排队 P50 / 最大 | 145.0 / 146.7 s | **110.4 / 122.6 s** |
| 长任务端到端 P95 | 173.9 s | 183.4 s |
| 同时存在的沙箱（取峰值） | 运行 5 | 运行 4 + **冻结 16** |

读法：

1. 短消息的等待少了约四分之一。按 v2.13 写进规格的上界算，前面有 12 个长任务在排队、
   4 个 Worker、30 秒时间片，是 90 秒，再加上正在跑的那一轮；实测 110–123 秒，和这个
   上界一致。
2. **轮转有代价。** 16 个长任务轮流推进，每个都带着一个冻结的沙箱等下一轮，所以同时
   存活的沙箱从 5 个变成了 20 个。这次每个沙箱只执行 `printf`，20 个合计 9 MiB；换成
   真实工具，这个倍数会直接放大内存占用。
3. **两种顺序下，短消息都等了约 2 分钟。** v2.13 防的是「饿死」：旧顺序下，等待时间随
   长任务的总工作量增长；新顺序下，等待只取决于排在前面的数量和时间片长度。但它不会
   让交互变快。在容量不够的时候要让交互快，得靠交互优先、每个用户的并发上限和更短的
   时间片，这些这一遍都没做。

第一次用 12 轮做的公平实验不计入：探针的沙箱采样线程在中途崩了，后来已修（`da3ba65`
测试，`d62710c` 修复）。

### 一台机器同时跑多少个沙箱

- **负载**：`WORKER_CONCURRENCY=32`，32 个长任务，每个 10 轮，模型延迟 1 秒。

| 指标 | 实测 |
|---|---|
| 完成 | 第一次 32/32；第二次 31/32，失败原因见下一节 |
| 长任务执行时间 P50 | 26.3 s。理论值约 12 s：10 轮 ×（1 s 模型 + 单任务时实测的约 0.2 s 工具开销） |
| 每轮额外开销 | 约 1.6 s，单任务时约 0.2 s，**放大约 8 倍** |
| Worker 进程 CPU 峰值 | **81.7%**（一个核）。不带工具、25 路并发时是 32.8% |
| Worker 内存 | 128 MiB |
| 数据库连接峰值 | 53 |
| 沙箱（各状态峰值） | 运行 23、冻结 16、创建中 4；合计内存 16 MiB |

在最忙的那一刻采样：控制器 CPU 23%、对象存储 12%、数据库 30%、Worker 40%，都没有打满。
所以放大更像是在**排队**，而不是在算。一个吻合的猜测是：控制器用 `asyncio.to_thread`
调 Docker，没有设线程池，用的是默认的 `min(32, CPU 数 + 4)`，这里是 12 个线程；而
`exec_start` 在命令执行期间一直占着线程。**这一点没有验证。**

## 这一遍发现的问题（都是改动之前就有的，这一遍没有修）

1. **租约续期和工作区提交会死锁。** 第二次 32 路运行中，一个长任务在
   `workspace_checkpoint_failed` 后被中断，恢复后失败。Postgres 同一时刻报
   `deadlock detected`：
   - 续期（`renew_lease`）先改 `worker_leases`，再改 `runs.last_heartbeat_at`；
   - 工作区提交（`committer._commit_once` → `record_slice`）先锁 `runs`，再
     `SELECT … FOR UPDATE` `worker_leases`。

   Worker 里的 `_lease_lock` 只把「记录时间片」和「续期」互斥开了，工作区提交这条路径
   没有拿它。64 个长任务、约 640 轮里出现 1 次。
2. **最后一次允许的调用把任务做完了，Run 却停在 `paused(limit)`。**
   `decide_after_round` 里 `budget_allows` 排在 `DONE` 前面。19 轮的长任务在第 20 次、
   也就是最后一次调用里 `goal_verdict: done`，结局却是 `run_limit_reached`。暂停的 Run
   还占着 Session 队首，这个人的下一条消息会一直卡着。
3. **时间片只在时长用完时结束，不在 Goal 轮结束时结束。** §21.3 写的是「一个 Goal 轮
   结束或 `max_slice_seconds` 到期」；实现里一轮结束只要时间没用完，Worker 就继续拿着
   这个 Run。公平测试因此把时间片设成了 1 秒。
4. **单个 Run 的执行上限。** `max_execution_seconds` 在 `AgentLimits` 里写死为 `le=900`；
   `max_model_calls` 受平台上限 `AGENT_MAX_MODEL_CALLS` 约束，默认 20。所以默认配置下，
   一个「长任务」最多约 20 轮、累计 15 分钟执行时间。
5. **Compose 没把三个容量旋钮传进容器**：`WORKER_MAX_SLICE_SECONDS`、
   `AGENT_MAX_MODEL_CALLS`、`AGENT_MAX_TOOL_CALLS`。**这一条这一遍已经修了**：`824b831`
   测试，`52a1357` 实现。实测把 `AGENT_MAX_MODEL_CALLS` 设成 40 后，30 轮的长任务能发布
   并完成。

## 这一遍没能证明什么

- **没用真实模型，也没用真实工具。** 沙箱每轮只跑一条 `printf`，内存数字只代表容器本身
  的开销。
- 「控制器线程池导致每轮开销放大」只是猜测，没有做对照实验。
- 公平 A/B 每边只跑了一次。
- 死锁的复现依赖时机，没有写成测试。
- 没有测 SSE 观看者，没有测多个 Worker 容器，也没有测超过 32 路。
- **没有取得 compose-e2e 结果。**

## 不声称什么

- 不声称新的领取顺序让交互变快了。它只是给等待加了上界，并去掉了等待随长任务总量增长
  的那部分。
- 不声称一台机器能撑 32 个带工具的并发 Run。32 路时，有一次出现了死锁失败，每轮开销
  也放大了 8 倍。
- 不声称上面列出的 1–4 已经修好。

测完已经恢复成 1 个 Worker、`WORKER_CONCURRENCY=1`、50 ms、默认上限。库里留下了名为
`probe-*` 的工作空间，以及一个因死锁失败的 Run（`21ffd055-…`）。
