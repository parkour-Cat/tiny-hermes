> 计划：`docs/superpowers/plans/2026-08-20-end-user-entry.md` §10。

## 1. 这一节为什么存在

它补的是**计划的漏，不是实施的漏**。§4.6 给终端用户两格权利——`Run 暂停、继续与
取消 = 本人`、`用户确认审批 = 仅发起人本人`——而前九节没有任何一节被指派去建它们。
于是八个任务各自「完成」并通过了各自的评审，两格却从头到尾没有落点。

**单节评审在结构上看不见这种缺口**：缺的东西不在任何一节的范围里。全分支评审是第一个
能看见的位置。这是这次唯一真正的教训，比这一节的代码本身更值得记住。

## 2. 做了什么

| 做的 | 之前是什么样 |
|---|---|
| `GET /api/v1/end-user/approvals` | 不存在。`decision` 路由建好且有测试，但**没人拿得到 `approval_id`**——没有列表、没有任何终端用户响应带得出它、`apps/chat-web` 里「approval」出现 0 次。那些测试之所以过，是因为它们直接从数据库读 id |

## 3. 只做了三分之一，而且是故意的

`暂停` 与 `继续` **没有建**。聊天界面里没有「暂停」这个动作的语义位置，而取消是抹除
和「我不想要这个答案了」都需要的那一个。

**这一点是用测试钉的，不是用一句话记的。** `test_pause_has_no_end_user_route` 和
`test_resume_has_no_end_user_route` 断言这两条路线返回 404。理由很实际：一句「我们
有意只做了三分之一」几个月后会被读成「这一行做完了」，而一条测试不会。

§4.6 那一行因此仍然欠着三分之二，**这份记录明确不声称它已经兑现**。

## 4. 出口检查对证据

- **本人能答自己的确认。** `test_end_user_approvals.py` 的列表半边 + e2e 里真正的点击。
- **别人的确认答不了。** 列表按 `requested_by = 本人` 过滤，且只列 `user_confirmation`
  与 `pending`。§763 说管理员都不能代批，那么另一个终端用户更不能。
- **治理审批永远答不了。** `test_a_governance_approval_is_refused_to_an_end_user_regardless`
  管住 decision 那一侧，列表这一侧与它一致。
- **取消只能取消自己的。** 复用 `_store.control_run`，没有第二套状态机。
- **响应不漏控制台字段。** 取消的响应断言 `not (_CONSOLE_ONLY_RUN_FIELDS & set(body))`。

## 5. §27.2 场景 6

**现在可以记成绿的了，而且是对证据说话的绿。** 生产者在上一阶段就有了；这一阶段补上
了消费者**够得着**的那一半。上一份记录（`2026-08-21-end-user-entry.md`）里那条补正
——「生产者有了，消费者有了，路走不通」——到此为止。

判据不是「后端测试过了」，而是 e2e 里一个人在界面上看见横幅、点了「同意」、Run 接着
跑完。上一阶段正是栽在把前者当成后者。

## 6. 这一遍没能证明什么

- **e2e 没有在本地跑过。** 它需要重建的 compose 栈，走的是 CI。本地跑过的是后端与
  前端单元/集成。
- **取消一个正在执行中的 Run 的时序**没有专门压测。测的是状态机接受这个转换、
  归属检查拒绝别人，不是「Worker 正写到一半时取消会怎样」——那是 M2 状态机自己的
  地盘，这一节没有改它。
- **`暂停`／`继续` 不存在**，所以关于它们的一切都没有证据，只有两条 404。

## 7. 顺手修的一个既有缺陷

`problemMessage` 直接 `import { t } from "../i18n/zh-CN"`，于是所有被映射的错误码
无论用户选了什么语言都渲染成中文——**全 app 唯一一处「切了语言但什么都没发生」的
地方，而且恰好是用户最用力在读的时候**。

不是这一节引入的，但这一节新增的三个错误码正好从这里过。改成由调用方传入自己的 `t`；
三个调用点本来就有 `useT()`。签名现在**强制**它，所以退回硬编码是编译错误而不是一个
安静的错字符串。
