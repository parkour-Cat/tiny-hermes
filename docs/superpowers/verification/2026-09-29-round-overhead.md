# 32 路并发时，每轮多出的 1.5 秒花在哪里

2026-09-29。这是一份调查记录，**没有改代码**。所有临时插桩和临时改动都已撤掉：源码和
运行中的容器里 `grep DEBUG-p1c3` 与 `EXPERIMENT-POOL64` 都是 0 条。

## 问题

[公平领取与长任务](2026-09-29-fair-claim-and-long-tasks.md)记录过：32 路并发的长任务，
每轮除了模型调用之外的开销，从单任务时的约 0.2 秒涨到约 1.6 秒。当时的猜测是
sandbox-controller 用默认线程池（`min(32, CPU 数 + 4)`，这里是 12 个线程）调 Docker，
在排队。[容量方案](../plans/2026-09-29-enterprise-capacity.md) 把它列为 P1 第 3 项。

## 方法

一律先量，再改；每次只改一个变量。负载都是：N 个长任务，每个 10 轮，每轮模型延迟 1 秒，
`WORKER_CONCURRENCY=N`。每轮在 SessionWorkspace 里跑一条 `printf` 并提交一个工作区版本。

- **每轮的拆分**：同一轮的事件在轮结束时一起写入。于是：
  - 墙钟时间 = 相邻两轮 `model_round` 事件的 `occurred_at` 之差；
  - 工具时间 = `tool_called.duration_ms`；
  - 模型时间 = `model_round.latency_ms`；
  - 其余 = 墙钟时间 − 模型时间 − 工具时间。
- **更细的拆分**：在 `SessionWorkspaceService.checkpoint` 的每一步，以及 Worker 一轮
  循环的各个阶段，加了带 `[DEBUG-p1c3]` 标签的计时打印。只改工作区、只在本机栈上用，
  测完用 `git checkout` 撤掉。

## 基线：默认线程池（每轮 P50）

| N | 工具（沙箱命令） | 其余 | 整轮 |
|---:|---:|---:|---:|
| 1 | 60 ms | 109 ms | 1173 ms |
| 8 | 96 ms | 304 ms | 1402 ms |
| 16 | 105 ms | 377 ms | 1472 ms |
| 32 | 368 ms | 1564 ms | 2980 ms |

变坏的拐点在 16 到 32 之间，不在超过 12 之后。这已经不太像线程池。

## 假设与检验

| 假设 | 做法（只改这一个变量） | N=32 的结果 | 结论 |
|---|---|---|---|
| controller 线程池 12 个不够 | 在工作区里临时把默认执行器设为 64 线程，重建 controller | 工具 368→222 ms，其余 1564→1335，整轮 2980→2680（−10%） | **次要因素**，不是主因 |
| Worker 进程 CPU 或 GIL 饱和（单进程 CPU 75%） | 同样 32 路，改成 2 个 worker 容器 × 16 | 每个进程 CPU 降到 43%；整轮 2682 ms（−10%） | **次要因素** |
| 数据库每次提交都等 fsync | 临时 `ALTER SYSTEM SET synchronous_commit = off`，前后用新连接核对，测完恢复 | 数据库各步 14/16/16/72 ms，开着时 15/17/18/84 ms | **排除** |
| 整台虚拟机 CPU 饱和 | 运行中每 2 秒从容器里读 `/proc/loadavg` | 1 分钟负载中位数 3.3，最高 5.3（8 vCPU） | **排除** |
| Docker 守护进程的 exec 吞吐 | 绕开 tiny-hermes：对空闲容器用 docker SDK 并发 exec | 1 路 p50 20 ms；8 路 50 ms；32 路 193 ms（p95 467）；吞吐在 **136–150 次/秒** 封顶 | **是一个硬上限** |

## 时间实际花在哪里（N=32，P50）

检查点这一轮（Worker 循环里「上一轮检查点 + 记录」这一段）：单任务 98 ms，32 路 1192 ms。

| 段 | 单任务 | 32 路 |
|---|---:|---:|
| 提交前准备 | 29 ms | 150 ms |
| `service.checkpoint`（工作区提交） | 54 ms | 726 ms |
| `_dispose_after_commit`（沙箱去留与本轮信号） | 18 ms | 176 ms |

`service.checkpoint` 里约 15 次**串行**往返，每一次都慢了 5 到 15 倍：

| 类别 | 步骤 | 单任务 | 32 路 |
|---|---|---:|---:|
| controller / Docker | `scan`、`stage_bodies` | 6、10 ms | 74–124、157–214 ms（p95 约 700 ms） |
| 数据库 | `register_upload`、`mark_finalizing`、`mark_ready`、`ledger_commit` | 3、4、3、10 ms | 14–20、15–19、16–20、69–84 ms |
| 对象存储 | `base_manifest`、`put_manifest`、`put_index_and_stat`、`place_final_objects` | 1–5 ms | 11–26 ms |

另外，一轮里的「执行工具」（预占工具次数 + controller exec）：单任务 67 ms，32 路 251 ms。

## 结论

1. **线程池不是主因。** 把它从 12 调到 64，32 路时整轮只快了约 10%。
2. **主要开销在「每一轮都提交一个工作区版本」这件事本身。** 一次提交约 15 次串行往返，
   前后还有两段各约 150 ms。并发一高，每一次往返都慢 5 到 15 倍，没有哪个单点被打满，
   是往返的次数被放大了。
3. **Docker 守护进程在这台机器上是一个硬上限**：exec 大约每秒 140 次封顶。每轮要经过
   它好几次（工具命令、扫描、导出），所以同一台主机上带工具的并发是有天花板的。这给
   容量方案里「沙箱主机池」一项补上了实测依据。

## 按证据排序的优化方向（都还没做）

1. **减少每轮经过 Docker 的次数**：比如把 `scan` 和 `stage_bodies` 合成一次 exec。
   这两步是 32 路时最慢的，p95 各约 700 ms。
2. **减少一次提交里的数据库事务数**：现在是 4 次。它们的先后顺序是为了崩溃安全和 GC
   区分进行中的提交（设计 §6.2、§8），合并之前要先弄清哪些顺序是必须的。
3. **controller 线程池调大**（比如做成配置，默认 32）：实测约 10%，改动小、风险低。
4. **沙箱多主机**：因为 Docker exec 吞吐是单机上限，见容量方案的 C 档。

## 这一遍没能证明什么

- 都是在 macOS 的 OrbStack 虚拟机上测的。Docker exec 的吞吐上限在原生 Linux 主机上
  可能完全不同，「每秒约 140 次」不能外推。
- 负载每轮都写文件，所以每轮都会提交。真实 Agent 里不写工作区的工具（HTTP、搜索）
  不会触发提交，这部分开销没有测。
- 每个配置只跑了一次。线程池和两进程带来的约 10% 改善，和单次运行的波动是同一个量级。
- 插桩是 `print`，本身也有一点开销；各步 P50 相加不等于整段的 P50。

## 过程中的差错

- 第一次 `synchronous_commit=off` 实验，关掉之后没有用新连接确认。在同一个连接里读到的
  还是 `on`，而 `pg_reload_conf()` 是异步生效的，所以那一次不作数。
- 第二次用 `$P` 变量拼命令，zsh 不做分词，psql 根本没有执行；那一次实际是开着
  `synchronous_commit` 跑的，正好成了一个开着时的对照点。
- 第三次每条命令都写全，关掉之前、运行中途、恢复之后，都用新连接核对过，才作为结论
  采用。开发库现在是 `synchronous_commit = on`，来源 `default`。
