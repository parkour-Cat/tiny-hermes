# 旧会话压成一份模型写的摘要 — 2026-08-30

> 产品：v2.7 §7.4.2。
> 起因：与 v2.6 同源。`#60` 给了用户一个人工出口（`/undo`、`/new`），但没有碰使那次
> 事故成为可能的机制——历史里的错话没有任何处理办法。压缩是唯一会重写历史的环节，
> 而它只在装不下时触发：那条 80 条消息的会话离 128k 窗口差得远，压缩一次都没跑过。

## 2. 那 2 条失败是环境

`test_a_check_on_a_deployment_with_no_boundary_says_so` 与
`test_a_check_reaches_nothing_when_there_is_no_boundary`。`shared/config.py:11` 是
`SettingsConfigDict(env_file=".env")`，而本机仓库根有一个给 compose 用的 `.env`，里面
有 `EGRESS_PROXY_URL`——于是「没有出口边界」这个前提在本机不成立。CI 上没有那个文件。
已单独立卡，不属于这条分支。

## 3. 这条路走得通

真实飞书应用、部署的那套栈，2026-08-30。为了在合理轮数内触发压缩，把该端点声明的
`context_window` 临时从 128000 改为 16000（阈值是窗口的比例，所以压缩点降到 8000）；
走查后已改回。**改的只是「平台以为这个端点有多大窗口」，压缩判据、摘要生成、复用、
计费、事件全部走真实代码路径。**

事件按时间：

```
12:51:55  billed + compacted(source=model, last_sequence=27)   第一次：生成并落库
12:55:53           compacted(source=model, last_sequence=27)   第二次：无计费事件
13:35:48  billed + compacted(source=model, last_sequence=42)   /new 撤回删掉摘要后重生成
```

| 要证的 | 观察到的 |
|---|---|
| 压缩触发 | `context_compacted` ×3 |
| 摘要是模型写的 | `source: "model"`，落库文本是 §7.4.2 的七节格式（「- 目标：用户未明确提出目标…」） |
| **生成一次** | **12:55:53 那次压缩用了模型摘要却没有计费事件——读的是存下来的那份** |
| 计费事件在流里 | `model_calls: 1, input_tokens: 364, output_tokens: 782, tokens: 1146` |
| `consumed_model_calls` 累加 | 2（本轮调用 + 摘要调用） |

两条计划外的确认：

- **压缩拆开工具对的 bug 在真实运行上修好了。** 走查第一轮撞到
  `400 Messages with role 'tool' must be a response to a preceding message with 'tool_calls'`
  ——压缩边界落在 `tool_calls` 与它的 `tool` 结果之间。这是本分支之前就有的潜伏缺陷，
  §7.4.2 明写「工具调用与工具结果不能拆开」而压缩边界从未实现它；**是本分支的比例
  触发让它第一次可达**。修复后同一路径 400 归零。
- **撤回删摘要这条链路真实生效。** 13:35:58 撤回 sequence 40–51，落在摘要覆盖范围内，
  那份摘要被删；下一次压缩因此重新生成而不是复用一份含有已撤回内容的文本。

## 4. 六个任务各自评审通过，最终整分支评审仍抓出 6 条

这一节是这一遍最值得留下的东西。

**最重的一条是本项目招牌 bug 的第四次出现。** `source`、`endpoint_id`、`model`
三个字段——§7.4.2 加它们的唯一理由是让运维分得清模型读到的是语义摘要还是一句
「这里曾有 38 条消息」的清单——写进了事件 payload，**没有任何渲染代码读它们**。
`git diff --stat -- apps/web` 是空的。而运维实际看到的那句话是「摘要由平台按固定规则
生成，没有为此多调一次模型」，在每一次模型路径的压缩上都是假的，就印在与它矛盾的
payload 上方。

另外两条中等：

- **被 `/undo` 撤回的轮次会通过复用的摘要重新进入上下文。** 摘要里蒸馏着用户刚收回的
  内容，而复用检查只往上界卡。这直接抵消 v2.6 的 `/undo`，也违反 §14.3。
- **比例触发会让一个装得下的 Run 被 `paused(context_overflow)`。** 进了级联但四步都没能
  接受，底部没有「装得下就返回原文」的兜底。**本分支之前这条按构造不可达**——级联只在
  原文已经装不下时才进入。

**同一形状在开发过程中出现了三次**（字段进不了持久化事件、端点没人证明真路由过去、
拒绝理由到不了 API），每一次都是评审比测试多追了一层才发现的。**每一次后端测试都是
全绿的**，因为断言都停在真正要紧的那一层前面一层。

`uv run alembic check` 在最终修复轮之前就已经是红的（0049 没有创建 ORM 声明的
`ix_session_compactions_workspace_id`），CI 跑这条命令——它会挡住合并，而没有人注意到。

## 5. 这一遍没能证明什么

- **`compose-e2e` 绿了，但它一条压缩都没测。** run `33296873289`（PR 触发那次），
  `18 passed (2.7m)`，已用 `gh run view --log | grep "^compose-e2e"` 确认是真跑了测试而
  不是只返回 success。但 `tests/e2e/` 里没有任何一条会让会话长到触发压缩。
  **它证明的是这条分支没有弄坏别的东西，不是压缩能用。**
- **摘要质量没有任何度量。** 没有对照，没有评分，没有人读过一份真实的模型摘要判断它
  是否忠实。所有测试断言的都是「有没有生成」「有没有复用」「失败时有没有降级」，
  没有一条断言「摘要说得对不对」。
- **多次更新后的漂移完全没有观察过。** §7.4.2 要求后续压缩**更新**上一份摘要，于是错误
  会被继承。压第五次、第十次之后摘要还剩多少真实信息，没有任何数据。
- **提示词里那句「只记录发生了什么，不要记录助手声称的能力状态」减轻不了全部风险。**
  摘要模型读到的仍然是那些话，它没有任何依据判断哪一句是故障产物。这一句是冲着
  2026-08-26 那次事故写的，但它不能消除那个问题，代码注释里也这么写了。
- ~~摘要调用的花费不计入预算~~ — **已在本分支修复**：摘要调用现在累加
  `consumed_tokens` / `consumed_cost` / `consumed_model_calls`，发出
  `CONTEXT_SUMMARY_BILLED` 事件，并在调用前预检调用次数上限。产品决定「计入
  `max_model_calls`」写进了 §12.4。**但缓存经济学没有验证过**：压缩会作废前缀缓存，
  所以压得更勤在计费上可能是成本上升而不是下降，这一点没有任何数据支撑，
  也正是下面「阈值 0.50 未经验证」的一部分。
- **生成失败没有负缓存**：摘要一直失败的 Session 每轮都会重试一次。不丢消息，只是多花钱。
- **`MIN_COMPACTION_THRESHOLD = 0.20` / `MAX = 0.90` 是实现时挑的，spec 里没有。**
  机制符合 §7.4.2（平台设边界），两个数字未经产品确认。
- **一条测试直接调了 `WorkerRuntime` 的两个私有方法**来构造损坏状态。不这么做就只能靠
  真实竞态触发，但它会随 Worker 内部重构而断。
- ~~在线迁移没有演练过~~ — **已演练**（2026-08-30）。把部署库复制成 `th_rehearsal`，
  回退到 0046，把 `run_events` 灌到 500,214 条（127 MB）、`channel_events` 灌到
  200,036 条，再逐个升回 0051：**数据一条不丢**，五个 downgrade 对着真实数据也全部
  跑得通。持锁操作实测：0048 的部分索引 **20 ms**（`WHERE` 只覆盖极少数行），
  0051 在 `run_events` 上重建 CHECK **100 ms**（全表扫描，但扫的是 varchar 列做集合
  比较）。不构成写入中断。

  这一遍**没能**证明：只测到 50 万行——0051 的耗时随行数线性增长，5000 万行约 10 秒，
  那时才需要 `NOT VALID` + `VALIDATE` 的两步写法；**演练时无并发写**，只量到「持锁多久」
  没量到「别人等多久」；数据是复制出来的，`payload` 大小分布不真实。

## 6. 不声称什么

- **不声称压缩能纠正历史里的错话。** 它不能，spec §7.4.2 里也写了这句：阈值下调只是让
  重写历史的机会更早到来，不会让任何一段历史变得更准确。这条分支解决的是「压缩从不
  发生」和「摘要什么都没说」，不是「模型说过的错话会被改正」。
- **不声称模型摘要一定比结构摘要好。** 它更可能有用，但它引入了结构摘要没有的失败方式
  ——蒸馏出一句更短、更权威、更难推翻的错话。上游把这类风险记在案，本设计只做了减轻。
- **不声称阈值 0.50 是经过验证的值。** 它抄自上游默认，没有在本项目的真实会话上测过。
- **不声称复用路径的行为与从前等价。** 它现在**总是**压缩到 `stored.last_sequence`，
  本轮自己的结构边界与已存范围之间的轮次即使还装得下也会被摘要替换——比它取代的搜索
  更激进。这是有意的，符合 §7.4.2 的「摘要文本与它覆盖的消息范围一同持久化」。
- **不声称本机跑绿等于可合并。** 判据是 CI 的 compose-e2e。
