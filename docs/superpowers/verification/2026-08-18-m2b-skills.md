## 3. The roadmap's five exit criteria

### 3.1 An Agent with no skill bound has no summary in its prompt; a bound one has only name and description

`packages/backend/tests/unit/runs/test_skill_request.py::test_an_agent_with_no_skills_sends_no_skill_message`
asserts that the outbound payload of an Agent with no skills carries exactly
two system messages — the safety preamble and the personality — and nothing
else.

`::test_the_summaries_come_after_the_persona_in_a_message_of_their_own` asserts
that a bound Agent's summaries arrive as a third system message, that the
personality does not contain them, and that they are enclosed by the boundary
markers the preamble refers to.

Over the database rather than over a payload:
`packages/backend/tests/integration/runs/test_skill_loading.py::test_the_summary_is_in_the_first_request_and_the_document_is_not`
publishes a real Agent against a real catalog version, runs a real slice, and
asserts the request holds the one-line summary and not the document body.
`::test_the_model_is_never_told_about_a_skill_it_cannot_load` adds a second
skill to the same workspace and asserts the Agent is told nothing about it.

### 3.2 When summaries exceed the segment's `max_tokens`, unmatched ones are removed whole, never truncated

`packages/backend/tests/unit/runs/test_skill_summaries.py`:

- `::test_the_segment_ceiling_removes_whole_summaries_never_part_of_one` — what
  survives is a subset of what was handed in, entry for entry.
- `::test_the_ceiling_takes_the_last_binding_first` — reverse binding order,
  because the order an author wrote their bindings in is a priority statement.
- `::test_a_skill_this_run_already_loaded_is_not_a_candidate` — a skill this Run
  loaded is never removed, so `rollback` goes instead of `audit` even though the
  fixed order would otherwise have reached `audit` last.
- `::test_every_summary_may_be_loaded_and_then_none_of_them_can_go` — a ceiling
  is not permission to remove something the Run is using.
- `::test_a_loaded_document_is_a_tool_result_and_is_trimmed_first` — where the
  *body* lives needs no new code: it is a tool result, so it is in the first
  segment the fixed order touches, and the summary naming it outlives it.

### 3.3 An unapproved `SkillProposal` produces no version; after an approval the old version can still be rolled back to

`packages/backend/tests/unit/skills/test_proposals.py::test_an_unapproved_proposal_produces_no_version`

## 4. Product design §27.2.5, end to end

`tests/e2e/skills.spec.ts`, one walk against the real stack: upload a skill
through the directory picker → bind it to an Agent by version → publish → run
it → `skill_loaded` on the timeline with the sentence saying which document
entered the conversation → a second Agent proposes a change → `skill_proposed`
→ a person opens the difference in the console → approves → version 2 exists —
**and the Agent that proposed the change is still running version 1**.

That last assertion is what the whole stage is for. It needs no check in the
code, because binding by version id is what makes it true; it is asserted
because nothing else would fail if someone later made approval repoint a
binding "helpfully".

## 6. What this run does not prove

**One integration test fails on this host and is not this stage's.**
`tests/integration/sandbox/test_engine_workspace.py::test_execute_feeds_stdin_and_the_helper_writes_atomically`
fails with `TypeError: 'NpipeSocket' object does not support the context
manager protocol` — Docker Desktop's named-pipe transport on Windows, in a file
this branch does not touch. It fails the same way with this branch's changes
stashed. CI runs on Linux sockets.

**The console's vitest suite is only green when files run sequentially.**
Running it with file parallelism on this host fails seven tests that pass
individually and pass sequentially, all with "unable to find" after a wait, in
files this branch does not touch (`App`, `ApiKeys`, `ModelEndpoints`,
`Secrets`). Confirmed pre-existing by re-running with this branch's changes
stashed. It is a contention artefact of this machine, not a result about the
code, and it is recorded rather than hidden because a future reader running
`pnpm test` here will see it too.

**The static scan is not a malicious-content detector.** It finds credential
material and a handful of shapes worth a reviewer's attention. A `SKILL.md`
whose entire content is an instruction to disregard the platform's rules
passes it, and a unit test pins exactly that. What stands between such a
document and the platform is elsewhere and is what should be maintained: skill
text enters the prompt inside boundary markers with the preamble saying it is
reference material, every tool call the model makes afterwards still passes
§16.2's two checks, and a skill grants no tool, no network and no credential.

**Git import covers public HTTPS tarballs and nothing else.** No SSH, no
authentication, no private host unless an administrator has approved its range
through the outbound policy. What is fetched is read as a stream and never
written to disk.

**Skill text in the prompt is still untrusted text.** Nothing in this stage
makes a workspace's document safe to follow; it makes it *legible as a
workspace's document*. The markers and the preamble sentence are a statement to
the model, not an enforcement mechanism, and they are worth exactly what a
model's attention to them is worth.

**A proposal outlives a rolled-back round.** `skill.propose` writes in its own
transaction, because the alternative is holding a write open across a model
round. A round that opened a proposal and was then rolled back leaves the
proposal behind, pointing at a Run whose turn is not in the transcript. That is
the honest side of the trade: a reviewer shown one proposal too many can reject
it; one shown none never learns a suggestion existed.

**The Agent-side ceilings are per Run, and a Session is not a Run.** Eight
loads and one proposal are counted against the Run, so a long Session of many
Runs may load and propose many times. That is the intended reading of §10.1 and
§15.3, and it is what `test_one_run_proposes_once_however_many_times_it_is_worked`
asserts, but it is worth stating rather than discovering.

## 7. Things worth carrying forward

**A trimmable segment was being counted as incompressible content.** The
planner adds skill summaries to `fixed`, and `fixed` fed the floor a round is
measured against — so an Agent that bound thirty skills would have reached
`paused(context_overflow)` while holding a segment the platform is explicitly
allowed to drop. Found by a unit test written to assert the opposite
(`test_a_round_that_is_barely_over_loses_one_summary_and_not_all_of_them`),
which failed on its first run. The floor is now measured with the unhit
summaries already gone.

**A foreign key resolves in whichever process happens to have imported the
table.** `skill_proposals.created_by` points at `users`, and SQLAlchemy
resolves that by name, at flush time, against the shared metadata. The API
imports every table module through its routers and never noticed; the Worker
imports far less, and the first Agent that proposed a skill change met
`NoReferencedTableError` in the middle of answering a tool call. Every backend
suite was green when this happened — it took the end-to-end walk to find it,
which is the clearest argument for the walk this stage has produced.
`skills/infrastructure/tables.py` now names the modules its keys point at, and
`tests/unit/skills/test_table_metadata.py` checks the resolution **in a
subprocess**, because in-process the rest of the suite has already imported
everything and the test would pass no matter what.

**A silent select is worse than a failing one.** The e2e walk chose a model
scenario from an Ant Design select, and when that click did not land the form
kept its default — so the walk published an Agent running `complete`, ran it
successfully, and failed three steps later on a missing timeline event. The
walk now reads the form back before saving it. A test that fails where the
mistake happened is worth more than one that fails where the consequence shows.

**Approval and switching are two acts, and it took writing them down to keep
them apart.** Approving a proposal publishes an immutable version and moves
nothing: not the skill's default for new bindings, not any published Agent's
binding. Both are true by construction, which is exactly why both now have
tests — the code that would break them is the code someone writes to be
helpful.
