# 调度器的会话队首巡检：从每秒 4 秒到每秒 2–5 毫秒

日期 2026-09-30。分支 `feat/capacity-acceptance`，未推送。
- 查询重写：测试 `936d26a`，实现 `143d1b7`；
- 部分索引：测试 `5ac4ef2`，实现 `af221ce`（迁移 0069）。

## 为什么有这一遍

修沙箱准入时发现，Postgres 的 CPU 中位数一直在 101%：
- 被拒循环减少 80% 之后，还是 101%；
- 栈完全空闲、没有任何 Run 的时候，也是 101%。

负载运行中抓了 6 次 `pg_stat_activity`，其中 5 次都在执行同一条语句：调度器的
`sessions_needing_repair`，也就是会话队首巡检（§11.1）。

## 慢在哪里

- 这条查询在本机库上（7534 个会话、7151 个 Run）单次约 4 秒，一个需要修复的会话都没找到。
- `EXPLAIN ANALYZE` 显示，其中一个子查询（「会话里有未结束的 Run，不是队首，而且被阻塞的对象
  不是队首」）引用了外层会话的 `head_run_id`，所以只能逐个会话执行：对 `runs` 做了 7534 次全表
  扫描，每次 0.52 ms，合计 3.96 秒。
- 调度器每秒跑一轮，这条扫描排在等待超时、审批过期、渠道回复派发之前，所以这些事每一轮都要
  先等它跑完。

## 改了什么

**查询重写。**结果不变，只改怎么算：
- 候选会话只取「有队首」或「有未结束 Run」的会话。原来的五个条件，每一个都要求这两者之一，
  所以原来能查出来的会话一定在候选里。
- 「阻塞不对」这个条件改成不依赖外层会话的集合：从未结束的 Run 出发，连接它所在的会话，只算
  一次。子查询里的会话表用了别名；不用别名，SQLAlchemy 会把它自动关联到外层，又变回逐个会话
  执行。

**两个部分索引。**重写之后，扫描不再是平方级，但仍要全表读一遍 `sessions` 和 `runs`，开销随
历史线性增长。
- `runs` 上按会话索引未结束的 Run，`sessions` 上索引有队首的会话；两个索引的大小都只随进行中
  的工作变化。
- 三个终态值以字面量写进 SQL。Postgres 缓存计划之后可能改用通用计划，而通用计划不知道绑定参数
  的值，就没法判断能不能用部分索引。

## 测试过了

- **特性测试（6 条）**：
  - 五种损坏情况各造一个，每一个都要被找出来：缺队首；队首停在最后一个已结束的 Run 上；队首停在
    已结束的 Run 上、后面还有未结束的；队首不是最小的序号；等待中的 Run 没有被队首阻塞。
  - 健康的、空的、已结束的会话，都不能被找出来。
  - 这 6 条在**旧查询上就通过**，作用是保证重写前后结果一致。
- **性能测试**：建 200 个没有未结束 Run 的会话，用 SQLAlchemy 的执行事件截获真正发出的 SQL，
  对它做 `EXPLAIN ANALYZE`，断言任何读 `runs` 的计划节点执行次数都不超过 5 次。旧查询是 201 次，
  所以是红的；新查询通过。
- **索引测试（2 条）**：两个部分索引都存在，条件也正确。
- 调度器、会话协调、公平领取的相关测试 31 条全部通过；单元测试 2500 条通过。
- 迁移 0069 升级、降级、再升级都正常，`alembic check` 没有差异。
- 完整的本机 CI 镜像（在 `af221ce` 上，不含 compose-e2e）全部通过：
  - ruff、pyright 0 errors；单元测试 2500 条；集成测试 1135 条；并发相关测试 ×10；
  - Redis 不可达时的集成测试 1130 条通过、5 条跳过；
  - alembic check 和迁移链；web 测试 391 条、chat 测试 88 条，以及两者的 lint 和 build。

## 走通了什么

**测试库里 30 万个已结束的会话和 Run**（从一个模板克隆出来，只有 2 个 Run 没结束），连跑 12 次：

| | 稳定后单次耗时 | 执行计划 |
|---|---:|---|
| 有部分索引 | 约 2 ms | 全部走两个部分索引 |
| 没有索引（临时删掉） | 约 40 ms | 对 `runs` 和 `sessions` 并行全表扫描 |

- 跑了 12 次，超过 asyncpg 第 5 次执行之后，照样走索引。
- 实际发出的 SQL 里三个终态值是字面量，唯一的绑定参数是 limit。
- 旧查询在这个数据量下没有跑：它是平方级的，本机 7534 个会话时已经要 4 秒。

**本机栈**（7534 个会话，重建后迁移到 0069）：

| | 修复前 | 修复后 |
|---|---:|---:|
| 单次扫描 | 约 4000 ms | 2–5 ms |
| 空闲时 Postgres CPU | 101% | 1–4% |
| 沙箱准入那个负载场景下，Postgres CPU 中位数 / P90 | 101% / 114% | 8% / 17% |

同一负载场景：474/474 完成，短消息排队 P95 0.0 秒，没有死锁、没有报错栈，VM 最多用 45%。

## 这一遍没能证明什么

- **调度器的其他扫描没有逐一审查。**空闲时 Postgres 只剩 1–4%，说明在本机的数据量下它们都
  不贵；但其中有没有别的全表扫描、到几千万行时会不会成问题，没有查。
- 30 万行的数据是从一个模板克隆出来的，所有会话都一模一样。真实数据的分布不同，计划的选择
  可能也不同。
- 在已有大量数据的库上建这两个索引，迁移时会锁表写入一段时间；没有用 `CREATE INDEX
  CONCURRENTLY`，也没有测在大表上建索引要多久。
- 负载场景只跑了一遍。

## 不声称什么

- 不声称调度器的每一轮在任何数据量下都是毫秒级的，只声称这一条扫描是。
- 不声称这两个索引对其他查询没有影响。它们会增加写 `runs` 和 `sessions` 时的开销，这一点
  没有单独测量。
