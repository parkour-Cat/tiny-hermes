# 主体数据权利：一条「报告成功但什么都没做」的擦除 — 2026-08-23

> 产品：v2.5 §4.6「本人会话与私有记忆的查看、更正、删除和导出」、§344、§348。
> 起因：M3 路由可达性普查里「管理员代终端用户导出/擦除/更正」那一条。

## 1. 本来要做的只是「补个界面」

`/api/v1/subjects/{id}/export|erase` 和 `/subjects/memories/{id}/correct|forget`
四条路由都在,两个控制台都没有引用。原计划就是给它们加一个页面。

加之前先问了一个问题:**管理员从哪儿拿到那个 `subject_id`?** `end_users.id` 是平台
自己铸的 uuid,而请求是以「目录里叫 alice@example.com 的这个人」的形式来的。没有
任何地方能把后者换成前者——所以那四条路由**只能靠手工读数据库才够得着**,等于够不着。

于是加了 `GET /api/v1/subjects/lookup?channel=&external_user_id=`。

刻意做成**查找**而不是**列表**:「这个工作空间有哪些终端用户」是另一个问题、另一种
披露,§4.6 没有授予它;处理一份请求只需要回答被点名的那一个人。

## 2. 然后发现路由本身是坏的

`subject_routes.py` 里:

```python
return CallerIdentity(caller_type=CallerType.USER, caller_id=subject_id)
```

写死成 `USER`。它的 docstring 还为此辩护过:这个 router 是 `_CONSOLE_ONLY`,终端用户
不会调到它。**这句话是对的,而且答非所问**——调用者是谁,和数据属于谁,是两件事;
而 §4.6 的「代办」那一行,问的正是后者。

实测(管理员擦除一个有一条私有记忆的终端用户):

```
status=200  report={"memories":0,"sessions":0,"messages":0,"artifacts":0}
memories_left=1   erased_at=None
```

删除语句按 `caller_type='user'` 匹配,而那些行是 `'end_user'`,一条也匹配不到;
`erased_at` 没被设置,所以那个人下次拿同一份凭据回来还会被认成原来的自己(§344
靠这一列拦)。**一次声称发生过、实际没发生的擦除,比一次失败的擦除更糟。**

同一个写死的类型也让代为导出返回空——「我们没有关于你的任何记录」,而其实有。

## 3. 修法

主体类型**由 id 解析**,不再假设:`subject_type_of()` 先查 `end_users`,再查
`memberships`。两张表各铸各的 uuid,一个 id 至多属于其中一张,所以这不是猜。

工作空间成员按**成员关系**判定而不是按 `users` 表:`users` 是实例级的,如果对一个
不属于本空间的人回答 `user`,就等于让一个空间的管理员能操作另一个空间的成员。

**解析不到就 404,不再回一份全 0 的报告。**「什么都没删,因为本来就没有」和
「什么都没删,因为这个 id 根本不是主体」是两回事,而管理员要先知道是哪一种,
才能回复提出请求的那个人。

## 4. 为什么原来的测试是绿的

`test_subject_erasure.py` 用 `session_for(...)` 建会话——那是**控制台**会话,
`caller_type='user'`,主体是工作空间成员。写死成 `USER` 对它恰好是对的。

整个套件里没有一条测试让管理员去擦除一个**终端用户**,而那正是 §344 的擦除故事
从头到尾在讲的那种主体。

## 5. 这一遍没能证明什么

- **没有走过真实的终端用户凭据登录路径**。新测试直接往 `end_users` 和
  `external_identities` 里种行,这对查找和类型解析是充分的,但没有证明真实登录
  写进去的行长得和种的一样。
- **`forget` 与 `correct` 只在控制台侧有测试**,后端那两条路由的行为是既有测试
  覆盖的,这一遍没有新增对它们的后端断言。
- **没有量过体量**:一个有几千条记忆的主体,导出页面会一次全渲染。
- **chat-web 的逐条更正/删除没有做**,终端用户目前仍然只有「全部导出」和
  「全部擦除」。§4.6 给了终端用户「更正」,那是下一条。
