# 两小时长任务压测

日期 2026-10-24。本机 Compose 栈，scheduler 用的是并发扫描这一版（分支 `perf/scheduler-concurrent-scans`）。

## 怎么跑的

- 确定性模型，每轮固定等 5 秒（`DETERMINISTIC_MODEL_DELAY_MS=5000`，上限就是 5000）。
- 一个 Agent，带 `shell.exec`，要求跑 998 轮，每轮调用一次工具。
- 工作区限额设为执行 7200 秒、1000 次调用；`AGENT_CEILING_MODEL_CALLS` 和 `AGENT_MAX_TOOL_CALLS` 临时调到 1000。
- 每 5 分钟记录一次 Run 的状态和计数。跑完后这些设置都改回了默认值。

## 结果

| 项目 | 数值 |
|---|---|
| 最终状态 | `completed` |
| 模型轮数 / 工具调用 | 999 / 998，工具失败 0 |
| 切片（租约） | 168 |
| 被打断 / 恢复 | 1 / 1（见下） |
| 沙箱缓存重置 | 2（开始一次，恢复时一次） |
| 墙钟时间 | 1 小时 44 分，其中约 17.5 分钟卡在下面的问题上 |
| 记账的执行时间 | 约 4770 秒，没有超过 7200 秒的限额 |
| scheduler 扫描失败 | 1 次（见下），其余全部成功 |

### 被打断的那一次：压测找到的缺陷

第 139 轮（15:41）时，本机同时在跑集成测试。测试里的 controller 和压测栈共用一个 Docker，清扫时把压测的
沙箱（容器和数据卷）当成没有记录的删掉了。Run 租约过期被打断，之后每次清理都在 Docker 的 404 上失败，
17 分钟里失败了 246 次，Run 恢复不了。修复在 #146。部署修好的 controller 后约 30 秒，Run 自动恢复，
从第 139 轮接着跑完。

### 那一次扫描失败：已有的竞争，不是并发扫描引入的

15:35:23，`collect_upload_garbage` 失败，报 `UploadStateConflict: upload ... is committed`。这个工作区
上传在 23.70 秒创建，23.79 秒提交，23.82 秒 scheduler 来清理。提交方（`committer.py`）自己会清掉暂存区，
scheduler 的清理也会去清，两边在这 0.1 秒里撞上，后到的一方失败。失败本身没有造成损失，但它让这一项
扫描记成失败，这一批里剩下的上传也被跳过。这段代码从 8 月就是这样，和这次的改动无关，**没有修**，
列为待办。

## 这一遍没能证明什么

- 只有一个 Run，没有多个长任务同时跑；也没有用真实模型。
- 每轮的工具调用只是很短的 shell 命令（全部工具执行加起来约 45 秒），没有测长时间运行的命令、大的工作区。
- 中途打断的原因是外部删了沙箱，恢复走的是这一条路径；worker 或 controller 进程崩溃后的恢复没有在这次
  压测里发生。

## 不声称什么

- 不声称两小时以上的任务都没问题：执行时间预算在 7200 秒，这次用了约 4770 秒。
