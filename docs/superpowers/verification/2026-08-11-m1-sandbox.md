## 4. What is asserted from the created container

The integration suite uses Docker inspect and real commands against the created
container; it does not merely inspect the arguments passed to docker-py. It
proves:

- numeric non-root user;
- read-only root filesystem;
- network mode `none`, with DNS and literal-address connection attempts both
  failing;
- all Linux capabilities dropped and `no-new-privileges` present;
- CPU, memory, process, and temporary-space ceilings applied;
- `/` is not writable and `/workspace/data` is writable;
- two commands in one live instance share one `boot_id`;
- an unapproved image is refused before Docker is called;
- no host path can be represented by the stored sandbox schema.

The declared `disk_mb` limit is not enforced in phase 3B. Docker's writable-layer
quota does not cover the named volumes where commands actually write and is not
portable across runner filesystems. The test names this gap explicitly; this
record does not turn the declared number into an enforcement claim.

## 7. Redacted failure evidence and fixes

1. **The Controller socket was too private for the platform itself.** It was
   root-owned `0660`; Worker and Scheduler run as `10001:10001`. The Controller
   now assigns the socket to the platform process group while keeping it not
   world-writable.

2. **A transport adapter returned refusal reasons as strings.** In-process code
   compared an enum, so the deployed Unix-socket path silently missed
   `already_reserved`. The adapter now restores the domain enum, with a test.

3. **Expired Worker leases did not reclaim active reservations.** The Scheduler
   scanned only kept and isolated reservations. It now isolates the active
   sandbox left by the expired lease, destroys it, and only then requeues the
   Run. A regression test records `sandbox_destroyed` before `run_requeued`.

4. **The first fourth scenario did not execute a tool.** `continue_once` never
   asks for one. The deterministic `shell_once` scenario requests a real command
   containing `sleep 20` and only completes after reading `drill-finished` from
   the tool result.

5. **The observer hid its own Docker error.** `docker top -eo args` is rejected
   by Docker Desktop because the result omits PID. The script saw empty stdout,
   ignored the error, and later reported zero containers. It now requests
   `pid,args`, checks `docker ps` failures, preserves `docker top` errors, and
   has two unit regressions.

6. **Ambient HTTP proxies replaced vetted connections.** The full suite returned
   non-platform 502 responses for local stand-ins. `SafeOutboundClient` now uses
   `trust_env=False`; a test installs a bad ambient proxy and still requires a
   direct connection to the address the platform checked.

7. **A create response could outrun its commit.** The drill created a Session,
   received 201, and immediately got `session_not_found` while creating its Run;
   the Session appeared in PostgreSQL moments later. All database transaction
   dependencies now use FastAPI function scope, which commits before sending
   the response. A route-structure regression covers all five transactional
   dependency families, and the rebuilt four-scenario drill passed the rapid
   sequence.

8. **A failed sandbox cleanup could cause a recovery loop or a permanent
   interruption.** Recovery now first turns every live reservation left by an
   interrupted Run into an isolated cleanup candidate. The Scheduler confirms
   the old container is gone before it returns the Run to the queue. A real
   Worker-path regression covers destroy failure leaving an `active`
   reservation, while another regression keeps the Run interrupted when Docker
   cleanup still cannot be confirmed.

9. **A failed socket group change was ignored.** The Controller used to catch
   every operating-system error while assigning the platform group to its
   socket. It could therefore report a successful startup while no Worker could
   connect. Only a missing stale socket is ignored now; `chown` failure aborts
   startup and has a unit regression.
