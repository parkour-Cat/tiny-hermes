# 出站范围那条偶发的 e2e：断言在两张列表里找同一个主机

日期 2026-10-21。分支 `fix/flaky-outbound-e2e`。测试 `dae693f`，实现 `43a86d7`。

## 现象

`tests/e2e/tools.spec.ts` 的 `approveHost` 偶发失败，main 上 9-27、10-01 各一次，PR #113 的
push 那次 CI 又一次（同一提交的 pull_request 那次通过，重跑也通过）：

```
strict mode violation: getByRole('region', { name: '出站范围' }).getByText('api', { exact: true })
resolved to 2 elements
```

## 原因

失败时的页面快照（CI 的 playwright-report）里，「设置 → 出站范围」上有两张列表：

- 「平台批准」：上一步在平台管理里批准的 `api`，**一打开就在**；
- 「本工作空间」：这一步刚批准的 `api`。

断言在整个「出站范围」区域里找 `api`，所以：

- 平台列表先加载好、工作空间的批准还没落地时，它找到**一个**——平台那个——就通过了。
  **这时它根本没有检查工作空间的批准。**
- 平台列表加载得慢（卡片在 loading 时不渲染内容），等它出来时工作空间那条也到了，
  就找到两个，strict mode 报错。

所以通过的那些次也不是在验这一步。

## 改了什么

- 前端：两张卡片各是一个以自己标题命名的 region（「平台批准」「本工作空间」）。
  同一个目标常常同时出现在两层里，只有所在的列表能说明它属于哪一层——读屏用户也一样。
- e2e：每一层的表单和断言都限定在那一层自己的 region 里。
- 单元测试：两层都有 `api` 时，各自的 region 里各找到一个。先提交、先看它红
  （`Unable to find role="region" and name "平台批准"`）。

## 测试过了

- `OutboundScopePage.test.tsx` 7 条通过；tsc 无错。
- 本机栈（重建了 web 镜像）单跑 `--project tools`，连续 3 遍通过。

## 走通了什么

本机那 3 遍都走完了整条工具链：两层批准 → 注册 HTTP 工具 → 调用拿到 HTTP 200 → 写操作
停下 → 人批准 → Run 完成。

本机要跑这条，`OUTBOUND_ALLOWED_CIDRS` 得是 `192.168.0.0/16`：OrbStack 的 Compose 网络在
192.168.x，CI 用的 `172.16.0.0/12` 覆盖不到，代理会以 `reason=private` 拒绝。这是本机网络
的事，没有改 CI 的值。跑完已恢复成不设这两个变量。

## 这一遍没能证明什么

- **没有在本机复现原来的失败。**它取决于两次请求谁先到，本机没压出来过；原因来自 CI 那次的
  页面快照和对代码的推理，不是现场复现。
- 3 遍通过只说明新定位器在真实页面上找得到，不说明它不会再偶发——以后 CI 上再出现，
  得看是不是别的原因。
- 本机前端单元测试全量跑有 `SkillsPage.test.tsx` 2 条失败，main 上（不带这次改动）一样失败，
  而 CI 的 web 任务是绿的。本机 `node_modules` 装于 8-20，早于最近一次 lockfile 变更，
  Node 是 23（CI 是 24.6）。没有查下去。

## 不声称什么

- 不声称这是 e2e 里唯一一处「在整页范围里按文字找」的断言，没有排查别的 spec。
- 不声称加 region 改善了读屏体验——只是给了两张列表可区分的名字，没有用读屏器试过。
