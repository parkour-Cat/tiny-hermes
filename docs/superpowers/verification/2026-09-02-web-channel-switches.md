# 控制台能开起网页渠道了 — 2026-09-02

> 由来：飞书长连接那条分支合并后走查网页渠道，撞上两堵墙，两堵都是**后端支持、
> 控制台没有**。见 `2026-08-31-feishu-long-connection.md` §6.3。

## 1. 做了什么

1. **签发方表单二选一**（`ChannelsPage.tsx`）：「从 JWKS 地址读取 / 直接贴公钥」，
   提交时**只发选中的那一半**。后端 `end_user_service.py:284/288` 对「两个都不给」
   和「两个都给」都返回 400，所以一个 `jwks_url: ""` 不是多余字段，是会被拒绝的
   第二份验签材料。
2. **Agent 详情页加「允许终端用户访问」开关**（`AgentDetailPage.tsx`）。
   只有开着才写 `end_user_access` 这个键；关着**整个键不写**——`models.py:796-799`
   的规范化把 `None` 弹掉，写成 `{enabled: false}` 会让每一个从没开过这个入口的
   Agent 内容哈希都动一次。

## 3. 真机走查：这一遍才是验收

**全程只用控制台，没有碰过一次 SQL。**这正是上一次走查做不到的那件事。

| 步骤 | 谁做的 | 证据 |
| --- | --- | --- |
| 注册签发方（贴公钥） | 人在控制台点 | 库里 `public_key` 非空、`jwks_url` 为空 |
| 打开 Agent 的终端用户访问 | 人在控制台点 | `spec->'end_user_access'` = `{"enabled": true}` |
| 企业签票 → 进聊天页 | 企业侧（本该如此） | 会话建成功 |
| 发消息 → Run 完成 → 回复显示 | — | Run `completed`，`notes-tidier` 真的回了话 |

（走查用的临时签发方是这次新注册的那一个；私钥和脚本已销毁。）

## 4. 这一遍没能证明什么

- **没有验过 JWKS 那条路真的能拉取并验签。**这次走的是公钥那条；JWKS 分支只被
  既有测试覆盖，没有对着一个真实的 JWKS 端点跑过。
- **没有验过后端对「两个都给」的拒绝在界面上长什么样。**前端现在只发一个，所以
  那条 400 走不到；它由后端自己的测试守着。
- **没有跑 compose-e2e**，也没有跑后端套件——这条分支一个后端文件都没碰。
- 没有验过英文界面（只看了中文）。

## 5. 不声称什么

- **不声称网页渠道现在「开箱可用」。**它仍然需要企业侧有一个能签名的服务，
  以及有人把票带进链接里。控制台补上的是**平台这一侧**原本缺的两步。
- **不声称这两处是控制台唯一缺的开关。**这一遍只覆盖了走查真正撞到的两堵墙；
  没有系统性地把「后端支持而界面没有」的字段清点一遍。
- **不声称聊天页的轮询有问题。**走查中一度以为它坏了（运行状态只查一次、界面
  卡在「正在回复」），查证后是**观察方式的问题**：自动浏览器面板一直隐藏，
  react-query 失焦时暂停 `refetchInterval`，而真实用户要么在前台每秒轮询、
  要么切回来时靠 `refetchOnWindowFocus` 自动重拉。**没有改任何东西。**
