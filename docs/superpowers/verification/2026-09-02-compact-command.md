# `/compact`：让人自己决定什么时候压缩 — 2026-09-02

> 由来：查参照实现（`NousResearch/hermes-agent` @ `3f83297`）时看到它有
> `/compress`（别名 `/compact`），而我们只有 `/undo`、`/new`。

## 1. 关键的产品决定：打标记，不立即压

`/compact` 和现有两个命令的形状不一样：`/undo`、`/new` 都是纯数据操作，而**压缩
必然要一次模型调用**。

选的是「命令打标记、下一轮生效」，而不是「命令路径直接调模型」。理由是这个仓库
已有的先例——被挡通知是「在这里**记下**、不在这里**发**」，因为一次入站投递不该
依赖外部服务可达。压缩同理：模型超时会变成投递失败和飞书重投六小时。

**功能上这不是打折的版本**：压缩发生在下一轮**开始之前**，也就是在用户下一条消息
被回答之前。用户想要的正是这个。差别只在回执的措辞。

## 2. 四层，任何一层断了都是「写进去了没人够得着」

| 层 | 做什么 |
| --- | --- |
| `channels/domain/commands.py` | 认 `/compact`、`/compress`，不收参数 |
| `channels/application/ingestion.py` | 打标记、给回执，**不建 Run、不撤回、不调模型** |
| `runs/infrastructure/sql_store.py` | 写标记 + 回答「这段会话有没有可压的」 |
| `runs/application/worker.py` | **读走标记 + 把阈值强制成 0** |

最后一层才是让它生效的那一层。前三层做完而第四层没做，就是这个仓库最常见的那种
bug——标记写进数据库，压缩永远不发生，而且后端测试全绿。

## 3. 测试

判据是 `CONTEXT_COMPACTED` 事件，**不是 `sessions.compaction_requested_at` 有没有值**。
照的是同文件里那条既有测试立的规矩：

> `plan_context` 被传了一个数字只证明有人调用过它，事件被写出来才证明那个数字真的
> 改变了这一轮。

入站那两条断言「没有 Run」和「没有撤回」，不只是「打了标记」——一个既打标记又顺手
提交了 Run 的实现也会让后者为真。

```

pytest packages/backend/tests/integration    983 passed（含 sandbox）
ruff / pyright                               干净
alembic check                                No new upgrade operations detected
```

**写测试时有一条先「绿」了，是走错了路径**：默认 fixture 故意不给会话，所以那条
测试测到的是「陌生人第一条消息不建会话」那条早退分支，压缩这段代码根本没走到。
补上会话之后才真的红。这一条值得记：**一条从没红过的测试，不能算守着什么。**

## 4. 这一遍没能证明什么

- **没有真机走查。**没有人在飞书里发过一条 `/compact` 然后看到回执、再发一条消息
  看到压缩发生。整条链路的证据来自集成测试，不是真实渠道。
- **回执的措辞没有被人读过。**「记下了。下一条消息之前，会先把这段对话的旧历史
  压成摘要。」——这句话是否让用户明白「不是现在压」，没有验证过。
- **没有验证过并发**：两轮同时开跑时只有一轮拿得到标记，靠的是 `RETURNING` 的
  单语句读+清，但没有一条测试真的并发跑过两轮。
- **控制台/聊天页没有这个命令的任何提示。**用户只能靠知道它存在才用得上。

## 5. 不声称什么

- **不声称 `/compact` 能立刻压缩。**它打标记，压缩在下一轮开始前发生。回执如实说了
  这件事。
- **不声称它一定会压出东西。**历史不够长时没有可压缩的内容，那时什么也不会发生——
  回执在命令当时就会说「这段对话还不长」，判断由 store 给（只有它知道会话多长），
  不是这一层猜的。
- **不声称标记会一直等到压得动为止。**它在下一轮被无条件清掉，压没压成都一样。
  留着它会让一段短对话背着一个几周后突然生效的请求。
