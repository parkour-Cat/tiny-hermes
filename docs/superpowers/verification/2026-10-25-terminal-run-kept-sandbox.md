# Run 结束时，前一片保留的沙箱一并销毁

日期 2026-10-25。分支 `fix/terminal-run-kept-sandbox`。由第一次真实模型长任务（`ledger` 中等规模，DeepSeek）发现。

## 问题

产品设计 §1526 要求：进入 `waiting_*`、`paused` 或任何终态时**不保温**，必须销毁实例并结束保留关系；§1166 也保证这几个状态下
不持有 SandboxReservation。

真实模型的那次 Run：
- 第一片：写测试、写代码、跑测试，结束时沙箱被冻结并保留，`kept` 到 11:52:23；
- 第二片：模型只给出最终回答，没有调用工具，所以没有打开沙箱；
- Run 在 11:47:24 变成 `completed`，沙箱却一直保留，到 11:52:30 才被 scheduler 按空闲期回收。

worker 只在「这一片打开过沙箱」时才处理沙箱，前一片留下的那个它看不见。确定性测试的最后一轮总会用到沙箱，所以一直没碰上。

## 改了什么

worker 在这一片**没有**沙箱、但 Run 要离开运行状态时，去查这个 Run 有没有 `kept` 状态的预约，有就销毁。

- **覆盖的路径：**
  - `_close_sandbox`（主循环、压缩完成、上下文溢出、费用上限这几处）；
  - `_fail`（5 个调用方）；
  - 工具清单超出预算时的暂停。
- **销毁不能确认时：** 和这一片自己持有沙箱时一样，Run 进入 `interrupted`，不报完成。
- **不处理的情况：**
  - 切片正常切换（`SLICE_ENDED`）时，保留的沙箱照旧留给下一片，这正是保留的用途；
  - `isolated` 的预约由 scheduler 负责清理，worker 不碰。

## 测试过了

- 集成测试，背后是真实的预约行：Run 带着一个 `kept` 的沙箱，这一片模型直接回答。
  - 正常情况：Run 完成，那个沙箱被销毁，预约释放；
  - 销毁失败：Run 变成 `interrupted`，预约仍是 `kept`，交给 scheduler；
  - **改之前两条都失败。**
- `test_scheduler_sandboxes.py` 13 passed；单元测试 2767 passed；非沙箱集成测试 1139 passed。

## 这一遍没能证明什么

- 测试里的 controller 是替身（它释放预约的方式和真实 controller 一样）；真实栈上这条路径要靠接下来的长任务再观察一次。
- 每次「没有沙箱的切片让 Run 离开运行状态」会多一次数据库查询，量很小，没有测性能。

## 不声称什么

- 不声称所有让 Run 离开运行状态的路径都覆盖了：我逐个找了 worker 里记录这类决定的地方，没有找到别的，但没有
  机械地证明。
