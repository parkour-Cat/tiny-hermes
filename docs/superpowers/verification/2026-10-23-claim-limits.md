# 交互优先领取与并发上限

日期 2026-10-23。分支 `feat/claim-limits`（基于 `feat/sandbox-networks`）。产品设计 v2.21 §1.21
第 2、3 条；设计：[领取顺序与并发上限](../specs/2026-10-23-claim-limits-design.md)；运维手册 §15。

| 改了什么 | 测试 | 实现 |
|---|---|---|
| 交互 Run 先领；后台 Run 等太久升级；每人、每工作空间的执行上限；并发领取时加锁重数 | `81c57b3`、`f1c624b`、`c266be2` | `a608745` |
| 压测探针 `--channels`；两个新设置进 Compose | 无（工具） | `257c120` |

## 为什么有这一遍

[单机档验收](2026-09-30-tier-a-acceptance.md)的第 3 档：长任务占满通道时，员工发的短消息排队
P95 31.6 秒，因为所有 Run 先到先得。同时没有任何上限：一个人开 10 个长任务，就占 10 份执行通道。

## 怎么做的

都改在 Worker 领取 Run 的那一条查询上：

- **排序**：交互的在前。交互指同步 Chat Completions，或者会话发起人是终端用户，并且不是子 Run。
  排队超过 `RUN_INTERACTIVE_PROMOTION_SECONDS` 的后台 Run 也按交互排。同一类里仍然先到先得。
- **排除已满的**：
  - 发起人（用户或终端用户）在这个工作空间里正在执行的 Run 数，已经达到上限的不领。上限是
    工作空间的 `max_running_runs_per_caller`，没设就用 `RUN_LIMIT_PER_CALLER`；
  - 工作空间整体达到 `max_running_runs` 的也不领；
  - 服务账号只受工作空间的上限约束。
- **并发领取不超额**：选出候选后，按工作空间、再按发起人，取事务级 advisory lock，锁住后重数。
  超了就把这个人或工作空间排除，换下一个候选，最多 5 次。

## 测试过了

- 后端单元测试 2690 passed；集成测试（含 sandbox 目录）**1274 passed、1 skipped、1 error**：
  - error 的是 `test_waiting_run.py::test_a_terminal_run_behind_it_is_not_waiting`，出错的阶段
    是 setup 或 teardown；
  - 单独重跑那个文件两次，都是 9 passed；
  - 没有查清原因，以 CI 为准。
- pyright 0 errors（全量跑完后修了测试里一处类型问题，重跑了 `test_claim_order` 和 pyright）。
- 新测试（真实数据库，都经过 `claim_head`）：
  - 终端用户会话里的 Run，比更早排队的后台 Run 先领；
  - 同步补全的 Run 同样先领；
  - 子 Run 即使在终端用户会话里，也按后台排；
  - 后台 Run 排队超过阈值后，排到交互 Run 前面；
  - 同一类里先到先得；
  - 一个人有 3 个在执行时，他的第 4 个不领，别人的照常领；队列里只剩他的时，返回空，不报错；
  - 他的一个结束后，第 4 个被领；
  - 服务账号不受每人上限约束；
  - 工作空间上限同样生效，工作空间也可以单独设每人上限；
  - **9 个并发领取同一个人的 Run，结果正好 3 个在执行**。

## 走通了什么

本机 Compose 栈，重建到这个分支。1 个 worker × 4 条通道，模型延迟 3 秒。8 个长任务（每个 15 轮，
带工具）先占满通道，之后每 2 秒来一条短消息，持续 60 秒。同一套代码跑两次：

| | 改动前的行为 | 改动后 |
|---|---|---|
| 怎么跑的 | 每人上限调到 1000，所有 Run 都是同一个控制台用户的后台 Run：等于原来的先到先得 | 默认上限 3，`--channels`：短消息是各自不同的终端用户（交互），长任务是各自不同的服务账号（后台） |
| 短消息排队 P50 / P95 / 最大 | 33.2 / 39.2 / 40.5 秒 | **6.0 / 10.9 / 11.5 秒** |
| 短消息端到端 P95 | 42.2 秒 | **13.9 秒** |
| 长任务端到端 P95 | 136.1 秒 | 136.8 秒 |
| 长任务排队最大 | 12.8 秒 | 38.4 秒 |
| 完成 / 失败 | 38 / 0 | 38 / 0 |

短消息的等待降到原来的大约四分之一，长任务的总时长没有变。代价是长任务每次重新排队时，要让
短消息先走，单次排队的最大值从 12.8 秒变成 38.4 秒。

短消息仍然要等 6 到 11 秒，因为 4 条通道都被长任务占着。交互优先只决定「下一个空出来的通道给
谁」，不会打断正在执行的时间片。要再短，靠加通道或者缩短时间片（`WORKER_MAX_SLICE_SECONDS`）。

测完之后栈已恢复成 `.env` 的配置。

## 这一遍没能证明什么

- **「改动前」不是旧代码，是新代码把上限调高、不标入口。**两者在排序上等价（所有 Run 都是后台、
  按时间排），但不是同一份代码。
- 探针用 SQL 把会话改成终端用户或服务账号，来模拟入口。没有用真实的 Web Chat 或飞书消息测。
- 「每人上限」在真实的多人场景下没有测。测试里是用 SQL 构造的。
- 工作空间设置只能用 SQL 改，没有界面，也没有 API。
- 领取查询多了两个相关子查询和最多两把 advisory lock。没有在大队列下量领取的耗时。
- 后台 Run 升级的阈值固定为 120 秒，没有验证它在长期负载下的效果。

## 不声称什么

- 不声称交互消息不再排队。它不再排在后台任务后面，但仍要等一条通道空出来。
- 不声称这些上限防得住恶意的大量提交。上限管的是同时执行的 Run，不管排队的数量。
