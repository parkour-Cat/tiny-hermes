# 沙箱在准入锁外创建

日期 2026-10-24。分支 `feat/sandbox-create-outside-lock`。[设计](../specs/2026-10-24-sandbox-creation-outside-lock-design.md)，
产品设计 v2.24（§1.24、§21.3）。

## 为什么有这一遍

原本打算做「数据库是下一个瓶颈」。先打开 `pg_stat_statements`，用确定性模型测了两档：

| | 40 个长任务 + 每秒 1 个短任务 | 120 个长任务 + 每秒 2 个短任务 |
|---|---|---|
| Worker | 3 个 × 16 条通道 | 4 个 × 32 条通道 |
| 同时执行 | 最多 42 | 最多 124 |
| Postgres CPU 平均 / 最高 | 36% / 88% | 62% / 157% |
| Worker 进程 CPU | — | 每个 90% 到 95% |
| 准入锁：加锁次数 / 等待合计 / 平均每次 | 40 / 80.7 s / 2.0 s | 120 / 320 s / 2.7 s |

8 核的机器上，124 个任务同时执行时 Postgres 只用了 1.6 个核，**还不是瓶颈**。最耗数据库时间的
语句是准入锁：同一台主机上的 `acquire` 拿着锁建完容器才放，新沙箱是一个接一个建的。所以先做这个，
数据库的优化（每一轮约 65 个事务、270 条语句，一半是只读后回滚的事务）往后放。

## 做了什么

- acquire 分三段：在准入锁里检查内存、写下 `creating` 状态的实例和 reservation，**提交并放锁**；
  在锁外清旧容器和卷、建卷、网络和容器；最后写上容器编号，状态改为 `running`。
- controller 新增可选的 `commit` 回调，socket 分派把会话的 `commit` 传进去。
- 建造失败：删掉已建的部分，实例标为 `destroyed`，释放 reservation，自己提交（分派层遇到非拒绝类的
  异常会回滚），再把异常抛出去。
- 建造中途崩溃：留下的 `creating` 实例由现有的租约过期流程回收；`cleanup` 时如果没有容器编号，就按
  实例标签找到容器来删。
- 清扫把 `creating` 实例算作「有记录」。
- 迁移 0080：`container_id` 可空，状态加 `creating`。

## 测试过了

- 集成测试（真 Docker、真 Postgres），建容器加了 1 秒的固定延迟：
  - 两个 acquire 同时进行，总耗时小于 1.8 秒（排队的话至少 2 秒）。**改之前这一条失败，改之后通过。**
  - 预算只够一个时，两个同时申请，仍然只有一个成功，另一个被拒绝为 `memory_budget_exhausted`。
  - 建容器失败：什么也不留下，已预约内存回到 0，reservation 被释放，之后再申请可以成功。
  - 模拟建容器之后 controller 崩溃：实例停在 `creating`，清扫不删它的容器；对它 `cleanup`，按标签删掉
    容器，实例变为 `destroyed`，已预约内存回到 0。
- `alembic upgrade head`、`downgrade -1`、再 `upgrade head` 都通过，`alembic check` 没有差异。
- 已有测试里两个返回容器编号的辅助函数和单元测试的假 store 按新的类型改了。
- 先写测试、看它失败、再实现，提交顺序是测试在前。

全量（本地）：单元 2752 passed；集成 1333 passed、1 skipped。

### 前后对比（同一台机器、同一套负载：120 个长任务 + 每秒 2 个短任务，4 个 Worker × 32 条通道）

| | 改之前 | 改之后 |
|---|---:|---:|
| 准入锁平均每次等待 | 2669 ms | **162 ms** |
| 准入锁等待合计 | 320 s | 19 s |
| 长任务端到端 P50 / P95 | 116.0 / 121.3 s | **91.9 / 98.8 s** |
| 吞吐 | 1.90 个/秒 | 2.26 个/秒 |
| Postgres CPU 平均 / 最高 | 62% / 157% | 56% / 118% |
| 全部语句执行时间合计 | 370 s | 49 s |
| 完成 | 240/240 | 240/240 |

全部语句执行时间的合计大幅下降，主要是因为准入锁的等待算在 `pg_advisory_xact_lock` 这条语句的执行
时间里，它从 320 秒降到了 19 秒。

## 这一遍没能证明什么

- 每档只跑了一次。机器是 8 核 / 7.8 GiB 的 OrbStack VM，不是参考机。
- 用的是确定性模型和每轮一条 `printf` 的工具；真实工具的容器启动时间、镜像大小不同，提升幅度会不同。
- Docker 守护进程同时建多少个容器才会变慢，没有测。
- 中途崩溃只在测试里模拟过（建完容器后抛出一个不被捕获的异常），没有真的杀掉 controller 进程。
- 沙箱内存预算临时调到 40000 MB，只是为了让 120 个任务都能同时拿到沙箱；它们每个实际只用几 MiB。

## 不声称什么

- 不声称数据库已经不是问题：它在这台机器、这个负载下还有余量，但每一轮的数据库来回次数仍然很多。
