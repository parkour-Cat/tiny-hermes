# 飞书里收发文件，真飞书走查（v2.27）

日期 2026-10-26。设计见 [办公任务设计](../specs/2026-10-25-office-tasks-design.md)，其中「只有文件的消息」和「同一个人几乎同时发来的消息合成一个 Run」两节是这次走查的产物。

## 跑了什么

- **栈：** 本机 Compose 全栈，分支 `feat/office-tasks`，迁移到 `20261026_0083`。沙箱是办公镜像 `sha256:37882bab…`，runc。
- **飞书：** 真实的企业自建应用，长连接，开了 `im:resource` 和 `im:message:send_as_bot`。一个真人在飞书客户端里发消息。
- **模型：** DeepSeek。Agent「Notes tidier」，设定从 v5 改到 v6（见下）。
- **材料：** 一张 200 行的订单表 `2026年9月办公用品订单.xlsx`，用固定种子生成，标准答案事先算好；一个 211 字节的 `reference.txt`；一个 17 MB 的随机字节文件。

## 这条路走得通（最后一轮，`3d35a75` 部署后）

| 发了什么 | 看到了什么 | 依据 |
|---|---|---|
| `/new`，然后「这个文件里的内容是什么」和 `reference.txt` 一起发 | 文字比文件早到 0.35 秒，合成一个 Run，文件放进 inbox，只回答一次，复述的四行数字全对 | `channel_events` 两行同一个 `held_taken_at`，Run `81089606` 有 `attachment_placed`（211 字节） |
| 只发 xlsx | 4.3 秒后平台发出一条消息，没有开 Run | 调度器日志 03:06:11 有一次发送；**那一行的记录后来被合批改写了，见「缺陷」第 4 条** |
| 快速连发「总金额多少？」「按产品分别多少？」 | 和上面那个 xlsx 一起合成一个 Run，一次答完；总金额、四个产品的金额、订单数、数量逐个核对全对 | Run `24c10f0f` |

之前几轮（同一天，修复之前和之间）走通、且之后的改动没有碰到的：

- 单独发 xlsx，平台在 3.9 秒后反问「收到《…》。需要我拿它做什么？」，对方回复后文件跟着那条消息进 Run（`held_asked`）。
- Agent 设定 v6 之后，只问问题时只用文字回答，没有发文件。
- 要柱状图时发回一张 PNG（`file_sent`，56 KB，`delivered: true`，审计有 `file.sent`），纵轴从 0 开始。
- 17 MB 的文件：下载在 16 MB 处停下，`attachment_failed`，原因是 `response exceeded 16777217 bytes`；模型如实说文件太大、请重发，Run 没有失败。

## 走查抓到的缺陷

每一条在被抓到之前，后端测试都是全绿的。

1. **文件和问题一起发，文件不见了，而且没有任何痕迹。** 飞书 SDK 默认会把同一会话里 600 ms 内到达的消息合并成一条，只留最后一条的 `raw`。我们读的正是 `raw`，于是文件被丢掉，连一行日志都没有。修复是关掉 SDK 的合并（`df4b2c1`）。测试用的是 SDK 自己的 `SafetyPipeline` 和 `InboundMessage`。改之前测试是红的，症状和真机一模一样。
2. **只发文件，模型自己猜要做什么。** 设定里写了「只发文件就问要做什么」，模型却做了分析，还发回一个汇总表。改成只有文件的消息不开 Run，由平台反问（`43e945c`）。
3. **飞书不保证文件和文字谁先到。** 一次文件早到 0.6 秒，一次文字早到 0.25 秒。文字先到的那次，Run 里没有文件，模型答非所问，平台的反问还出现在答案之后。改成消息先存着，调度器把同一个人 1.5 秒内的消息合成一个 Run（`3d35a75`）。第 2 条的设计当时写着「飞书目前看到的是先发文件」，这是从一次观察推出来的，第二次就被推翻了。
4. **反问发出去了，记录却说没有问过。** 合批把一行已经结案为 `held_asked` 的文件记录改写成了 `gathered`。修复是合批只结案还没结案的行（`41a86d0`）。
5. **（不是代码缺陷）Agent 设定让它每次都发文件。** v5 写的是「做完后用 file.send 把文件发给对方」。改成 v6：对方要文件时才发。

## 看到的质量问题

- **模型编了一列数字。** 有一轮回答在你没要求的情况下加了「订单数」一列，华北、西南、华南三个数都是错的（写的 51、51、48，实际是 55、53、42），四个数加起来却正好是 200。它跑过的脚本只按地区汇总了金额，从没算过订单数。设定里已经写了「材料里没有的内容不要自己编」。最后一轮的订单数是对的，但这只说明那一次没编。

## 这一遍没能证明什么

- **最后一个修复（`41a86d0`）部署后没有再走一遍。** 它只有集成测试覆盖。
- **「只发 xlsx」那一步，反问的内容这一轮没有直接看到。** 依据是调度器日志里那个时间点有一次发送，而当时没有别的回复在等着发。前几轮用户截图里看到过反问的原文。
- **1.5 秒的窗口只来自两次测量**（0.25 秒和 0.6 秒）。网络差的时候，两条消息可能隔得更远；超过窗口，文字和文件就会进两个 Run，后到的文件会被反问。
- **没有测 Webhook 传输。** 这次全程走的是长连接。两种传输在入站之后走同一套代码，但 Webhook 没有真机走过。
- **`/new` 丢掉暂存的消息**，只有集成测试，没有真机走过。
- **多个调度器副本同时合批**，只靠 `SKIP LOCKED` 加扫描锁，没有测过。
- **单个超过 30 MB 的文件发回飞书**，没有测。
- **全量集成测试在最后几个提交之后没有再跑**，compose-e2e 也没有跑。合并前必须重新拿到 compose-e2e 的绿色结果。
- **没有测 gVisor。** 沙箱跑的是 runc。

## 不声称什么

- 不声称员工发的每个文件都能被收到。窗口之外的乱序、飞书 SDK 未来的行为变化，都可能让文件和文字分开。
- 不声称模型的回答可以不经检查直接用。上面那列编出来的订单数就是反例。
- 不声称这套栈的状态可以复现。走查期间删除了 297 个测试工作空间（删除前做了整库备份），验收记录里引用过的旧 Run 只能从备份里查。
