# 发往外面的调用被中断：告诉模型，不再失败

日期 2026-10-22。分支 `feat/interrupted-tool-calls`。设计 v2.17（§1.17、§11.3、§17.2），
运维手册 §8.5。接着[沙箱生命周期那一遍](2026-10-22-sandbox-lifecycle.md)：那一遍让「效果未知」
的 Run 在恢复时直接失败，这一遍把它换成更好的做法。

| 改了什么 | 测试 | 实现 |
|---|---|---|
| HTTP 工具的写操作真的带上请求体 | `04943c2` | `d8885b9` |
| 发往外面之前记下这一轮；恢复时写进会话，告诉模型结果未知；HTTP 写操作带 `Idempotency-Key`，原样重发用同一个键 | `af9fe33`、`0d0d2bc` | `dd1688a` |

## 为什么有这一遍

上一遍之后，一轮里 `http.*`、`mcp.*` 或联网 `shell.exec` 正在进行时 Worker 没了，Run 就失败，
要人来处理。讨论的结论是：防重复的正道是业务端做幂等，但平台要先给业务端两样东西，一是稳定的
幂等键，二是恢复时不让模型重新生成请求（重新生成的参数可以不一样，对方按请求去重也认不出）。

**顺带发现一个更大的问题：HTTP 工具的写操作从来没发出过请求体。**`OutboundHttpToolSender`
调 `client.request(method, url, headers=...)`，`plan.body` 没传，请求头却写着
`Content-Type: application/json`。测试用的替身 API 只记方法、路径、请求头，不记请求体，所以
所有测试都是绿的。这是这个项目最常见的那类问题：写进去了，没人够得着。

## 怎么改的

- **请求体**：`SafeOutboundClient.request` 多了 `content`（已编码的字节），发送端把
  `plan.body` 传进去。
- **记下这一轮**：新方法 `reserve_outside_call` 在扣工具调用次数的同一个事务里，把效果设成
  `unknown`，并把这一轮写进 `runs.inflight_round`：模型这一轮的全部调用、已经拿到的结果、
  正在发的是哪一个、HTTP 写操作的幂等键和请求指纹。`record_slice` 清掉它；`claim_head`
  也清掉（排队中的 Run 不该有在途的轮）。
- **恢复**：`recover_interrupted` 发现有这份记录、且工作区版本和检查点一致时，把那一轮写进
  会话记录：
  - 正在发的那个调用，结果写成「中断，结果未知，可能已经生效，先查再做」；有幂等键的再加一句
    「原样重发会用同一个键」；
  - 它之后的调用写成「没有完成」；
  - 它之前已经完成、可能改过 `/workspace/data` 的调用（`file.write`、`shell.exec`），结果
    后面注明这些改动没有保存。
  然后效果改回 `none`，按原有条件（`replay_safe`、预算、恢复次数）决定回队列还是失败。
  恢复事件的 payload 带 `interrupted_call_id`。
- **工作区版本对不上时不写**：那一轮的改动可能已经提交了，「没有保存」这句话就是错的。这种
  Run 照 §12 失败，和以前一样。
- **幂等键**：每个 HTTP 写操作发出时带一个新的 UUID 作为 `Idempotency-Key`，读操作不带。
  恢复时把被中断的写操作的「请求指纹（方法 + 地址 + 请求体）→ 键」记进
  `runs.interrupted_writes`。之后这个 Run 里第一个指纹相同的写操作拿这个键，用过就删；其他
  写操作，包括同一轮里两个一模一样的，各拿新键：两笔一样的订单可能就是两笔订单。

## 测试过了

- 后端单元测试 2645 条通过；集成测试（含 sandbox 目录）1213 passed、1 skipped（原有的 TLS
  socket 权限那一条）；ruff、pyright 0 errors；`alembic check` 无差异，新迁移降级再升级通过。
  全量集成跑完之后又改了一处（工作区版本对不上时不写），之后重跑了 `test_interrupted_calls`
  与 `test_scheduler`（18 passed）和全部单元测试，没有重跑全量集成。

- 新的集成测试（真 Worker、真 Scheduler、真出口代理、替身 API）。替身 API 收到请求时取消
  Worker 的任务，模拟进程在请求发出后、拿到回复前死掉：
  - Run 回到 `queued`，不是 `failed`；恢复事件带 `interrupted_call_id`；下一个 Worker 发给
    模型的请求里，那个调用的结果是「结果未知」；替身 API 总共只收到一次 POST；Run 最后完成。
  - 一轮里两个调用、死在第一个上：第二个的结果是「没有完成」。
  - 恢复后模型原样重发：第二次 POST 的 `Idempotency-Key` 和被中断的那次相同；第三次再原样
    发，换了新键。请求体换了的写操作也拿新键。
  - 正常记账的一轮之后，`inflight_round` 为空，效果为 `none`。
  - 工作区版本对不上：Run 失败，会话里没有写入这一轮。
- 请求体：替身 API 现在记录请求体，`createOrder` 收到的正是模型给的 JSON。修复前这条测试
  红（收到空请求体）。
- 一轮里两个相同的写操作各带不同的键，读操作不带键。
- 联网 `shell.exec` 执行时，`inflight_round` 指向这个调用。
- 单元测试：恢复写进会话的内容逐条覆盖（未知、没有完成、已完成的读保持原样、已完成的写注明
  没保存、有键才提重发、存取往返）。

## 这一遍没能证明什么

- **业务端会不会真的按 `Idempotency-Key` 去重，平台管不了。**不支持这个请求头的接口，模型
  原样重发就是第二笔。平台告诉了模型「可能已经生效，先查再做」，模型照不照做没有测过真实模型，
  测试里用的是脚本化的模型。
- **MCP 和联网 `shell.exec` 没有幂等键。**MCP 的 `tools/call` 没有标准的幂等请求头；shell
  命令发什么请求平台看不到。这两类只有「告诉模型结果未知」。
- **一轮里先发了外部调用、后面的调用又要审批时**，这一轮整个丢弃（原有行为，`answer_http_call`
  的文档写明了），`record_slice` 也会清掉在途记录。已经发出去的那次调用不会被告诉模型。这个
  缺口在这一遍之前就有，没有动。
- 「已完成的写操作的改动没有保存」这句话依赖恢复从最近提交的版本开始，并且版本对不上时不写。
  后者有测试；前者是现有的工作区恢复路径，这一遍没有重新验证。
- 只在本地跑了单元和集成测试；compose-e2e 以 CI 为准。

## 不声称什么

- 不声称外部调用现在是「恰好一次」。平台保证的是：不会自动重发；模型原样重发时带同一个键；
  被中断的那次有没有生效，平台仍然不知道。
- 不声称模型提供方自己报告的「外部效果未知」也被处理了。那种情况平台不知道发出过什么，Run
  照旧失败。
