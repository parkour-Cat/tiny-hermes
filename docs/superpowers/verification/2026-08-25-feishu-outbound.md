# 飞书出站：Run 跑完之后，第一次有人收到 — 2026-08-25

> 产品：v2.5 §19.2（飞书渠道、状态卡片）、§19.3（渠道适配接口四项职责）、
> §497（阻塞时必须立即告知）、§16.5（统一出站边界）。
> 起因：真实租户发消息，Run 完成，聊天窗口一片空白。

## 1. 之前是什么状态

入站整条链路是通的，而且**每一次都是通的**：验签、解密、去重认领、建
EndUser/Session、建 Run、调模型、完成。数据库里躺着 Agent 写好的回答。

§19.3 的四项职责做了三项。第四项「发送进度、结果和审批通知」**整个不存在**。

从发消息的人那一侧看，这和「平台把我的消息吃了」完全一样。

## 2. 抓到的五个真 bug

前三个是做的过程中撞上的，后两个是真租户当场打出来的。

### 2.1 `attach_run` 有写入方，没有调用方

`channel_events.run_id` 有列、有写它的方法、有测试。**没有任何生产代码调用
它。** 在一个跑着的部署里读出来：两条事件、两个 Run，两个 `run_id` 都是
NULL。

后端测试全绿。这就是 CLAUDE.md 第一段写的那件事。

现在它是出站队列的键，所以再丢会**直接停掉回复**，而不是安静地断掉一条审计
链。这是刻意的：让一个不会被发现的错误，变成一个立刻被发现的错误。

### 2.2 绑定建好之后没法改

`uq_channel_bindings_target` 一个 (workspace, channel, agent) 只允许一个绑
定，而 **`disable` 不释放这个约束**。所以出站做出来之前建的绑定：拿不到
app secret，也没法删了重建。**永久只能收不能发。**

控制台那一侧更糟：表格根本没有 `app_secret_ref` 这一列，所以「能回复的绑
定」和「只能收的绑定」长得一模一样。「Agent 明明答了，飞书什么都没有」这件
事，在那个本该解释它的页面上没有任何痕迹。

加了 `PATCH`、编辑对话框、以及那一列。

### 2.3 出站没有按 workspace 层度量

第一版共用一个 `SafeOutboundClient`。`EgressRoute` 的层是在建连接时定死的，
不是每次请求带的——所以共用一个客户端 = 不指名任何 workspace = **只按平台层
度量**。

平台放行了 `open.feishu.cn`，一个从没批准过它的 workspace 也照样发得出去。
那条 workspace 出站范围还在库里、还在控制台上显示、**什么也不管**。

§16.5 写的是 platform ∩ workspace ∩ Agent ∩ Run。改成按 workspace 一个客户
端。Agent 层和 Run 层刻意不指名：回复是平台在发自己的通知，Agent 没有要求
调飞书，拿 Agent 的 `network.allow` 去量它会逼着每个发布到渠道的 Agent 都去
列这个厂商。

### 2.4 压缩响应读不出来（影响所有调用方）

`SafeOutboundClient` 用 `stream=True` + `aiter_bytes()`，而 `aiter_bytes()`
给的是**已经解压**的字节。重建 `Response` 时把原始响应头原样带过去了，
`Content-Encoding: gzip` 也在里面。httpx 又解压一次 →
`DecodingError: incorrect header check`。

**这不是飞书特有的。** 这个客户端的每一个调用方，遇到任何会压缩响应的服务
器，`.json()` 都会炸——而会压缩的服务器是大多数。它一直没被发现，是因为在
这之前没有调用方走到过一个开压缩的真实服务器。

### 2.5 重试没有幂等键（这条把 2.4 放大成了事故）

调度器用 `except Exception` 兜住发送，把异常一律当成「没发出去」。但 2.4 的
异常发生在**拿到 200 之后**。5 次尝试 = **5 条真消息发给了同一个人**。

根因修掉了，但结构问题独立存在，必须单独修：**请求离开本进程之后的失败，
根本无法和离开之前的失败区分开**。`_read` 里对 `OutboundUnreachable` 早就写
着这句话，渠道这一层没照做。所以重试永远可能是二次投递，这边再小心也定不
了——只有渠道自己能定。

现在带飞书的 `uuid`：这次投递自己的行 id，跨每次重试不变。

关键是**跨重试稳定**。每次生成一个新的 key 会看起来像去重、实际不去重，那
比没有更糟。

> 重试上限从来就不是投递保证。现在它旁边有一个真的是了。

## 3. §19.2 的状态卡片

§497 要求的每一个事实——`blocked_by_run_id`、head 状态、暂停原因、排队位置、
可用操作——**早就算出来了**，`BlockedNotice` 从渠道落地那天就带着它们。

它们被写进了 webhook 的 HTTP 响应体。**飞书服务器读到 200 就把 body 扔了。**

所以 §19.2 的「不能静默吞入新消息」一直是假的，而且是以最难看见的方式假：
每个字段都对，每个测试都绿，没有一个人看见过。

设计上两个决定：

**存下来，不在发送时重算。** 入站那一刻是**唯一准确**的时刻。head 可能两秒
后就不阻塞了，但「你的消息当时排在第 2 位」在当时是真的，而且那正是要告诉人
的。扫描时重查会描述一个已经变了的世界——而且在「很快就不阻塞了」这个最常见
的情况下，会变成**什么都不说**。

**扫描时发，不在 webhook 里发。** 在 webhook 事务里发会让入站请求依赖
`open.feishu.cn` 可达；超时飞书就重投，而 claim 已经拿了——消息丢掉，且没有
任何东西留下痕迹。

一条投递现在会发两次，所以通知有自己的 stamp 和自己的去重 key：
- 共用 stamp → 在答案存在之前就把行结掉，人收到「排队了」然后**永远等不到结果**
- 共用 key → 飞书的去重把第二条吃掉，而第二条正是那个答案

一趟扫描里通知排在结果前面：两者可能同时到期，而「你排队了」在结果之后到达，
比不发更糟。

卡片把 `available_actions` 为空渲染成一句话，不是渲染成没有。飞书用户是
`EndUser`，不是工作空间成员（§122），所以 `can_control` 是 false，这个列表
**通常就是空的**。空不是缺信息，空的意思是「得别人来处理」。

## 4. 这一遍怎么验的

每个修复都做了破坏性验证——把保护打掉，确认有测试挂：

| 打掉什么 | 挂了几条 |
|---|---|
| `attach_run` 调用 | 7 |
| 扫描的 `replied_at IS NULL` | 2 |
| `record_blocked_notice` 调用 | 4 |
| 通知和结果共用 delivery key | 1 |
| `settle_blocked_notice` 调用 | 2 |

gzip 那条是先写复现测试、看它抛出**一模一样**的 `incorrect header check`，再
修的。

本地：2071 单元 + 839 集成 + 208 前端全绿；ruff / pyright / tsc 干净。

真实链路：飞书 → cloudflared → nginx → api → 验签解密 → 去重 → Run →
DeepSeek → 完成 → Scheduler → 换 token → 发消息 → 飞书。端到端约 5 秒。
数据库落地为 `reply_attempts=1 / reply_note=sent`，两条连续消息都是。

### §929：那个开放问题这次有答案了

演练终于做成了。停 web 容器（隧道 URL 不变，nginx 重启还能顺带避开 DNS 缓存那个坑）：

| 时刻 (UTC) | 事件 |
|---|---|
| 03:48:59 | 平台对飞书返回 502 |
| ~03:49–03:51 | 发出 drill-1/2/3，**三条都没进来** |
| 03:52:29 | 恢复服务，事件数仍是 12 |
| **03:56:43** | **三条同时到达**，全部建 Run、全部 `sent` |

补投距首次投递约 5–7 分钟，和飞书文档记的 `15s / 5min / 1h / 6h` 吻合——15 秒那档也落在停机窗口里，是 5 分钟那档兜住的。

**能写进结论的只有这一句**：Webhook 模式下，3.5 分钟的 502 停机，事件在约 5 分钟后被完整补投。

**不能写**「飞书保证补投」。这一遍的样本是 n=1、3 条消息、3.5 分钟、单一故障形态（502，平台在但拒绝服务）。1 小时和 6 小时档没测；DNS 失效、连接超时、TLS 失败会不会走同一条重试路径没测；**WebSocket 是不是同样语义完全没测**——而 spec 说私有部署默认走 WS。

### 又抓到三个真 bug

**进度提示的阈值定错了。** 代码对，数字错——20 秒，而真实的慢任务是 17.7 秒，**差 2.3 秒没触发**。原来的依据是「普通 Run 约 5 秒」这个太窄的样本。这类最难抓：没有任何东西失败，功能只是在它唯一被需要的场合没出现。改成 8 秒，并用两条按秒数断言的测试钉住（12 秒必须提示、5 秒必须不提示）——读常量的测试在常量错时不会失败。

**Runs 列表最新的排在最后**，和工作空间那次同一个形状，被同一个人问了第二遍。修法不是简单倒过来：全局列表是工作列表（最新在上），**按 session 过滤时那就是队列**（`position` 1、2、3，倒过来会让第 1 位掉到最底下）。我第一版就是简单倒过来，被一条既有测试抓住。

**卡片声称了它没有的能力。** 真租户上 `available_actions` 返回 `resume`/`cancel`（被阻塞的 head 是发消息者自己的 Run），卡片就写「你现在可以：继续、取消」——而飞书里**没有任何按钮或链接能做这两件事**。这条 docstring 本身也是错的：它说这个列表「通常为空」，那是**推理**出来的（EndUser 不是工作空间成员 ⇒ `can_control` 为 false），第一次真实观测就推翻了。CLAUDE.md 那条规则是讲注释的，但它对用户看到的文案一样成立——而且后果更直接：注释骗的是下一个开发者，文案骗的是正在等的人。

### 以及一个渠道之外的严重 bug

`endpoint_status:400`：

```
The `reasoning_content` in the thinking mode must be passed back to the API.
```

DeepSeek 的 thinking 模式要求把 `reasoning_content` 原样回传，而重放历史时丢了它。**模型第一次产出 reasoning 之后，这个会话的每一轮都必然失败**，而 transcript 看起来完全正常。

两件事值得记：

- **它能被诊断，靠的是几小时前为了另一件事（工具名 400）加的那条 `model endpoint refused: status=%s body=%s`。** 没有它这就只是一个不透明的 `endpoint_status:400`。
- **pyright 抓到了一个测试没抓到的运行时崩溃**：`context_budget` 的 block 遍历里 `else` 分支读 `block.output`，而新的 `ReasoningBlock` 没有这个属性——第一次跑 thinking 端点就会 AttributeError。891 条测试没碰到，类型检查碰到了。

`ReasoningBlock` 不是 `TextBlock`，两个方向都要紧：`CanonicalMessage.text` 只收 `TextBlock`，所以模型的思考过程永远不会出现在 transcript、飞书回复或 completions 文档里（§19.1）；但它被存下来了，所以下一轮能带回去。没有 reasoning 时一个字段都不发——给不支持的端点凭空造字段，是拿 thinking 模型的 bug 换所有其他模型的 bug。

## 5. 这一遍没能证明什么

**compose-e2e 没有重新取得绿色结果。** 本地跑过的栈不算数，这是 CLAUDE.md
的硬条件，PR 上的 CI 是唯一算数的地方。这份记录在那之前不构成合并依据。

**飞书的 `uuid` 去重仍然没有被证明起作用。** 我能断言的只有「每次重试发的是
同一个 key」。真租户上每次都一次成功，重试路径始终没走到。要证明它挡住了二次
投递，得故意让一次发送在拿到 200 之后失败——没做。

**图片只是被拒绝了，不是被处理了。** 飞书的图片消息只带 `image_key`，把图片
真正取下来需要一条新的出站下载路径（`im/v1/messages/{id}/resources/{key}`）、
落地策略和大小上限，之后才谈多模态或 OCR。这一轮做的是「诚实地说读不了」，
不是「读得了」。

~~**状态卡片没有对着真租户发过。**~~ 2026-08-25 验掉了：飞书接受 `interactive`
消息，卡片正常渲染。

**但只验了 `paused` 这一种阻塞。** 真实的 `waiting_approval` 路径（审批系统 →
head 阻塞 → 新消息排队 → 卡片）端到端仍然没走过，而那是审批场景下最常见的
一种阻塞。

**卡片上的按钮不是交互式的。** §19.2 允许「必要的审批卡片**或跳转管理页
面**」，这一版做的是后者。真正的按钮回调需要另一条 card action webhook 路
由、它自己的验签、和动作授权——没做，也没有假装做了。`CONSOLE_BASE_URL` 不
配就不渲染按钮。

**`reply_note` 只有写没有读。** 和 `audit_events` 当年一样的形状。它现在能从
psql 读到、我这一轮排查全靠它，但控制台上没有任何地方显示它——所以运维要回
答「为什么那条回复没到」，仍然得会连数据库。

## 6. 顺带发现、没在这一轮修的

**重建 api 容器会让控制台整个 502。** web 容器里的 nginx 在启动时解析一次
`api` 的 DNS 就缓存住，api 换 IP 之后一直往死地址转发。症状极难看：首页照常
打开（nginx 自己活着），但所有 API 全挂，而飞书那边只看到投递失败、平台日志
里什么都没有——请求压根没到 api。

这一轮是靠重启 web 容器绕过去的。正经修法是 nginx 配置里用 `resolver` + 变
量形式的 `proxy_pass` 强制运行时解析。已单开任务。

**`Settings(env_file=".env")` 让本机 `.env` 漏进测试进程。** 有可用本地部署
的人跑 `test_endpoint_api.py` 会有两条红，CI 上是绿的——因为 CI 没有那个
`.env`。本地跑全量要 `export EGRESS_PROXY_URL="" EGRESS_PROXY_TOKEN=""`。
