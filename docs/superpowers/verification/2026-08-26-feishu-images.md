## 2. 那 2 条失败是环境，不是分支

`test_a_check_on_a_deployment_with_no_boundary_says_so` 和
`test_a_check_reaches_nothing_when_there_is_no_boundary` 断言
`refusal == "egress_not_configured"`，实际拿到 `egress_unavailable`。

原因是 `shared/config.py:11` 的 `SettingsConfigDict(env_file=".env")`：仓库根目录
存在一个为本机部署准备的 `.env`，里面有 `EGRESS_PROXY_URL`。于是「没有出口边界」
这个前提在本机不成立——边界配置好了，只是连不上。

两个方向都验过：`EGRESS_PROXY_URL=""` 时该文件 17 条全过；不设时那 2 条失败。
CI 上没有这个 `.env`。

**这是一个真实的脆弱点，但不属于这条分支**：任何一个在本地部署过的人，跑集成测试
都会撞到，而且失败信息完全不指向 `.env`。

## 3. 这条路走得通

和 §1 是两句话。真实飞书应用、真实凭证、真实 DeepSeek vision 端点，用户自己发的图：

```
model request images attached=1 missing=0 accepts_images=True
```

机器人的回复正确描述了内容（三只灰色卡通猫的角色三视图，正面/侧面/背面）。

这一行日志是这条分支加的，也是唯一能把「图到底有没有附上去」和「模型说了什么」
分开的东西。在它出现之前，管道每一层单独验都是对的，而结果是错的。

## 4. 三个真实缺陷

**一、`accepts_images` 从来没进过数据库。** 创建端点时被静默丢弃。界面上勾了，
库里是 `false`，运行时按不接受图片处理。后端测试全绿——因为没有一条测试跨过
「写进去」和「读出来」之间那道缝。这是本项目最常见的 bug 的第六次。

**二、一张取不到的图会杀掉整轮。** 飞书里被撤回的消息，`resources` 接口永久返回
`234003 File not in msg.`。这种图会让整个 Run 失败，而不是让那一张缺席。

**三、图片密钥在错误的 session 里解析。** 绑定是在一个 session 里读出来的，凭证却
在另一个里解，拿不到。

## 5. 提示语声称了代码没有的范围

取不到图时注入的句子原来是「这个对话里有 N 张图取不到」，而它是**按单条消息**注入的。

一条真实会话把代价演示了出来：两张图属于发送方撤回的消息，永远取不回，于是这句话
每一轮都出现。模型把它读成关于所有图片的既定事实，连同旁边真正附上的七张一起拒绝看
（`attached=7 missing=2`）。把同一段 77 轮历史去掉这句重放，同一个模型正确描述了图片。

CLAUDE.md 禁止注释声称代码没有的保护。**同一条规矩适用于模型会读到的字符串**，而且
后果更直接：注释骗的是人，这句话骗的是正在回答的模型。

## 6. 破坏性验证

诊断是靠 A/B 重放确立的，不是靠推理：

| 改动 | 结果 |
|---|---|
| 原样重放 77 轮历史 | 拒绝看图（复现） |
| 去掉助手自己的 4 次否认 + 去掉那句提示语 | 正确描述图片 |
| 只把提示语换成新措辞，保留否认 | 仍然拒绝，并**逐字引用旧措辞** |

最后一行是关键：它证明毒源在**已存下来的历史**里，不在当轮注入的字符串里——也因此
证明了 §5 的改动**救不了那条已经中毒的会话**，只能防止下一条。

复数分支是先写红测试抓到的：`f"[{missing} {subject}..."` 配 `subject = f"{missing} images"`
会产出 `[2 2 images ...]`，单数用例看不见。

## 7. 这一遍没能证明什么

- **`compose-e2e` 绿了，但它一条图片都没测。** run `32928725904`（PR 触发的那次，不是
  push 那次），`18 passed (2.7m)`，确认过是真的跑了测试而不是只返回 success。但
  `tests/e2e/` 里没有任何一条涉及图片，`channels.spec.ts` 也不碰。**它证明的是这条
  分支没有弄坏别的东西，不是图片能用。**图片能用只有 §3 那一次真实运行。
- **只在一个租户、一个飞书应用、一个模型端点上走通过。** 别的 vision 端点是否接受
  同样的 `data:` URL、是否有大小或格式限制，没有验过。
- **只验过 JPEG 和 PNG。** 飞书还能发 GIF、WEBP、HEIC；`MAX_IMAGE_BYTES = 8MB` 这个
  上限没有对着真实的大图试过边界。
- **多图的行为只在重放里见过，没在真实会话里走过。** 真实那一轮是 1 张图。
- **永久取不到的图每轮都会重新去取。** 没有任何地方记住「这张没了」，于是每轮多两次
  注定失败的飞书调用和两次取 token。这是已知的、没修的。
- **没有测过并发**：同一个人连着发多张图、多个 Run 抢同一个绑定，没有观察过。
- **端点列表的价格显示是 `undefined undefined / undefined`**，这条分支碰了那个接口
  但没有修它。
- **`20260825_0045` 的在线迁移没有演练过。** 对着有历史数据的部署升级会发生什么，
  不知道。

## 8. 不声称什么

- **不声称这条分支解决了「历史污染」。** §5 只是不再制造新的污染源。已经把否认写进
  历史的会话，本分支**没有任何办法**救——用户当时唯一的出路是我直接删掉
  `channel_conversations` 里那行映射，那是数据库手术，不是产品能力。
- **不声称用户能自己脱身。** 渠道层一条聊天命令都不解析，没有 `/new`，没有 `/undo`。
  spec §916 和 §935 要求的「新建会话」入口，一处都没有实现。
- **不声称删映射是干净的。** 它留下一个 80 条消息、没有任何东西指向的孤儿 session，
  不会被回收，界面和渠道都够不着。
- **不声称诊断日志是可运营的观测。** `images attached=N missing=M` 是一行 INFO 日志，
  没有指标、没有告警、没有面板。下一次同样的故障，仍然要有人手动去 grep。
- **不声称本机跑绿等于可合并。** 判据是 CI 的 compose-e2e。
