# 沙箱内存准入与禁止 swap：让整个栈宕掉的场景，现在平稳跑完

日期 2026-09-30。分支 `feat/capacity-acceptance`，未推送。规格 v2.14（`fefb59f`）。实现从
`74ff2ec` 到 `ef21a03`，测试和实现分开提交。

## 为什么有这一遍

[OOM 记录](2026-09-30-sandbox-oom.md)：24 个沙箱各常驻 400 MiB（合计 9.6 GiB），8 GiB 的主机
13 秒内耗尽内存，OOM killer 杀掉了 `dockerd`，整个栈都停了。原因是没有任何东西限制沙箱内存的
总和。

产品负责人定了三件事：
- 按内存**上限**之和准入，不按实际用量；
- 默认预算取主机内存的一半；
- 每个沙箱的上限保持 1 GiB，改成可配置。

## 改了什么

- **配置**：新增 `SANDBOX_MEMORY_MB`（默认 1024）和 `SANDBOX_MEMORY_BUDGET_MB`。
  - 预算不填（或 Compose 传来空字符串）表示取主机内存的一半，由 controller 启动时读
    `/proc/meminfo` 算出。
  - 预算小于一个沙箱时拒绝启动，并在错误信息里写明该改哪个配置。
- **记账**：实例记下自己创建时的内存上限（迁移 0067，已有的行回填 1024）。已占用内存 =
  所有「预留还有效」（active、kept、isolated）的实例的上限之和。
- **准入**：controller 在新建实例前，拿一把 Postgres 事务级 advisory lock，锁住
  「数 → 建容器 → 登记」这一整段，直到事务提交。
  - 放不下时，先回收其他 Run 的冻结沙箱（按保温到期时间从早到晚）。只挑「预留 KEPT 且实例
    FROZEN」的，因为解冻后预留仍是 KEPT，只看预留会误删正在运行的沙箱。
  - 回收了也放不下时，一个都不回收，直接以 `memory_budget_exhausted` 拒绝。
  - 同一 Run 解冻自己的冻结沙箱不计入准入。
- **防竞争**：解冻方先 `FOR UPDATE` 锁自己的预留行；回收方用 `FOR UPDATE SKIP LOCKED` 跳过被锁的
  行，所以不会删掉正在被解冻的容器。回收时容器已经不在（例如被调度器同时清掉）算成功。
- **Worker**：收到 `memory_budget_exhausted` 时结束时间片，把 Run 放回 `queued`，不算失败；
  然后这条通道暂停一个空闲轮询间隔（默认 2 秒）再领取。暂停用普通等待而不是唤醒通知，因为每来
  一个新 Run 都会发唤醒，恰恰是没有空间的时候。
- **禁止 swap**：沙箱的 `memswap_limit` 等于 `mem_limit`。
- **Compose**：把两个配置项传给 controller。

## 测试过了

- 后端单元测试 2499 条通过；沙箱集成测试 107 条通过，其中新增 8 条准入测试、8 条存储层测试、
  1 条引擎测试。
- **并发测试是有效的**：两个申请同时抢最后一份额度，只有一个能成功。
  - 临时去掉准入锁后连跑 5 次，5 次都失败；
  - 加上锁连跑 5 次，5 次都通过。
- **退避测试是有效的**：只实现「放回队列」而不暂停时，一条通道 1.5 秒内调用了 116 次 acquire；
  加上暂停后是 1–2 次。
- 完整的本机 CI 镜像（在 `ef21a03` 上，不含 compose-e2e）：
  - ruff、pyright 0 errors；
  - 单元测试 2500 条；集成测试 1123 条；并发相关测试 ×10；
  - Redis 不可达时的集成测试 1118 条通过、5 条跳过；
  - alembic check 和迁移链；web/chat 的 lint 和 build，chat 测试 88 条；
  - 以上全部通过。
  - web 测试整套跑时有 1–2 条失败（`AgentDetailPage`、`AgentModelPolicy`），单独跑都通过。
    这条分支的 `apps/` 和 main 逐字节相同，所以这是 main 上本来就有的不稳定，和这里的改动无关。

## 走通了什么

**controller 实际生效的配置**（在容器里调用同样的函数算出）：每个沙箱 1024 MiB，预算
4002 MiB（VM 的 8005 MiB 的一半），预算环境变量为空时读成 None，controller 正常启动。
迁移 0067 已执行。

**重跑让栈宕掉的那个场景。**24 个长任务，每个沙箱常驻 400 MiB；2 × 16 条通道；每秒 3 条短消息，
持续 150 秒；模型延迟 2 秒。为了能在合理时间内跑完，每个长任务 20 轮（OOM 那次是 60 轮；OOM
发生在开始后 13 秒，远早于任何一个任务跑完）。

| | 没有准入（OOM 那次） | 有准入 |
|---|---|---|
| 结果 | 13 秒内内存耗尽，`dockerd` 被杀，整个栈停止 | 474 / 474 完成，没有失败 |
| 同一时刻的沙箱最多 | 24 | **3**（4002 ÷ 1024） |
| 沙箱内存合计最多 | 约 9.6 GiB（写入中） | 1207 MiB |
| VM 占用最多 | 可用内存只剩 160 MiB | 43% |
| swap 增加 | 约 7–8 GiB | 0 |
| 内核新增的 OOM 记录 | 有，最后杀到 `dockerd` | 0 |
| 死锁 / Postgres ERROR / Worker 报错栈 | —— | 0 / 0 / 0 |

- 回收了 22 次（审计里的 `sandbox.evict`），正好等于缓存重置 46 次减去最初的 24 次。
- 模型轮次 954 = 450 + 24 × 21，工具调用 480 = 24 × 20：**被拒的尝试没有花掉任何一次模型调用。**

**禁止 swap 的行为对照。**用同一个沙箱镜像，内存上限 256 MiB，往 tmpfs 写 384 MiB：

| | MemorySwap | 结果 | 容器 |
|---|---|---|---|
| Docker 默认 | 512 MiB | 写成功（借了 swap） | 仍在运行 |
| 等于上限 | 256 MiB | 写不进去 | 整个容器被 OOM 杀掉（`OOMKilled=true`） |

压力留在了那一个沙箱里，它的 tmpfs 也随容器一起释放。

## 代价与发现

1. **不用工具的短消息变慢了**（已在后续修掉，见下一节）。排队 P95 从 0.02 秒变成 2.0 秒，
   端到端 P95 从 2.1 秒变成 4.1 秒：通道在工具 Run 被拒后暂停 2 秒，这段时间里短消息也领不到。
2. **被拒的循环很频繁**（已在后续修掉，见下一节）。`run_lease_acquired` 有 4923 条，正常约
   500 条，多出来的约 4400 次都是「领到 → 被拒 → 放回队列」，约每秒 11 次；每次被拒都往那个
   Run 的事件记录里写一条，平均每个长任务多了约 180 条。
   - 这一轮 Postgres CPU 中位数是 101%。**我当时把它归到了被拒循环上，这是错的**：循环减少
     80% 以后仍是 101%，空闲的栈上也是 101%。真正的原因见下一节的「调度器扫描」。
3. **这台 VM 同时只能有 3 个带工具的沙箱。**这是按上限准入的代价，也是事先说好的取舍。运维可以
   调低 `SANDBOX_MEMORY_MB` 换更多个数。
4. **整个项目的日志都看不到 `extra=` 字段。**`configure_logging` 的格式是 `%(message)s`。
   controller 启动时记下的预算、Worker 记下的拒绝原因和 run_id，都没有打印出来。
5. **`SANDBOX_START_ATTEMPTS` 定义了，但没有任何代码读它。**

## 后续：被拒循环，以及现场暴露的回收 bug

**改法**（规格 v2.14 同步修改，`b375540`；测试 `7a197db`，实现 `c05c350`）：等待的是被拒的 Run，
不是通道。
- 被拒的 Run 放回队列时记下 `claimable_after = now + 10 秒`（迁移 0068），领取查询跳过还没到
  时间的 Run；
- 去掉通道暂停，通道立即继续领取其他 Run。
- 测试：
  - 被拒的 Run 在 1.5 秒内只被领一次（原来的实现领了 2 次）；
  - 被拒之后，通道在 1 秒内就处理完了一条不用工具的消息（原来的实现要先暂停 2 秒）；
  - 等待时间过去后，这个 Run 能再被领到。

**现场第一遍就暴露了一个真 bug。**474 个 Run 里 1 个长任务失败，Worker 日志有 4 个报错栈：
Run 结束时销毁沙箱得到 `no_reservation`，检查点后解冻沙箱得到 `DockerUnavailable`。
- 原因：回收的条件是「预留 KEPT 且实例 FROZEN」。但每轮提交工作区都会冻结容器，而一个 Run
  在时间片边界被解冻后，它的预留一直停在 KEPT。所以**正在运行的 Run 在检查点那一刻，看起来和
  时间片之间的冻结沙箱一模一样**，被回收删掉了。
- 后果：Run 被中断，恢复后换了新沙箱。模型看到的上一次工具结果是「已回滚」，而确定性的测试
  场景把它当成命令失败，于是判为失败（换成真实模型会重试）。
- 修法（测试 `7ade387`，实现 `6b2be78`）：只回收「所属 Run 没有有效租约」的沙箱。和调度器清理
  沙箱用的是同一个判断：时间片之间 Run 已经释放了租约，时间片进行中租约还在。
- 复现测试：把一个 Run 在时间片边界停放、再解冻、再做一次检查点冻结，然后让别的 Run 来申请。
  修复前这个沙箱被回收，修复后申请被拒、沙箱仍在。

**修复后同一场景连跑两遍：**

| | 通道暂停（原实现） | Run 自己等，修复前 | 修复后第 1 遍 | 修复后第 2 遍 |
|---|---:|---:|---:|---:|
| 完成 / 失败 | 474 / 0 | 473 / **1** | 474 / 0 | 474 / 0 |
| Worker 报错栈 | 0 | **4** | 0 | 0 |
| 短消息排队 P95 | 2.0 s | 0.0 s | 0.0 s | 0.0 s |
| 短消息端到端 P95 | 4.1 s | 2.1 s | 2.1 s | 2.1 s |
| `run_lease_acquired` | 4923 | 961 | 918 | 962 |
| 回收次数（缓存重置 − 24） | 22 | 5 | 0 | 4 |
| 长任务端到端 P95 | 374 s | 394 s | 405 s | 403 s |
| Postgres CPU 中位数 | 101% | 101% | 101% | 102% |

- 被拒循环少了约 80%，短消息回到了没有准入时的水平。
- 长任务慢了约 30 秒：空间腾出来之后，等待中的 Run 最多要晚 10 秒才会被领到。
- 两遍都是 VM 最多用 43–44%，swap 没有增加。

**调度器扫描（新发现，没有修）。**Postgres 的 CPU 一直在 101%，和负载无关：
- 在栈空闲、没有任何 Run 的时候，也是 101%。
- 负载运行中抓了 6 次 `pg_stat_activity`，5 次都在执行同一条语句：调度器的
  `sessions_needing_repair`（会话队首巡检）。
- 在空闲的栈上单次要 4.0–4.1 秒。这时库里有 7534 个会话、7151 个 Run，一个需要修复的都没有。
- 它把每个会话都和这个会话的**全部** Run 做连接，再加上几个按会话关联的子查询，开销随历史
  数据一起增长。
- 调度器每秒跑一轮，这条扫描排在等待超时、审批过期、渠道回复派发之前，所以这些事每一轮都要
  先等它跑完。

## 这一遍没能证明什么

- 沙箱在自己内部被 OOM 杀掉之后，它所在的 Run 会怎样（失败、中断，还是恢复），没有测。
- 「内核没有新增 OOM 记录」是读内核日志缓冲区得出的，而缓冲区会滚动，这个证据偏弱。更强的
  证据是：swap 没有增加，VM 占用最多 43%。
- 回收和解冻之间的竞争，只在存储层测过（`SKIP LOCKED`）。**「现场回收了 22 次、没有失败」
  盖住了一个真 bug**：回收的条件会误删正在运行的 Run 的沙箱，见下一节。那一轮没出事是运气。
- 预算来自 controller 容器里读到的 `/proc/meminfo`。在装了 lxcfs、或者给 controller 容器设了
  内存上限的主机上，它读到的可能不是主机的总内存，这种情况没有测。
- **只适用于单机。**准入锁和已占用内存的总和都是整个数据库范围的；以后有多台沙箱主机时，每台
  主机要有自己的预算，这里的做法就不对了。
- 只在 OrbStack 上测过。最终版本跑了两遍，之前的几个版本各跑了一遍。

## 不声称什么

- 不声称 10 秒的重试间隔适合所有工作负载。工具 Run 很短、又很多的部署，空间腾出后最多空等
  10 秒的代价会更明显。
- 不声称默认预算（主机内存的一半）适合所有主机。
- 不声称这套准入适用于多台沙箱主机。

测完之后，栈已经恢复成 1 个 Worker、`WORKER_CONCURRENCY=1`、模型延迟 50 ms、调用上限 20，
没有遗留的沙箱。
