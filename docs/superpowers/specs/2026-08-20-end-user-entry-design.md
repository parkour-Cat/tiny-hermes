# 终端用户入口设计 — 2026-08-20

> 产品依据：产品设计 v2.5 §4.5.1–§4.5.4、§4.6、§278、§282、§344、§348、§928。
> 路线图：M2 路线图 §10 之后的 M3，对应 §27.3 第 2 条与第 3 条的身份那半。
> 前置研究：`docs/superpowers/research/2026-08-16-end-user-entry.md`。

## 1. 这份设计的范围

**只写终端用户入口**：身份、Agent 分配、会话可见性、聊天界面。

M3 有七条，这份覆盖第 2 条和第 3 条的身份那半。其余四条各自独立，不该捆在一起：
OIDC（§27.3 第 1 条）是给**平台成员**的另一套身份；管理员视图、KEK 轮换、备份回滚、
开源材料互不依赖，各写各的 spec。

一句话说清这个入口：**平台不认识终端用户，是企业认识他。** 身份由企业担保，授权由
企业分配，界面嵌在企业自己的页面里；平台只保存一个映射和一段对话。

## 2. 0.2 留下的地基

这份设计的多数工作是把已经预留的结构接上电，而不是新建。

| 已有 | 这次要做的 |
|---|---|
| `CallerType` 有 `user` 与 `service_account` | 加第三个值 `end_user`。M2D 的路线图 §9 押的就是这一注，`memories` 表形状不变 |
| `MemoryScope` 按 `workspace + agent + subject` 隔离，且**无法构造「所有主体」** | 主体换成 `EndUser` 即可，隔离逻辑一行不改 |
| `runs.end_user_id` 已存在，`caller_type=user` 时写入调用者 | 改为写入真正的 `EndUser` id |
| `ApprovalType.USER_CONFIRMATION` 全套建好但**没有生产者** | 第一次有生产者。§27.2 场景 6 那格「绿得不对」随之变成真的绿 |
| 主体自助接口（导出、更正、遗忘、抹除） | 主体从 `CallerIdentity` 扩到 `EndUser`，接口形状不变 |
| `apps/chat-web`（#8，约 6300 行） | 换掉认证接缝，UI 基本保留 |

## 3. 数据模型

三张新表，一个枚举值。

```
end_users            id, workspace_id, created_at, erased_at
                     └─ 稳定主体。默认不含任何可识别信息。

external_identities  id, workspace_id, channel, external_user_id, end_user_id, created_at
                     UNIQUE (workspace_id, channel, external_user_id)      ← §282
                     └─ web 与 feishu 共用。跨渠道合并必须显式绑定，本设计不做。

channel_issuers      id, workspace_id, channel, issuer, public_key | jwks_url,
                     allowed_origins, status, created_by, created_at
                     UNIQUE (workspace_id, channel, issuer)
                     └─ 工作空间承认谁签发，以及允许从哪些来源嵌入（§7）。
                        两件事放一张表，因为它们是同一句话的两半：这个企业是谁，
                        它从哪里来。停用即刻对新凭证生效，不等旧凭证过期。
```

`CallerType` 增加 `end_user`。`sessions.caller_type='end_user'` 时 `caller_id` 指向
`end_users.id`。

**`end_users` 默认不存邮箱、姓名或任何可识别信息**（§4.5.1）。企业若在凭证里提供，
存进 `external_identities` 的附属字段而不是主表——这样 §344 的抹除只需清一张表的
一列，而不是追着主体到处跑。

`erased_at` 在主表上：抹除后这一行留着，因为 `runs` 和 `sessions` 引用它，而 Run 是
平台「这件事发生过」的记录（M2D 的验收记录已经就这一点表过态）。

## 4. 凭证与验签

### 4.1 凭证形状

企业签发的 JWT，`RS256` 或 `ES256`：

| 声明 | 含义 | 校验 |
|---|---|---|
| `iss` | 签发方 | 必须匹配 `channel_issuers` 中该工作空间的启用记录 |
| `sub` | 终端用户在企业侧的稳定标识 | 成为 `external_user_id` |
| `aud` | 工作空间 id | 必须等于凭证换取会话时声明的工作空间 |
| `exp` | 过期 | **最长 15 分钟**，超过一律拒 |
| `agents` | 该终端用户可用的 Agent 别名数组 | §4.5.2 的企业侧那层 |

`nbf` 与 `iat` 按标准校验，允许 60 秒时钟偏移。

**`exp` 的上限由平台强制，不由企业决定。** 一张长期有效的凭证等于一个长期密码，而
平台无法撤销它——企业改了组织架构，旧凭证仍然能用。15 分钟意味着最坏情况下一次
过期窗口，而不是一次任期。

### 4.2 换取会话

```
POST /api/v1/end-user/sessions
Authorization: Bearer <凭证>
X-Workspace-Id: <工作空间>
```

平台验签 → `upsert external_identities` → 得到 `end_user_id` → 发平台自己的会话
cookie（`HttpOnly`、`SameSite=None`、`Secure`，因为要跨域嵌在企业页面里）。

会话 cookie 的有效期独立于凭证，默认 8 小时，可续期但不可无限续。凭证只用于**换取**
会话，之后每次请求不再需要它——这让企业只需在打开助手时签一次。

### 4.3 撤销

停用 `channel_issuers` 的一行，该签发方的**新**凭证立刻无效。已换出的会话 cookie
不受影响，需要单独撤销：`DELETE /api/v1/end-user/sessions/{end_user_id}`，工作空间
管理员可调。

这是一个真实的权衡而不是疏漏：让每次请求都回查签发方状态，等于把验签成本加到每个
请求上。分成两个动作，并把「停用签发方不会踢掉已在线的人」写进文档，比一个看起来
即时、实际要等 8 小时的承诺诚实。

## 5. Agent 分配：两层

§4.5.2。两层都过才能跑：

**平台侧闸门。** `AgentSpec` 增加可选顶层文档 `end_user_access`：

```json
{ "end_user_access": { "enabled": true } }
```

不写就不带这个键——`skills`、`http_tools`、`mcp_tools`、`delegation` 依次做过同一个
承诺，这是第九次，**已发布版本的内容哈希不变**。

**企业侧分配。** 凭证 `agents` 数组里的别名。平台校验每个别名在该工作空间存在、已
发布、且 `end_user_access.enabled` 为真。

凭证列了但闸门没开 → 拒绝并说明是哪个；闸门开了但凭证没列 → 该终端用户看不到它。
**两个方向都不静默**，因为这两种错误的修法在不同的人手里。

分配关系不落库。企业的人员变动不需要同步给平台，这是 §4.5.1 省下的成本。

## 6. 会话可见性：读得到，但留痕

§4.5.3 与 §4.6（v2.5 修订后）。这一节比早先的设想**小**：既然开发者可以读，就不需要
按主体收窄查询，`list_sessions` 的现有行为保持不变。

要加的只有审计。

| 接口 | 改动 |
|---|---|
| `GET /api/v1/sessions` | 不变。列表只有状态与时间，本来就不含正文 |
| `GET /api/v1/sessions/{id}/messages` | 会话属于终端用户时，写一条 `end_user_session.read` 审计 |
| `GET /api/v1/runs/{id}` 与 `/events` | 不变——状态不是内容 |
| 更正 / 删除 / 遗忘 | **不对开发者开放**。§4.6 只放开了「查看」 |

审计记录含：读取者、被读主体、会话 id、时间。企业问「谁看过小张的对话」时，这是能
拿出来的东西。

**列表页不写审计，读正文才写。** 一次列表返回几十个会话标题，为它写几十条审计既没用
也会把真正有意义的读取淹掉。审计要能回答「谁读了谁的对话」，而不是「谁打开过页面」。

一条测试钉住：开发者读终端用户会话正文后，审计表多一行且含双方身份。这是本节唯一的
新行为，没有测试它会在某次重构里悄悄消失。

## 7. 聊天界面

`apps/chat-web` 保留，换掉认证接缝：

```
现在：  api("/api/v1/auth/me") + X-Workspace-Id + X-CSRF-Token + credentials
改为：  凭证换会话一次，此后携带 end-user 会话 cookie
```

研究文档已经指出这是「一个文件而不是七十个」的改动，前提是 API 层收在一个接缝后面。
本设计要求实施时**先做这个接缝**，再替换实现。

企业以 iframe 嵌入或新窗口打开。跨域因此是常态：`SameSite=None; Secure` 必需，
`X-Frame-Options` 不能是 `DENY`，允许嵌入的来源由工作空间登记（复用
`channel_issuers` 的同一份配置，多一列 `allowed_origins`）。

控制台仍是控制台（§928）。widget 与 SDK 不属于本设计。

## 8. 错误与失败

| 情形 | 行为 |
|---|---|
| 签发方未登记或已停用 | 401，不说明是哪一种（避免探测哪些签发方存在） |
| 验签失败 / 过期 / `aud` 不符 | 401 |
| `exp` 超过 15 分钟上限 | 401，且**明确说明超限**——这是企业配置错误，值得被告知 |
| 凭证列了未开闸门的 Agent | 403，指名是哪个 |
| 终端用户调用未分配的 Agent | 403 |
| 终端用户尝试访问控制台接口 | 403，无一例外（§4.5 首句） |
| 主体已抹除 | 401，凭证不再能换出会话 |

## 9. 测试

**单元。** 凭证校验（每一条声明的每种失败）、`exp` 上限、两层分配的四种组合、
`MemoryScope` 拿到 `EndUser` 主体后仍无法表达「所有主体」。

**集成。** 一次完整换取与对话；同一 `sub` 第二次进来拿到**同一个** `end_user_id` 且
记忆仍在；不同 `sub` 互相看不到对方的记忆与会话（M2D 的隔离测试换主体重跑）；
开发者读终端用户会话正文**写下审计**；开发者不能更正或删除终端用户的记忆；
停用签发方后新凭证被拒。

**端到端。** 一条 `end-user.spec.ts`：企业签凭证 → 打开聊天 → 对话 → 关闭重开仍是
同一个人 → 主体自助导出拿到自己的数据。

**必须有一条测试**断言开发者读取终端用户会话正文时写下审计。§6 是这份设计里唯一
「改既有行为」的部分，而它现在只剩这一条——没有测试钉住，它会在某次重构里悄悄消失。

## 10. 这份设计明确不做

- **跨渠道身份合并。** §282 要求显式绑定，本设计不提供绑定入口。同一个人从飞书和
  Web 进来就是两个 `EndUser`，各自的记忆不互通。这是诚实的默认。
- **平台自己的终端用户登录**（邮箱、魔法链接、密码）。选它就等于平台成为身份提供方，
  §4.5.1 明确排除。
- **widget 与 SDK。**
- **飞书渠道的去重与 WebSocket 接入。** 那是 §27.3 第 3 条的另一半，共用本设计的身份
  路径，但事件去重与传输是它自己的问题。
- **OIDC。** 那是平台成员的身份，与本设计是两套东西。

## 11. 这份设计替产品做的两个决定

**一、凭证有效期上限由平台强制，15 分钟。**
另一个合理答案是让企业自己定。不选它：一张长期凭证等于一个平台无法撤销的长期密码，
而企业改组织架构时旧凭证仍然有效。代价是企业每次打开助手都要签一次——但那本来就是
一次后端调用，不是负担。

**二、停用签发方不踢掉已在线的会话。**
另一个合理答案是每次请求回查签发方状态。不选它：那把验签成本加到每个请求上，而收益
只是把最坏 8 小时缩短到即时。分成两个动作，并把这一点写进文档，比一个看起来即时、
实际要等一个会话周期的承诺诚实。需要立刻踢人时有单独的撤销接口。
