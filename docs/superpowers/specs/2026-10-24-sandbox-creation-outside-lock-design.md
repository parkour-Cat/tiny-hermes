# 沙箱在准入锁外创建

日期 2026-10-24。产品设计 v2.24（§21.3）。

## 1. 要解决什么

2026-10-24 用确定性模型压测数据库时，最耗数据库时间的语句不是任何写入，而是沙箱准入锁：

| 负载 | 同时执行 | 加锁次数 | 等锁合计 | 平均每次 |
|---|---:|---:|---:|---:|
| 40 个长任务 | 42 | 40 | 80.7 s | 2.0 s |
| 120 个长任务 | 124 | 120 | 320 s | 2.7 s |

原因：一台主机上的 `acquire` 拿着准入锁（`pg_advisory_xact_lock`）做完全部事情才放：

1. 算内存够不够，不够就驱逐；
2. 清掉这个 Run 留下的旧容器和卷；
3. 建数据卷、建沙箱网络；
4. **建容器**（最慢，零点几秒到一两秒）；
5. 写实例和 reservation；
6. 整个请求的事务提交时才放锁。

所以同一台主机上的新沙箱是**一个接一个建的**。任务一多，排在后面的要白等好几秒才开始执行。

产品设计 §21.3 原文是「放行检查、新实例的创建与登记在同一把 PostgreSQL advisory lock 下完成」。
锁要保证的是「两个申请不能同时数到同一块空闲内存」，这只需要**数和登记**在锁里；建容器不需要。

## 2. 设计

### 2.1 三段

| 段 | 在哪 | 做什么 |
|---|---|---|
| 一、登记 | 准入锁里，一个事务 | 检查内存，不够就驱逐；写实例（状态 `creating`，还没有容器编号）和 reservation（`active`）；**提交**，锁随之释放 |
| 二、建造 | 锁外 | 清旧容器和卷；建卷、网络、容器 |
| 三、完成 | 新事务 | 实例写上容器编号，状态改为 `running`；登记出站地址 |

- 内存在第一段就算进去了：`creating` 实例的 reservation 是活的，准入求和照样数它。所以两个申请仍然
  不会同时拿到同一块空闲内存。
- 同一个 Run 不会建出两个：「每个 Run 只有一个活 reservation」的唯一索引在第一段就生效。
- controller 需要能在一次调用中途提交。新增一个可选的 `commit` 回调，由创建 controller 的地方传入
  （socket 分派里就是那个会话的 `commit`）。不传时不中途提交，行为和以前一样，单元测试的假 store 用这种。

### 2.2 第二段失败

建卷、建网络、建容器任何一步失败：删掉已经建好的部分，实例标为 `destroyed`，reservation 释放，
**提交这些变化**，然后照原样把异常抛出去。内存额度随之归还。

为什么要自己提交：分派层遇到非拒绝类的异常会回滚。不自己提交的话，这些变化会被回滚掉，留下一个
永远是 `creating`、占着内存的实例。

### 2.3 第二段中途崩溃

controller 进程在第一段提交之后、第三段之前死掉，会留下：一个 `creating` 实例（可能已经有了容器，
可能没有），一个 `active` 的 reservation。

不需要新机制：Worker 的这次调用拿不到回答，按 B 档规则处理（请求已经发出，可能已经生效）。租约
过期后，Scheduler 现有的流程把 reservation 标为 `isolated`，再让 controller `cleanup`。`cleanup`
要能处理还没有容器编号的实例：**按实例标签找出容器来删**，而不是按编号。

### 2.4 清扫

清扫判断「这个容器有没有人记录」时，`creating` 的实例算有记录。

以前清扫靠准入锁保证「没有登记的容器一定是 acquire 死在半路留下的」，因为建容器和登记都在锁里。
现在先登记再建容器，**任何容器在建出来之前就已经有一行登记**，这条保证反而更直接了。清扫仍然拿
本机的准入锁，和第一段的驱逐互斥。

### 2.5 表结构

迁移：`sandbox_instances.container_id` 改成可空；状态的检查约束加 `creating`。

## 3. 换不来什么

- Docker 守护进程自己处理并发创建的能力有上限，这次只是不再由平台把它们排成一队。
- 驱逐仍然在锁里做（它要和计数在同一把锁下）。驱逐要停容器，会慢一些，但只在内存不够时发生。
- 第一段多了一次提交，每次新建沙箱多一次数据库往返。

## 4. 验收

- 集成测试（真 Docker）：两个 acquire 同时进行，给建容器加上固定延迟，两个的总耗时接近一个，而不是
  两个之和；内存预算刚好只够一个时，两个同时申请仍然只有一个成功。
- 建容器失败：什么都不留下，内存额度归还，实例是 `destroyed`。
- 有一个 `creating` 实例和它的容器时，清扫不删它；对这样的实例 `cleanup`，能按标签删掉容器。
- 重跑 120 个长任务的压测：等锁时间应该大幅下降，长任务端到端时间也应该下降。如果没有下降，说明
  瓶颈在 Docker 守护进程自己，要记录下来。
