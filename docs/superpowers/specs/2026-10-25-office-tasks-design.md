# 让员工在飞书里用 Agent 完成日常办公任务（v2.27）

日期 2026-10-25。产品设计 §1.27。

## 目标

公司员工在飞书里给 Agent 发消息（可以带文件），Agent 在沙箱里处理，把结果（文字，或者 Excel、Word、PPT 文件）发回飞书。

## 验收用的 6 个任务

都是公司里常见的事，每个任务都有可以客观判断对错的产出：

| # | 员工在飞书里说 | 附带的文件 | 期望的产出 | 怎么判对错 |
|---|---|---|---|---|
| 1 | 把这周的销售明细按部门汇总成周报，带一张图 | `sales.xlsx`（几千行） | `周报.xlsx`（汇总表、图表）和一段文字总结 | 汇总数字和我的参考计算逐个核对；文件能用 LibreOffice 正常打开 |
| 2 | 这三份合同里的付款条款列个表 | 3 个 PDF 合同 | `付款条款.xlsx`（合同名、金额、节点、比例、期限） | 和我埋在合同里的条款逐项核对 |
| 3 | 根据会议记录写纪要，列出待办 | `会议记录.docx` | `会议纪要.docx`（决议、待办、负责人、截止日期） | 待办和负责人与原文一致；文档能打开 |
| 4 | 客户名单很乱，帮我去重、统一格式 | `客户.csv`（重复、手机号和日期格式不一） | `客户_清洗后.xlsx` 和一句说明 | 去重后的条数、手机号和日期格式与参考结果一致 |
| 5 | 根据这份说明做个 5 页的汇报 PPT | 一段文字说明 | `汇报.pptx`（5 页，带标题和要点） | 页数、每页标题；能用 LibreOffice 打开 |
| 6 | 帮我写一份下周五团建的通知 | 无 | 一段可以直接转发的文字 | 包含时间、地点、报名方式等要素（人工看） |

## 需要补的三块能力

### 1. 沙箱能处理办公文件

沙箱镜像加上 Python 3，以及处理办公文件的库：表格（openpyxl、pandas）、Word（python-docx）、PPT（python-pptx）、PDF（pypdf、pdfminer；pdfplumber 在 Debian 里没有包，不装）、画图（matplotlib，配中文字体）。

- **做法：** 直接升级默认镜像，不做按 Agent 选镜像。平台现在只批准一个镜像（`SANDBOX_IMAGE_DIGEST`），多镜像要改审批模型，等真有需求再做。
- **代价：** 镜像会从约 100 MB 变大，具体大小在实现时量出来；沙箱建容器的速度要重新测。
- **不变的：** 安全限制完全不变。仍然没有网络、只读根文件系统、非 root 用户。镜像里也不放包管理器和网络工具。

### 2. 员工能在飞书里把文件发给 Agent

- **接收：** 飞书的「文件」消息（`message_type: file`）现在会被拒收。改成接收，在对话记录里存一个引用，格式和图片一样：`feishu:{message_id}:{file_key}`，再加上清理过的文件名。旁边加一句给模型看的说明：「附件 X 在工作区的 inbox/X」。
- **放进沙箱：** 这个会话里**第一个打开沙箱的 Run** 负责放：用渠道绑定的凭据从飞书下载，写到 `inbox/<文件名>`，在这一轮的任何命令之前。之后它就是工作区里的普通文件，随检查点保存。
  - 为什么不是「收到文件的那个 Run」：飞书的文件是单独一条消息，没有文字。收到它的 Run 通常只回一句「收到」，不跑命令，也就不开沙箱。真正干活的是下一条消息的 Run。
  - 每个附件只放一次：放好或放不了，都写一条 Run 事件（`attachment_placed` / `attachment_failed`），以后的 Run 看到事件就不再下载，免得覆盖 Agent 已经改过的文件。
  - 写文件用的是 `file.write` 同一个助手程序，路径和大小的限制和模型自己写文件完全一样。
- **限制：**
  - 单个文件不超过 16 MB，就是 `file.write` 的上限（原计划 50 MB；用同一条写入路径更重要）。超过的拒绝，不截断：半个表格打开是坏的，而且没人知道为什么；
  - 文件名会被清理：只留最后一段，控制字符换成 `_`，去掉开头的点，太长的保留扩展名截短。解析时清理一次，进 Run 时再清理一次；
  - 下载失败时，在这一轮第一个工具结果前面如实告诉模型「文件没能取到」，并让它请对方重发，不能假装文件存在。
  - 撤回的消息里的附件不放。

### 3. Agent 能把文件发回飞书

- **新工具 `file.send`：** 参数是工作区里的一个路径。它是平台自己回答的工具，不进沙箱，处理方式和 `site.publish` 一样：从会话最新的已提交版本里取这个文件。
- **Run 来自飞书时：** 先把文件上传到飞书（`im/v1/files`），再在原来那个对话里发一条文件消息。
- **Run 不是来自飞书时**（控制台、网页聊天）：回答「文件已保存在工作区，可以在 Run 的文件列表里下载」。
- **限制：**
  - 单个文件不超过 30 MB，这是飞书的上限；
  - 每个 Run 最多发 10 个文件；
  - 每次发送写一条事件；审计只记文件名和大小，不记内容。
- **要单独一轮：** 和 `site.publish` 一样，同一轮里刚写的文件还没提交，所以发送要放在单独一轮。

## 不做

- 网页聊天的文件上传：首版只做飞书。
- 联网搜索：现在没有搜索工具，需要时再单独设计。
- 文件格式转换（比如 Word 转 PDF）：需要 LibreOffice，体积太大，首版不装。

## 测试计划

- **镜像：** 沙箱里能导入这些库，能生成并读回 xlsx、docx、pptx、pdf；生成的图表里中文不是方块。
- **文件进入沙箱：** 用飞书 SDK 自带的事件类型构造文件消息，不手写事件结构；文件下载用一个返回真实字节的假飞书服务。
- **文件发回飞书：** 上传和发送的请求形状，用飞书 SDK 的请求类型来校验。
- **用 DeepSeek 把 6 个任务跑一遍：**
  - 输入走真实的接收路径（模拟飞书事件），产出用我的参考结果核对，文件用 LibreOffice 打开检查；
  - 最后请你在真实的飞书里，用一个真实任务走一遍完整流程。
