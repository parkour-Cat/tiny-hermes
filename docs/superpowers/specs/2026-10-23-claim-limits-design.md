# 领取顺序与并发上限

日期 2026-10-23。状态：**已评审（§5），实现中**。产品设计 v2.21 §1.21 第 2、3 条的实现设计。
两条都改的是 Worker 领取 Run 的那一个查询（`SqlRunStore._select_claimable`），所以放在一起。

## 1. 现在怎么领取

Worker 用一条 `SELECT ... FOR UPDATE SKIP LOCKED` 选出一个可领取的 Run：

- 状态是 `queued`、是自己会话的队首、没被别的 Run 挡住、没有活着的租约、不在被拒后的等待期里；
- 按 `queued_at`（进入队列的时间）最早的先领。

长任务每跑完一个时间片（默认 30 秒）就回到队列，重新按 `queued_at` 排队。

## 2. 交互优先（第 2 条）

### 什么算交互

产品负责人选的是**按入口**：

| 入口 | 怎么从数据里看出来 | 交互？ |
|---|---|---|
| 同步 Chat Completions 接口 | `runs.delivery_mode = 'chat_completions'` | 是 |
| Web Chat、飞书等聊天渠道 | 会话的发起人是终端用户：`sessions.caller_type = 'end_user'` | 是 |
| 控制台、异步 Runs API（用户或 API Key） | 其余 | 否 |
| 子 Run（委派） | `runs.parent_run_id` 不为空 | 否，即使父 Run 是交互的 |

子 Run 不算交互：它是父 Run 在后台拆出来的活，没有人在屏幕前等它。父 Run 等它的时候本身不占通道。

### 怎么排

```
ORDER BY 是否交互 DESC, queued_at, id
```

同类之间仍然先到先得。

### 代价：后台任务可能一直排不上

如果交互请求源源不断，后台 Run 理论上可以一直轮不到。两种处理：

- **A. 不处理。**容量够时交互请求是一阵一阵的，后台总有空档。
- **B. 后台 Run 等太久就升级。**排队超过 N 秒（比如 120）的后台 Run，当作交互 Run 排。

**我的建议：B。**多一个条件，换来「后台任务不会被饿死」这个保证。阈值做成配置。

## 3. 并发上限（第 3 条）

### 什么算「在执行」

状态是 `running` 的 Run，也就是正拿着租约跑时间片的。在等审批、等外部事件、暂停中、排队中的都
不算。所以一个人开 10 个长任务，同一时刻占用的只是正在跑时间片的那几个。

### 按什么算「一个人」

按会话的发起人：`sessions.caller_type` + `sessions.caller_id`，也就是控制台用户、终端用户或者
服务账号。

**要你确认的一点：服务账号（API Key）算不算「一个人」？**API Key 一般是一个系统在调用，背后可能
代表很多人。如果按人限到 3 个，一个对接系统就只能同时跑 3 个。

**我的建议：每人上限只管用户和终端用户，服务账号只受工作空间的上限约束。**

### 上限放在哪

两个新的工作空间设置，和已有的 `max_run_cost` 一样放在 `workspaces` 表上：

| 列 | 默认 | 含义 |
|---|---|---|
| `max_running_runs_per_caller` | 平台配置 `RUN_LIMIT_PER_CALLER`，初值 3 | 同一个人同时在执行的上限 |
| `max_running_runs` | 空，表示不限 | 整个工作空间同时在执行的上限 |

和 `max_run_cost` 一样，**这一遍不做设置界面和 API**，先用 SQL 设；界面放到第 4 项「长任务上限」
时一起做，那一项本来就要做工作空间设置页。

### 怎么在领取时执行

在 SQL 里把「这个人已经满了」「这个工作空间已经满了」的 Run 排除掉：

```
AND (该会话发起人在执行的 Run 数) < 每人上限
AND (该工作空间在执行的 Run 数) < 工作空间上限
```

**并发领取会多给。**两个 Worker 同时领取，各自数到「2 个在执行」，各领一个，结果变成 4 个。
处理：选出候选后，按发起人取一个事务级 advisory lock，锁住后再数一次；超了就放弃这个候选、
把这个人排除掉再选一次，最多重试几次。工作空间上限同理。

### 超出的会怎样

排队，不报错，也不改状态。界面上看到的就是「排队中」。**这一遍不在界面上说明「因为你已经有 3 个
在执行」**，要做的话是后续的展示改动。

## 4. 测试

- 交互 Run 比更早进入队列的后台 Run 先被领取；同类之间仍按时间。
- 子 Run 不算交互。
- 后台 Run 排队超过阈值后，排到交互 Run 前面（如果选 B）。
- 同一个人有 3 个在执行时，他的第 4 个不被领取，别人的照常领取；他的一个结束后，第 4 个被领取。
- 服务账号不受每人上限约束，只受工作空间上限约束（如果选建议的做法）。
- 工作空间上限同理。
- **并发领取不超额**：多个 Worker 同时领取，在执行数不超过上限。用真实数据库、并发事务测。
- 压测：用探针跑「长任务占满 + 持续短消息」，对比改动前后短消息的排队时间（容量方案里那组 P95 31.6 秒的数据）。

## 5. 已决定（2026-10-23）

1. 后台任务防饿死：**B**，排队超过 `RUN_INTERACTIVE_PROMOTION_SECONDS`（初值 120）的后台 Run
   按交互 Run 排。
2. 服务账号**不算**「一个人」：每人上限只管用户和终端用户，服务账号只受工作空间上限约束。
3. 上限先只用 SQL 设，设置界面放到第 4 项（长任务上限）一起做。
