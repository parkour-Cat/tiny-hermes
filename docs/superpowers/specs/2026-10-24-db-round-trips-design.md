# 减少数据库来回：三处确定的浪费

日期 2026-10-24。

## 1. 测出来的

在本机 Compose 栈上打开 `pg_stat_statements` 和逐条语句日志（带客户端地址，区分 worker、controller、
scheduler、api），跑一个 10 轮的确定性长任务：

- 一个任务 11 轮，约 400 个事务，**每轮约 36 个**，其中约 25 个只读后回滚。
- 每个真正的事务前面几乎都有一对空的 `BEGIN; ROLLBACK;`：这是连接池借出连接前的探测
  （`pool_pre_ping=True`）。所以「事务数」里有一半是这种探测。
- **scheduler 空闲时每秒约 52 条语句、16 个事务。**一轮扫描约 1.7 秒（间隔 1 秒加上扫描本身），
  14 项扫描每项一个事务。其中 4 项是整理类：删过期记录（幂等记录、过期事件、登录失败记录等）、
  清上传垃圾、过期产物、取消 24 小时的兼容超时，每秒做一次没有意义。
- **controller 每次调用把同一个沙箱实例读 2 到 3 次**：`_reservation` 里检查「是不是本机的」读一次
  （C 档加的），`_require_owned` 又读一次，有的操作还再读。每轮约 5 次 controller 调用。
- **worker 每轮构建两次上下文**（模型调用前读一次，调用后为了看到用户中途的暂停、取消再读一次），
  每次都读已发布的 Agent 版本、再解析一遍 spec；记忆检索还要再查一次这个版本属于哪个 Agent。

同一时间的另一轮压测（124 个任务同时执行）里，Postgres 只用了 8 核中的 1.6 核。所以这不是救火，
是把确定的浪费去掉，让数据库在并发再往上走时晚一点撞墙。

## 2. 改什么

### 2.1 scheduler：整理类扫描每 60 秒一次

`collect_expired_records`、`collect_upload_garbage`、`expire_artifacts`、`cancel_aged_compat_timeouts`
四项改成距上次执行满 `SCHEDULER_HOUSEKEEPING_SECONDS`（默认 60）才执行；进程启动后的第一轮照常执行。
其余十项（回收租约、恢复中断、沙箱回收、等待到期、审批过期、渠道回复等）和延迟有关，仍然每轮都做。

这四项晚最多一分钟没有可见后果：过期数据多留一分钟，24 小时的超时晚一分钟取消。

### 2.2 controller：一次调用只读一次实例

「是不是本机的沙箱」的检查改为使用调用里已经读到的实例，不再单独再读一次。拒绝的条件和原因
（`reservation_elsewhere`）不变。

### 2.3 worker：已发布的 Agent 版本按编号缓存

已发布版本的内容不可变（内容哈希不变是项目约定），一个 Run 用的版本编号在 Run 的一生里也不变。
所以 `execution_context` 和记忆检索读到的 spec、版本所属的 Agent，按版本编号缓存在进程里（上限
1024 个，最久未用的先淘汰），连解析好的 spec 一起缓存。

## 3. 不改什么，为什么

- **连接池探测**：它让数据库重启后第一次借出的失效连接被丢弃，而不是让正在执行的 Run 出错。去掉的
  代价是可见的错误，换来的是一个很便宜的空事务。不改。
- **每轮第二次读上下文**：它拿的是最新的运行状态、预算消耗和模型配置，后面很多步都要用，换成精简
  读取风险大。不改。
- **记忆检索**：Run 执行期间记忆可能变化，不缓存。

## 4. 验收

- scheduler：连续两轮里整理类扫描只执行一次，其余扫描两轮都执行；间隔满了再执行。
- controller：execute、freeze、thaw 各只读一次实例；别的主机名下的沙箱仍然拒绝。
- worker：同一个 Run 连续两次读上下文，只查一次 `agent_versions`。
- 用同样的方法再测：每轮语句数、scheduler 空闲时每秒的语句数，前后对比写进验收记录。
