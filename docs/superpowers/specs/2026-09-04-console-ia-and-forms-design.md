# 控制台：入口重组与表单收纳 — 2026-09-04

> 由来：使用者的原话是「**我是觉得入口太多，配置太多，别说用户了，连我都不知道
> 这些都是干嘛的**」，以及「有些配置页面太复杂太凌乱」。
>
> 这两句指的不是同一件事，也不能用同一个办法解决。前一句是**找不到、看不懂**，
> 后一句是**填不动**。

## 1. 这份文档管什么，不管什么

**管三件：**

1. 顶级入口从 18 个降到 7 个（§2）
2. 三个最重的表单改成分段收纳（§3）
3. 一组**可验收的**界面规则（§4）

**不管：**

- **不重做那 9 个轻量配置页**（成员、密钥、API 密钥、MCP 服务、HTTP 工具、
  出站范围、身份提供方、技能、提案）。实测它们都在 12 个字段、6 列以内，
  重做它们是花力气换不到东西。
- **后端只加一样东西：当前成员在这个工作空间的角色。**前端现在拿不到它——
  `/api/v1/members` 给的是成员列表（而 viewer 未必列得出来），没有任何接口回答
  「我是什么角色」。§2.6 需要这个答案。**除此之外后端不动**：接口、数据、
  权限判定一律照旧，尤其是拒绝的判定仍然只在后端。
- **不替任何页面写文案。**§4.4 要求四个缺说明的页面**各补一句**，但**写什么由
  那一页自己定**——这份文档只要求那句话存在，不规定它说什么。

**「界面优化」在这份文档里不是一个目标，是 §4 那四条规则。** 一个没有验收判据的
「让它变好看」会一直做不完，而且没有人能说它做完了没有。

## 2. 入口：18 → 7

### 2.1 现在为什么不行

18 个入口平铺一排，无分组，导航上只有词、没有说明。`ConsoleLayout.tsx` 的注释
已经承认这一排装不下：

> One row could not hold a brand, a workspace name, eighteen destinations and the
> account controls without every one of them shrinking below its own text

页头因此被拆成两行——**那是症状，不是解法**。

三组入口其实是同一件事被拆成了三份，从它们自己写的说明里就看得出来：

- **审批 / 提案 / 记忆审核** — 都是「有东西停在这里等人点通过或拒绝」
- **技能 / HTTP 工具 / MCP 服务** — 三句说明都以「Agent 绑的是……」结尾
- **模型端点 / 密钥 / 身份提供方 / 出站范围** — 配一次，之后不碰

### 2.2 新的七个入口

| 入口 | 内含 | 合并依据 |
| --- | --- | --- |
| **Agents** | Agents、Agent 详情、Playground | 不变 |
| **运行** | 运行列表、运行详情 | 不变 |
| **渠道** | 渠道绑定、终端用户签发方 | 不变（本来就是两段） |
| **待办** | 审批 · 提案 · 记忆审核 | 都在等一个人点通过或拒绝 |
| **工具与技能** | 技能 · HTTP 工具 · MCP 服务 | 都是 Agent 绑定的来源 |
| **记录** | 审计 · 用量 · 主体数据 | 都是已经发生的事，只读或按人查 |
| **设置** | 成员 · API 密钥 · 身份提供方 · 模型端点 · 密钥 · 出站范围 | 配一次，之后不碰 |

**一个入口都没有被删掉。**

### 2.3 导航上要带那句说明

每个入口在导航上显示它自己的一句话（悬停或二级菜单）。这些句子**已经写好了**，
存在 `apps/web/src/i18n/zh-CN.ts` 的 `*Intro` 里——问题是它们只在人**已经走进去
之后**才显示，而需要它们的时刻是「决定走进哪里」之前。

对合并出来的四个入口（待办、工具与技能、记录、设置），导航上显示的是这个入口
自己的一句话；进去之后每一段仍然显示各自原有的那句。

### 2.4 旧地址保留成跳转

`/workspaces/:id/approvals`、`/skills`、`/audit` 这些地址可能被存过书签，也可能
出现在别处（文档、消息、别人的笔记）。全部保留，跳到新位置对应的段。

**跳转不是过渡措施，是长期行为。** 一个能打开的旧链接不会因为新导航上线就变得
不该打开。

### 2.5 「待办」上的计数

「待办」入口显示一个数字：三个队列里一共有几件事等着人处理。

**做法：前端并发调用现有的三个列表接口，把条数加起来。不新加计数接口。**

理由是这样不新增任何后端面，权限沿用三个接口各自已有的判定；而且这三份数据进了
缓存之后，点进「待办」是即时的——一个只回数字的接口反而要在点进去之后再拉一次
列表。

代价写明：三个队列都很长时这是三次全量请求。**队列长到让这件事变慢的那天，就是
该加计数接口的那天**，不是现在。

**没有这个数字，「待办」这个入口就不比原来三个分开的入口强多少**——它省下的只是
两次点击，而它真正的价值是让人不必逐个点进去才知道有没有事。

### 2.6 分段要按角色显示

现在的导航**无条件显示全部 18 项**：一个 viewer 看得见「渠道」，点进去拿到 403。

合并成分段之后这个问题更难看——一个 403 的段夹在两个正常段中间。所以合并页的
每一段按当前成员的角色决定显不显示。

**这是现在没有、要新加的能力。**它不改后端的判定（后端照旧拒绝），改的是前端
不再展示一个注定被拒绝的入口。

**前端的隐藏不是权限。**后端的拒绝仍然是唯一的权限判据；前端少画一个段只是
不去邀请一次注定失败的点击。这一条必须写在代码里，否则下一个人会以为隐藏就是
授权。

## 3. 表单：分段 + 折叠时显示当前值

### 3.1 只动三页

实测（表格列数、表单字段数、文件行数）：

| 页面 | 行数 | 表格列 | 表单字段 |
| --- | --- | --- | --- |
| Agent 详情 | 878 | — | 15 |
| 渠道 | 700 | 13 | 5 + 5（两个表单，跨三个弹窗重复） |
| 模型端点 | 466 | — | 14 |
| 其余 9 个配置页 | ≤274 | ≤6 | ≤12 |

**字段没有虚的。**36、26 这类大数字来自同一套字段在新建/编辑弹窗里重复出现，
不是真有那么多不同的东西要填。

### 3.2 规则

每个表单切成命名分段。**一段里所有字段都有合理默认时，该段默认折叠。**

**折叠条上必须显示这一段现在的值。**例如：

```
这个模型的能力 · 128k 窗口 · 最多 4096 输出 · 不收图片        [展开]
计价 · 未设置，这个端点的花费无法计算                          [展开]
```

**这一条是整个设计的关键，不是装饰。**没有它，折叠等于把字段藏起来，人会不敢折叠，
因为不知道里面有什么——那就退化成了「一个叫『更多设置』的抽屉」，只是把乱推进
一个看不见的地方。有了它，**折叠状态比展开状态信息量更大**：一行就说清了那一段
此刻是什么。

新建与编辑**共用同一套分段**，不做两份布局。

**一段只有在它此刻能通过校验时才允许折叠。**

这一条是写实施计划时才发现要补的：模型端点的「上下文窗口」和「最大输出」是
`required`，而它们落在默认折叠的那一段里。折叠一段里藏着空的必填项，后果是人点
提交、拿到一个校验错误、而**出错的字段在一个看不见的地方**——比不折叠更糟。

推论有两条，都必须实现：

1. **新建时**，含未填必填项的段一律展开，不管它默认折不折叠。
2. **任何时候**校验失败，出错字段所在的段自动展开。一个人不该为了看见错误先去
   猜它藏在哪一段里。

这条规则同时给了「默认折叠」一个可判定的判据：不是「我觉得这段不常改」，而是
**这段现在填完了没有**。

### 3.3 三页的分段

**模型端点**（14 个字段）

| 段 | 字段 | 默认折叠？ |
| --- | --- | --- |
| 连到哪 | 名称、类型、地址、模型、凭据 | 否——全是必填 |
| 这个模型的能力 | 上下文窗口、最大输出、窗口计账方式、是否收图片、分词器 | 编辑时是；**新建时否**（前两个是必填） |
| 计价 | 币种、输入单价、输出单价、用量可信度 | 是 |

「计价」整段可选。不填的后果要写在折叠条上：**这个端点的花费无法计算**——
用量页本来就把「实测费用」和「无法计价」分开显示，不合并成一个总数。

**Agent 详情**（15 个字段）

| 段 | 字段 | 默认折叠？ |
| --- | --- | --- |
| 身份 | 名称、别名、人格 | 否 |
| 模型 | 供应方、端点、场景 | 否 |
| 能力 | 技能、HTTP 工具 + 写策略、MCP 工具 + 写策略、网络 | 是 |
| 对外 | 终端用户入口开关、Chat Completions 开关、同步超时 | 是 |

「能力」段折叠条要显示绑了几样，而不是只写「能力」——`已绑 3 个技能 · 1 个
HTTP 工具（只读）· 无 MCP · 不允许出网`。

**渠道**（两个表单，各 5 个字段）

这一页的表单问题比数字看起来轻：真正的毛病是**两个不相干的东西挤在一页**
（渠道绑定、终端用户签发方），且新建/编辑走三个弹窗、字段定义重复三遍。

分段规则同样适用，但这一页优先要做的是**把重复的字段定义收敛成一处**，
新建与编辑共用。

## 4. 界面规则（这四条是「UI 优化」的全部含义）

这四条都来自实际看到的东西，都可验收。

### 4.1 表格里不整列显示原始 ID

渠道页的「加密密钥」列把一个完整 UUID 折成两行，占掉整屏最宽的一格，而那个值
几乎没有人会去读。

规则：**表格里的 ID、引用名、UUID 一律截断显示**，完整值放进详情或复制按钮。

### 4.2 一格只放一样东西

渠道页的「接入方式」一格里同时有：配置标签（长连接）、状态标签（已断开）、
灰字提示（重启 scheduler 后生效）——三样东西，三种含义。

规则：**一列表达一件事。**配置和状态是两件事，占两列或明确的主从关系。

### 4.3 标签只用于状态，不用于是非

「可回复」现在是一个绿色标签。它是个布尔值，不是状态——绿色标签在同一张表里
还表示「连接中」，两种含义共用一种视觉。

规则：**彩色标签只留给会变的状态**（连接中／已断开／active）。布尔用文字或
勾叉，不占用状态的颜色。

### 4.4 每页顶部有一句说明

四个页面现在**一句说明都没有**：成员、API 密钥、模型端点、出站范围。

它们正是使用者说「不知道是干嘛的」那一类。

规则：**每个页面顶部有一句话说明它是干嘛的。**写什么由那一页自己定；
这份文档只要求那句话存在。

## 5. 验收判据

按「这条路走得通」，不是「测试过了」：

1. 导航上是 **7 个**入口，不是 18 个。
2. 每个旧地址都能打开，并落在新位置的对应段上。
3. 「待办」上的数字与三个队列里实际待处理的条数相等。
4. 一个 viewer 登录后，**看不到**他会被拒绝的段；而后端对同一请求**仍然拒绝**。
5. 模型端点的**编辑**表单，首屏只展开「连到哪」，另外两段折叠且折叠条上写着
   它们此刻的值。**新建**表单里「这个模型的能力」是展开的——它含两个未填的
   必填项（上下文窗口、最大输出）。
9. 故意把一个必填项清空再提交，出错的那一段**自动展开**，错误看得见。
6. 「计价」一段不填时，折叠条上说的是「这个端点的花费无法计算」，用量页对这个
   端点的显示与之一致。
7. 渠道页表格里没有任何一格因为一个 UUID 而换行。
8. 上面点名的四个页面，顶部各有一句说明。

## 6. 这份设计替产品做的决定

- **「待办」是一个入口，不是三个。**代价是三种审阅工作被放在同一个心智容器里，
  而它们的后果并不相同（批准一个运行 ≠ 通过一条记忆）。选择合并是因为「有没有
  东西等我」这个问题比「等我的是哪一类」更常被问到。
- **「设置」是一个入口，装了六样东西。**它是这次分组里最像垃圾桶的一个。之所以
  可接受，是因为里面每一样都满足同一个真实条件：配一次，之后不碰。哪天有一样
  开始被频繁修改，它就该搬出来——而不是把「设置」拆成两个抽屉。
- **前端按角色隐藏分段**，但隐藏不构成授权。这条决定引入了一个前后端都能拒绝的
  局面，代价是两处逻辑要保持一致；收益是不再向人展示注定失败的入口。
- **折叠必须显示当前值。**这条把「折叠」从省地方的手段变成了传递信息的手段。
  它也是这份设计里实现成本最高的一条——每一段都要写一个摘要行，而摘要行是代码，
  不是配置。
