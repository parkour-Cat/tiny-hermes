# 飞书长连接接入 — 设计

> 日期：2026-08-31
> 状态：待实施
> 产品：v2.9.2 §19.2（飞书两种接入模式）、§929（Webhook 作为生产兜底）。
> 起因：spec §19.2 写着「私有部署计划**默认**使用飞书官方 SDK 的 WebSocket 长连接模式
> 接收事件，不要求企业开放公网入站地址」，而代码里**零实现**——四处提到它的地方全是
> 注释，飞书 SDK 依赖也没引。实际部署一直靠 cloudflared 临时隧道，四天里过期四次，
> 每次都要去飞书控制台改地址。

## 1. 现状

| | |
|---|---|
| spec 说的 | 长连接是私有部署的默认，Webhook「同时支持」 |
| 代码里有的 | 只有 Webhook |
| 现有代码的态度 | 已经在为长连接让路 |

最后一条是这次设计的基础。`channels/application/webhook_service.py:5` 的模块注释写着
「*inbound delivery means* lives where the WebSocket adapter can call it too」，第 99 行
再次说明「the WebSocket adapter will call the same service」。**「一条入站消息如何变成
Run」这部分已经被有意抽离**，本设计沿用那个预留，不新发明结构。

`channels/domain/blocked.py:17` 则写明了它当初为什么被推迟：「the limit that keeps the
WebSocket transport out of this milestone」。

## 2. 三个已定的决定

- **两种模式并存，每个绑定选一种。** §19.2 要求两种都支持，且在断线补投语义被验证之前，
  Webhook 必须保留为生产兜底（§929）。
- **先实现，同时把补投当作未知写明。** §19.2 要求 M1 技术验证确认断线期间的补投语义，
  而那只能对着真实飞书拔网线试出来。在拿到答案之前，文档与控制台必须写明
  「断线期间可能丢事件；不接受丢失的部署请用 Webhook」。
- **长连接住在 scheduler 进程。** 它已经是常驻循环进程，多一条常驻连接是同一类东西，
  不新增容器——这个项目已经因为「只重建了一部分容器」坏过两次，少一个服务就少一处
  漏掉的可能。

## 3. 架构

拆 `FeishuWebhookService.accept()` 为两段，两种 transport 共用后半段：

```
accept()                       ← Webhook 走完整条
  验签 → 解密 → accept_verified(secrets, document)

accept_verified(...)           ← 长连接从这里进（SDK 已验签、已解密）
  归一化成 ChannelEvent
  按 (binding_id, channel_event_id) 认领   ← 去重只有这一份
```

**去重只有这一份实现，两条 transport 都走它。不得为长连接另写一份去重**——本仓库刚在
`feat/goal-preemption` 上吃过一次「问的一边和答的一边判据漂移」的亏。

**修订（真机走查之后）：两条 transport 共用的是这份*实现*，不是同一个*键空间*。**
本节原来还断言「迁移期间同一条消息若两路都到，第二条被现有 claim 挡掉」。那句话建立在
一个错误的前提上：以为两条 transport 拿到同一个信封。**它们没有。**

lark SDK 交给 `MESSAGE` handler 的是 `InboundMessage`，它的 `raw` 是**消息对象**，
不是事件信封；飞书的 `event_id` 被 `channel.py` 的 `_handle_message_event` 取出来当
参数传给规范化流水线，`InboundMessage` 不留它，`Events.RAW` 在这个 SDK 版本里是个
没有任何地方触发的死常量。所以长连接**拿不到** `event_id`，它的认领键是 `message_id`。

后果：webhook 按 `event_id` 认领，长连接按 `message_id` 认领，同一条消息两路都到会
产生两个认领。**接受它**，因为飞书开发者后台的投递方式是**单选**的（要么发到服务器
地址，要么走长连接），两路同时收到只可能发生在切换的那一瞬间。另一条路是让两边都改用
`message_id`，那会动到 10 个测试文件里 39 处 webhook 断言，以及线上已有的去重键——
为一个飞书结构上不产生的场景付这个代价，不划算。

这条语义由 `test_transport_dedup.py` 的两条测试钉着：一条守「适配器不许自带去重」
（仍然成立），一条守「两条 transport 不再共用键空间」（这条钉的是代价，不是成绩）。

四块，各自可独立测试：

| 块 | 职责 |
|---|---|
| `accept_verified(...)` | 归一化 + 认领。两种 transport 共用 |
| 长连接适配器 | 建连、收帧、断线重连；把帧交给上面那个 |
| `channel_bindings.transport` | `webhook` / `long_connection`，默认 `webhook` |
| scheduler 中的持有者 | 启动时按绑定建连，与 `run_forever` 并排跑、共用 `stop` |

`transport` 默认 `webhook`：既有绑定的行为一个字不变。

## 4. 数据流

```
飞书 SDK 收到一帧
  → 适配器取出事件文档
  → accept_verified(secrets, document)
  → 归一化、认领、变成 Run、进队列
  → 回复仍走 scheduler 现有的扫描与发送路径，不变
```

回复不受影响：它走的是 Feishu 的 HTTP API，与入站 transport 无关，仍然经过
egress 代理。**但长连接本身是一条出站连接**，见 §9.1。

## 5. 断线与重连

重连交给 SDK。但**每一次断开与重连都必须记录一条事件，带上断开时长**。

理由不是可观测性好看：**这是将来判断「补投到底有没有发生」的唯一依据**。没有断开时间
窗，§19.2 要求的那次验证就只能靠猜——拔了网线之后，需要知道断了多久、以及那段时间里
本该有哪些消息。

**绑定变更不热重载。** 新增绑定或改 `transport` 需要重启 scheduler。YAGNI：热重载要处理
「连接建到一半绑定被删」这类竞态，而改绑定是低频操作。**但这条必须写进文档与控制台
提示**——否则用户改完发现没生效，会以为功能坏了。

## 6. 错误处理

| 情况 | 行为 |
|---|---|
| 建连失败（凭据错、应用未开长连接） | 记事件，退避重试，**不得拖垮 scheduler 主循环** |
| 收到帧但认领失败 | 与 Webhook 同路：记 `unsupported_kind`，欠发送者一句话 |
| 断线 | SDK 重连；记事件并带断开时长 |
| 同一绑定两路都收到同一条 | 各自认领一次（见 §3 修订）；飞书投递方式单选，只在切换瞬间可能发生 |

## 7. 测试

- **拆分之后，Webhook 现有的全部测试必须一条不改地继续通过。** 这是拆对了的判据；
  任何一条需要修改的既有测试，都说明拆的位置不对。
- 长连接适配器：喂一个假帧，断言它以正确参数调用了 `accept_verified`。
- **一条集成测试：同一帧经长连接到达两次，只产生一个认领。** 这是「适配器不许自带
  去重」的证明，也是本设计最容易在实现中被绕开的一条。**另一条钉住两条 transport
  不共用键空间**（见 §3 修订）——它钉的是代价，将来谁让两边的键重新对上，那条会红，
  那时该回来改这份文档，而不是删断言。
- **明确测不了的**：真实断线的补投行为。只能上线后拔网线。

## 8. 这份设计替产品做的决定

- **`transport` 是绑定级而非工作空间级。** §19.2 没说粒度。绑定级更细，且与
  `encrypt_key_ref`、`app_id` 这些同属绑定的凭据一致。
- **不做热重载**（见 §5）。§19.2 没有要求，但用户会期待，所以要显式说明。

## 9. 明确不做的

- **断线补投的验证**：只能对着真实飞书做，不在本次实现范围内，但必须在验收记录里
  写明它没做，且文档要写明后果。
- **多副本 scheduler 下的连接唯一性**：当前部署是单副本。将来若要多副本，需要一个
  选主或分片机制，否则每个副本各建一条连接会重复收事件——**去重会挡住重复的 Run，
  但白白多收多解一遍**。本次不做，但记录在案。
- **迁移既有绑定**：不自动把任何绑定切到长连接。切换是人工操作。

### 9.1 已知限制：长连接不经过 egress 代理

**长连接是 scheduler 主动打出去的一条 WSS**，它不经过 `outbound/client.py`，
因此不经过 egress 代理。而且 `lark_oapi/ws/client.py:73-80` 在建连时把
`proxy` 钉成 `None`，**主动关掉了对 `HTTP_PROXY`/`HTTPS_PROXY` 的识别**——
所以这不是「配一下环境变量就能纳入边界」的事，SDK 层堵死了这条路。

具体后果：**把 egress 代理关掉，消息照样进来、照样触发 Run，只有回复发不出去。**
`outbound/client.py` 原来那句「关掉代理一切就停是代码的性质」因此对入站不再成立，
那段 docstring 已经改成实话。

为什么接受它：§19.2 已经把长连接定为私有部署的默认，也就是说「让进程主动连出去」
这件事产品上早就同意了。要真堵住，得改 SDK 源码或在容器网络层做透明代理，成本
远超这条特性本身。

参照实现是同一种结构。`NousResearch/hermes-agent` @ `3f83297` 的
`docs/security/network-egress-isolation.md` 把 gateway 设成双宿主（同时挂在
`internal` 和 `egress` 两张网上），注释写着 `# needs outbound for Telegram, LLM APIs`，
并在 **Limitations** 一节里明说「Platform adapters need egress」。区别只在于
**它从没声称过「唯一的出口」**。

**将来接别的长连接适配器的人要知道：一个自己持有 socket 的 SDK，在这份代码库的
每一道出站检查之外。**这一节就是给那个人看的。
