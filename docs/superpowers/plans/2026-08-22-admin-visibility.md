# 管理员视图实施计划 — §27.3 第 4 条

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**产品：** v2.5 §4.6 审计记录一行、§422 第 8 条、§27.3 第 4 条。
**上一步：** 终端用户入口与控制面已合并。

**目标：** 「管理员查看 Approvals、任务树、用量、错误和脱敏审计记录。」

**这一条的真实缺口不是五个视图，是一个。** Approvals 有页面，任务树在 Run 详情里
（M2E），用量的数据在 `runs.consumed_cost` 与 `run_budget_scopes` 里，错误的原因埋在
`runs.checkpoint` 的 JSON 里。**审计记录一条读路径都没有**——`audit/` 模块只有 `tables.py`，没有 domain、没有
application、没有 presentation。每一层都在写，没有人读得出来。

这正是这个项目反复踩的坑：**写进去了不等于有人够得着。** 上一阶段的
`user_confirmation` 消费者、导出按钮、`forgetAllSessionIds` 都是同一个形状。

## 全局约束

- 审计表**只增不改**。这一条不加任何写路径，也不加删除或保留期清理——那是另一件事。
- 读审计**不得**成为绕过其他权限的旁路：一条 `context` 里带了会话正文的审计，不能让
  开发者靠读审计看到他本来看不到的东西。
- 新端点必须显式声明服务哪一类主体。终端用户**永远**够不着（§4.6 那一格是「否」）。

## 四条红线

- **五种主体，五种可见范围，不是一个开关。** §4.6 那一行写了五格，其中三格是
  「部分可见」而不是「可见／不可见」。把它做成布尔是这一条最容易犯的错。
- **脱敏只对查看者。** 不是对所有人。工作空间管理员读到的是完整记录——把所有人都
  脱敏等于让管理员查不了事故。
- **平台管理员跨空间读要留痕。** §4.6 那格写的是「跨空间只读**并留痕**」，§190 又
  重复了一次「平台管理员跨工作空间操作必须写入审计记录」。读审计这个动作本身进审计。
- **开发者只能看「与自己资源相关的」。** 不是本空间全部。

## 1. 审计的领域模型与查询

- [ ] `audit/domain/`：`AuditRecord`，以及表达可见范围的 `AuditScope`。
      **`AuditScope` 必须无法构造「全部」**——照 `MemoryScope` 的先例（M2D）：能被
      构造出来的最宽范围，就是有人终将拿到的范围。
- [ ] `audit/application/audit_service.py`：按主体解析出 `AuditScope`，再查询。
- [ ] `audit/infrastructure/sql_audit_store.py`：分页、按时间倒序、按
      `action`／`resource_type`／`actor_id`／时间窗过滤。
- [ ] 单元测试钉住五种主体各自的范围，**包括「查看者拿到的是脱敏的」和「开发者拿不到
      与自己无关的」**。

**出口检查：** 五种主体五种结果，且 `AuditScope` 表达不出「所有工作空间的全部记录」。

## 2. 脱敏

- [ ] 脱敏规则作用在 `context` 上——那是唯一可能装业务数据的列，其余列都是标识符。
- [ ] **默认拒绝而不是默认放行**：`context` 的键走白名单，不在名单里的键连键名都不出现。
      黑名单会在下一个人往 `context` 里塞新键时静默漏掉，而那一天不会有测试失败。
- [ ] 一条测试：往 `context` 里塞一个名单外的键，查看者读到的结果里它**不存在**。

**出口检查：** 新增一个未登记的 `context` 键，查看者读不到它，且测试是红的。

## 3. 留痕：读审计这件事本身

- [ ] 平台管理员跨工作空间读 → 写一条 `audit.cross_workspace_read`，含读取者、
      被读工作空间、过滤条件、时间。
- [ ] **本空间读不留痕。** 理由与 §6 的会话列表一致：把每一次翻页都记下来，真正
      重要的那条会被淹掉。留痕要能回答「谁越界看了别人空间」，不是「谁打开过页面」。
- [ ] 一条测试断言跨空间读留痕、本空间读不留痕。

**出口检查：** 跨空间读后审计表多一行且含双方身份；本空间读后不多。

## 4. HTTP 与响应模型

- [ ] `GET /api/v1/audit-events`，分页 + 过滤。
- [ ] **响应模型按主体收窄**，不是一个模型配一个 `if`。查看者的响应类型里根本
      没有那些字段——这是 `19b91e3`／`b97ddb3` 已经立过的先例。
- [ ] 终端用户 cookie 到这里一律 403。

## 5. 控制台页面

- [ ] `apps/web` 新增审计页：时间倒序、过滤、分页。
- [ ] **按角色显示不同的东西，并且说明为什么少**。查看者看到脱敏结果时要知道
      「这里被脱敏了」，而不是以为那条记录本来就长这样——一个静默脱敏的界面会让人
      对着不完整的证据做判断。
- [ ] i18n 两种语言都要有。

## 6. 用量、错误与任务树：补齐而不是重做

- [ ] 用量：把 `consumed_cost`／`consumed_model_calls`／`cost_quality` 在工作空间
      层面聚合出来。**`cost_quality` 必须显示**——一个把估算值和实测值混在一起
      展示的用量页，会让人拿估算数去对账。
- [ ] 错误：失败 Run 的列表与原因。**失败原因不是一列**——它埋在 `runs.checkpoint`
      这个 JSON 里，由 `_failure_reason()`（`runs/infrastructure/sql_store.py:3110`）
      取出来。所以「按原因分组统计错误」不是一句 `GROUP BY`，要么在 JSON 上查，要么
      先决定把它提成一列。**先量一下再选**，不要默认它便宜。
- [ ] 任务树：确认 M2E 的 Run 详情树已经够用，**不够再补，够就明确记下「不做」**。

- [ ] e2e：管理员打开审计页，看见自己刚做的那个动作。**要断言看见的是真实写入的

## 8. 这份计划替产品做的两个决定

**一、脱敏走白名单，不走黑名单。**
另一个合理答案是列出敏感键。不选它：黑名单的失败方式是静默的——下一个往 `context`
里加键的人不会想起来更新它，而那一天没有任何测试会红。白名单的失败方式是显式的：
新键默认不可见，谁需要它就得来登记。**让错误的方向偏向「少给」而不是「多给」。**

**二、本空间读审计不留痕，只有跨空间读留痕。**
另一个合理答案是每次读都记。不选它：审计的价值在于能回答问题，而一个把每次翻页都
记下来的审计表，会让「谁越界看了别人空间」这条淹没在几万条例行读取里。§6 的会话
列表已经就同一个取舍表过态，这里保持一致。
