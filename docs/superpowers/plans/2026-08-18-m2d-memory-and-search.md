# M2D 实施计划：双层记忆、会话搜索与本人自助

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**产品：** `docs/superpowers/specs/2026-08-09-tiny-hermes-product-design.md` §4.5、§4.6、§7.4.2、§14、§16.3。
**路线图：** `docs/superpowers/plans/2026-08-17-tiny-hermes-m2-roadmap.md` §7。
**上一步：** `docs/superpowers/plans/2026-08-18-m2c-tools-approvals.md`（M2C，已完成，验证记录
`docs/superpowers/verification/2026-08-18-m2c-tools-approvals.md`）。

**开场只有一句：审批已经在了。** M2C 交付了两类人工审批、`waiting_approval` 的
第一个生产用法，以及一条「参数变了原批准就失效」的规则。§14.1 的「所有记忆候选
等待审批」因此不需要新造一套流程——它要用的东西已经在跑了。这份计划做的是**记得**
这件事本身，以及它带来的那些必须由主体自己说了算的权利。

**目标：** Agent 在多次会话之间记得同一个人的偏好；共享记忆只能由管理员编辑或经
批准的提案写入；过去的会话按需检索而不是整体塞进上下文；每个主体可以看到、更正、
删除和导出属于自己的东西，而抹除本身留下审计。

**顺序原则：先隔离，后写入；先人工，后自动。**
第 1 步只做「记忆属于谁」和「谁能读到」，一条都不写。第 2 步才让记忆被写进去，而且
默认走审批。第 3 步的自动写入是第 2 步的一个**收窄**，不是一条新路径。
这个顺序不是审美：记忆最危险的坏法是 A 的偏好出现在 B 的会话里，第二危险的是没人
同意过的东西被记住了。前者是隔离问题，后者是审批问题，而隔离必须先成立——一条写
错地方的记忆，事后再怎么审批也已经在别人的上下文里了。

## 四条贯穿全篇的红线

- **私有记忆按 `workspace + agent + 调用主体` 隔离，读取路径上没有「所有主体」这个
  写法。** 和 MCP 的「不许绑定全部」同一个手法：不是禁止，是让它写不出来。一个能
  按 agent 查询全部记忆的函数，第一天就会被某个报表用上。
- **原始用户消息永远不自动成为记忆。** §14.2 对共享记忆写死了这一条，这份计划把它
  扩到私有记忆：记忆是**候选**，由某处显式提出，经过策略；从来不是「把这句话存
  下来」。区别在于前者可以被审、被拒、被更正，后者只能被发现。
- **相关度是关键词匹配，不是语义。** §14.3 明确排除向量记忆。所以裁剪记忆段时排序
  的依据要在名字和文档里说清楚是 PostgreSQL 全文检索的排名加时间衰减——一个叫
  `relevance` 而实为 `ts_rank` 的字段，会让下一个人以为平台懂了意思。
- **抹除是可追溯的删除，不是标记。** §4.6「本人」那一行给了删除权，抹除流程执行后
  私有记忆、会话、文件与身份信息都不可再检索；而抹除这件事本身写审计，因为一个
  什么都没留下的删除和一个没发生的删除，事后分不出来。

## 1. 记忆属于谁：数据模型与读取隔离

- [x] `packages/backend/tests/unit/memory/test_scope.py`：先写会失败的测试。
      纯函数决定一条记忆属于谁：`MemoryScope(workspace_id, agent_id, subject)`，
      `subject` 是 M1 已有的 `CallerIdentity`（`caller_type` + `caller_id`）。
      共享记忆是同一张表上 `subject=None` 的那些。
      测试要钉住：两个 `caller_id` 不同的主体算两个 scope；
      同一个人在两个 Agent 下也算两个；**没有任何构造方式能得到「这个 Agent 的
      全部私有记忆」**。
- [x] 数据模型与迁移 `0024`：`memories`（scope 四列、`kind`（`private`/`shared`）、
      正文、来源、`created_by`、`updated_at`、`status`）。
      正文上建 `tsvector` 生成列与 GIN 索引——第 4 步的检索和第 5 步的相关度用
      同一个索引，两套会给出两个答案。
- [x] 工作空间加 `memory_policy` 列：`off` / `all_pending` / `low_risk_auto`，
      默认 `all_pending`。**默认不是 `off`**：关掉自动记忆的部署应该是选出来的，
      而不是因为没人配过；也不是 `low_risk_auto`，那会让「规则检查」在没人看过
      它之前就开始放行。
- [x] 读取：`MemoryLibrary.for_run(run)`，只按该 Run 自己的 scope 取。
      Run 已经带着 `CallerIdentity`（M1）和 `end_user_id`（M2C），
      这一步要写清楚它们不是一回事：前者是**记忆属于谁**，后者是**谁能批准**。
      这一阶段两者对 `caller_type=user` 的 Run 指向同一个人，写下来是为了 §4.5
      的终端用户身份落地时不用重新猜。
- [x] 集成测试：A 主体写一条记忆（直接落库，本步还没有写入路径），
      B 主体用同一个 Agent 跑一轮，模型请求里没有它。
      这是路线图第一条出口检查，也是这一步唯一要证明的事。

## 2. 记忆怎么进来：候选、审批与共享记忆

- [x] `memory.remember` 平台工具：模型提出一条**候选**，不是写入。
      工具结果要像 `skill.propose` 一样把这句话说明白——「已提出，等待处理，
      本次运行不会用到它」——否则模型会当成已经记住了。
- [x] 策略分流（§14.1 三选一）：
      `off` → 具名拒绝，不留候选；
      `all_pending` → 写一条 `pending` 记忆并写 `memory_proposed` 事件；
      `low_risk_auto` → 进第 3 步的规则检查。
      三条各有一条测试，且 `off` 那条要断言**库里什么都没多**。
- [x] 审批复用 M2C 的 `approvals`：私有记忆候选按 `user_confirmation`
      （它只影响提出者自己的数据，§16.3 的原话），
      共享记忆候选按 `governance_approval`（§16.3 把共享记忆列在治理那一行）。
      **这里不新建审批表**；如果发现需要新建，说明记忆候选不是审批，要回头重想。
      **实现时这条的逃生口生效了，而且是往回退的方向。** `ApprovalRow` 绑在一次
      工具调用上，驱动 `waiting_approval` 状态机和过期扫描；而记忆候选不挂起任何
      Run，没有调用可哈希，也没有东西会过期。挤进去要么加一堆可空列，要么让
      状态机认识一种它不该认识的东西。所以按计划说的「回头重想」办：**没有新建
      审批表，也没有复用它**——`pending` 的记忆行本身就是队列，和 `SkillProposal`
      同一个形状，由 `MemoryService` 审，按 §4.6 的「代办并审计」那一行判谁能审。
- [x] 共享记忆的两条入口，且只有两条：管理员在控制台直接编辑，
      或一条被批准的提案。路由层要保证第三条不存在——
      没有任何 Run 能写 `kind=shared`，测试直接断言这一点。
- [x] 集成测试：策略设为 `all_pending` 时，跑一轮会提记忆的 Run，
      库里只有 `pending`，模型的下一轮上下文里没有它；
      批准之后才进。这是路线图第二条出口检查。
- [x] 集成测试：一条原始用户消息不会因为任何路径变成共享记忆。
      第三条出口检查，断言的是「没有这条路」而不是「这条路被拒了」。

## 3. 低风险自动写入：规则检查

- [x] `memory/domain/risk.py`：纯函数。一条候选是不是低风险，
      判据要能被一个人读懂并复述：长度上限、只允许第一人称偏好的形状、
      命中密钥/凭据形状即高风险（复用 `skills/domain/scan.py` 已有的模式）、
      命中权限与身份词汇即高风险、含他人姓名或联系方式即高风险。
      每一条判据一条测试，**并且有一条测试断言默认判高风险**——
      规则检查的默认答案必须是「拿不准就等人」。
- [x] `low_risk_auto` 策略下：低风险直接写入并写 `memory_written` 事件；
      其余仍然进 `pending`。策略是**放宽的上限，不是开关**：
      它不能让一条高风险候选绕过审批，一条测试钉住这个。
- [x] 共享记忆永远不走自动写入，无论策略是什么。§14.2 没有给它这条路。

## 4. 会话搜索

- [x] `session.search` 平台工具 + `GET /api/v1/sessions/search`：
      PostgreSQL 全文检索，按需返回片段，**不整体进上下文**（§14.3）。
- [x] 权限：只返回请求者有权读取的会话。对 Run 内的工具调用，
      范围是该 Run 自己的主体；对控制台，范围按 §4.6 的矩阵。
      路线图第五条出口检查，测试要包含一条「另一个主体的会话不在结果里」。
- [x] 结果尺寸：单次返回条数与每条片段字节都有上限，超了就少给，
      不截断单条片段——和 `skill.load` 同一条理由：模型拿到半句话不知道自己
      拿到的是半句。

## 5. 记忆进上下文：记忆段与相关度裁剪

- [x] `runs/domain/context_budget.py` 的 `memory` 段第一次有内容。
      注入的是**已写入**的记忆（`pending` 的永远不进），
      按相关度排序，超预算时先掉相关度最低的。
- [x] 相关度 = `ts_rank`（对本轮 Run 输入）+ 时间衰减，名字里带 `keyword`
      或在文档里第一句说明它是关键词匹配。红线三。
- [x] 路线图第四条出口检查：记忆段超预算时先移除低相关记忆，
      **不波及不可裁剪内容**。M2A 的 `plan_context` 已经有这套机制，
      这一步是给它接上真实数据，并加一条测试证明安全规则与人格没有被动过。

- [x] 谁能发起：本人；工作空间管理员在本空间代办并审计；
      平台管理员依法代办并审计。三条各一条测试，
      且「开发者不能」和「查看者不能」也各一条——矩阵里这两格是「否」。
- [x] 集成测试：抹除之后，同一个主体再跑一轮，上下文里没有旧记忆；
      会话搜索搜不到；导出接口对已抹除主体返回空而不是报错。

## 8. 这份计划替产品做的三个决定

**一、记忆的主体就是 `CallerIdentity`，不是新造一个。**
路线图第 9 节把这条列为整份路线图唯一的产品假设，这里承接它。另一个合理答案是
现在就建 §4.5 的终端用户身份表，让记忆挂在它上面。不选它，是因为终端用户身份要
连着渠道、验证与会话绑定一起做，而记忆不需要等那些；`CallerType` 现在是 `user`
和 `service_account`，将来加第三种时这张表的形状不变——变的是 `caller_type` 的取值。
代价是这一阶段「终端用户」在数据上等同于登录用户，这一点在 §1 里写下来了。

**二、默认策略是「全部待批」，不是关闭也不是自动。**
另外两个都合理：关闭最安全，自动最好用。不选关闭，是因为一个默认关掉的功能等于
没交付，而记忆的价值只有在它真的记住了东西之后才看得见；不选自动，是因为规则检查
的判据必须先被人读过一遍才配放行，而没人配过的部署恰恰是没读过的那个。待批是唯一
一个「东西被记下来了，但要有人看一眼」的默认。

**三、记忆候选复用 M2C 的审批表，不新建一套。**
另一个合理答案是给记忆做独立的候选/审批模型，像技能提案那样。不选它，是因为
§16.3 已经把共享记忆写在治理审批那一行，而私有记忆候选正好是「只影响自己数据、
不扩大权限」——`user_confirmation` 的定义原文。两套审批意味着两个地方定义「谁能批」，
而这正是 §16.3 花了整整一节去防的事。代价是记忆候选要挤进一张为工具调用设计的表；
如果实现时发现挤不进去，那说明这个判断错了，回到第 2 步重想，而不是加一列硬塞。
