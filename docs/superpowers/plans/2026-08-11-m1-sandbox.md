# M1 Sandbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver phase 3B: a Docker sandbox the platform owns and the Agent cannot configure, and one tool — `shell.exec` — that proves it. An Agent runs a real command inside a non-root, network-less container, sees the output, runs another in the same container, crosses a slice boundary and is told when its cache was reset.

**Architecture:** A fourth long-running process. Only `controller` mounts the Docker socket; the Worker and Scheduler reach it over a Unix domain socket in a shared volume, and the API and Web reach it not at all. The Controller's rules live in a transport-free class, because `socket.AF_UNIX` does not exist in Python on Windows and the rules must be testable on the machine they are written on. Container parameters are generated from the database and configuration; nothing in a tool request can name an image, a mount, a capability, or a network mode.

**Tech Stack:** Python 3.12, docker-py over the Docker Engine API, asyncio Unix sockets, FastAPI, SQLAlchemy 2 async, PostgreSQL 17, Alembic, ruff, pyright, pytest, Docker Compose, GitHub Actions.

## 1. Fixed scope and working rules

- Work in `.worktrees/m1-run-execution` on branch `m1-sandbox`.
- Treat the product design v2.4 §16, the M1 technical design v1.1 §10 and §11,
  and `docs/superpowers/specs/2026-08-11-m1-sandbox-design.md` as authoritative.
- **There is no host-execution fallback.** Not as a retry, not as a degraded
  mode, not "just for tests". A sandbox that will not start fails the Run. The
  process ban in Task 6 is what keeps this true after this slice ends.
- **The Agent names nothing about its container.** No image, no mount, no
  capability, no network mode, no host path — in the request or in the
  AgentVersion. Every parameter is generated.
- **Reaching the socket is not authorization.** Every Controller action
  re-checks Reservation ownership and, for a Worker call, lease validity. Write
  the refusal tests before the happy path.
- **Assert on the created container, not on the arguments passed.** A test that
  checks the dict we handed Docker proves we wrote a dict.
- **No file tools, no workspace versioning, no Artifacts, no egress proxy, no
  approval, no second resource profile.** Design §4 lists every deferral; if a
  task seems to need one, re-read rather than build a small version.
- `/workspace/data` is a scratch mount in 3B. Do not describe it as persistent
  anywhere a user can read.
- Every database integration command targets only `tiny_hermes_test`.
- Use `uv run --no-sync` for backend commands.
- Do not run `ruff format`.
- Write and observe a failing test before each production behavior.
- Commit after each task only when its focused checks pass.

### Task 1: A remote, and CI that has actually run

**Files:** none in the repository. This task is infrastructure.

Nothing else in this slice should be built on an unverified CI, and 3B is the
slice that finally cannot tolerate it: a GitHub runner differs from Docker
Desktop on cgroups, seccomp defaults, and overlayfs, and none of that surfaces
locally. Doing this first also separates two failure modes — "CI has never run"
from "Docker-in-Docker does not work in CI" — which would otherwise arrive
together and be hard to tell apart.

- [ ] **Step 1: Create the private repository** (operator, not the agent)

An empty private repository, no README, no license, no `.gitignore` — the
repository already has all three and an initial commit would need merging.

- [ ] **Step 2: Add the remote and push**

```bash
git remote add origin <url>
git push -u origin main
```

Confirm before pushing that `deploy/compose/.env` is absent from
`git ls-files` — it holds a real model credential and is gitignored, and this is
the moment that gitignore either holds or does not.

- [ ] **Step 3: Read the first run, unchanged**

The existing four jobs, against the workflow exactly as it stands. Expect
failures: `backend-unit`, `backend-integration`, `web`, and `compose-e2e` have
been reproduced locally on Windows, never on Ubuntu. Fix what breaks and record
each one — the difference between "we thought CI would pass" and what a runner
actually does is the point of this task.

- [ ] **Step 4: Commit any fixes, with the run URL in the message**

### Task 3: Container policy, as a pure function

**Files:**
- Create: `sandbox/domain/container_policy.py`
- Create: `packages/backend/tests/unit/sandbox/test_container_policy.py`

The same shape as phase 3A's address policy: the security-relevant decisions are
a pure function, settled and exhaustively tested before anything opens a socket.

> Phase 3C note, 2026-08-13: this task's `disk_mb` — declared here and never
> enforced by Docker — left the profile in 3C. Its successors are the
> `workspace_max_bytes` checkpoint quota and the kernel-bounded cache tmpfs;
> the policy also grew data-volume ownership labels. See
> `2026-08-11-m1-session-workspace.md` Task 6.

- [ ] **Step 1: Write the failing policy tests**

`container_config(digest, profile, run_id, mounts) -> ContainerConfig`, and a
table asserting every line of design §7: non-root user, `read_only=True`,
`network_mode="none"`, `cap_drop=["ALL"]`, `no-new-privileges`, cpu, memory,
pids, disk, a `noexec,nosuid,nodev` tmpfs at `/tmp`, `init=True`, and exactly two
mounts.

Then the refusals:

- a digest outside the allowlist raises;
- a profile above the instance ceiling raises;
- a mount naming any path other than the two allowed ones raises;
- the returned config contains no key that could carry a host path, asserted by
  comparing the key set against a literal — so a future parameter has to be
  added to the test deliberately.

### Task 4: The Controller, against a real Docker daemon

**Files:**
- Create: `sandbox/ports/controller.py`, `sandbox/application/controller.py`, `sandbox/infrastructure/docker_engine.py`
- Create: `packages/backend/tests/integration/sandbox/conftest.py`, `test_controller.py`

- [ ] **Step 1: Write the failing ownership tests first**

Before any happy path, because these are the rules:

- `acquire` for a Run that already holds a live Reservation is refused, and no
  container is created — assert by counting containers before and after;
- `execute` with a lease belonging to another Run is refused;
- `execute` with an expired lease is refused;
- `execute` with a `sandbox_id` belonging to another Run's Reservation is
  refused;
- a Scheduler cleanup call is refused while the Run's lease is still live;
- a Scheduler cleanup call after expiry succeeds and writes an AuditEvent;
- `execute` after `freeze` is refused.

- [ ] **Step 2: Write the failing container tests**

Asserted from `docker inspect` on the created container, never from the config
we passed:

- user is not root, `ReadonlyRootfs` is true, `NetworkMode` is `none`,
  `CapDrop` contains `ALL`, `SecurityOpt` contains `no-new-privileges`, and the
  ceilings are set;
- a command in the container cannot reach the network — both a DNS lookup and a
  raw connect to a literal address fail;
- writing to `/` fails and writing to `/workspace/data` succeeds;
- two `execute` calls between one `acquire` and one `destroy` report the same
  `boot_id`;
- an image digest outside the allowlist is refused before Docker is called.

- [ ] **Step 3: Implement**

`docker_engine.py` is the only module that constructs a Docker client. docker-py
is synchronous, so calls go through `asyncio.to_thread` — chosen over an async
client because docker-py speaks the Windows named pipe and the alternatives do
not, and the development machine is Windows.

`SandboxController` takes the engine and the store, and holds every rule. It is a
plain class with no transport.

- [ ] **Step 4: Verify and commit**

### Task 7: The Unix socket transport

**Files:**
- Create: `sandbox/transport/server.py`, `sandbox/transport/client.py`, `sandbox/cli.py`
- Create: `packages/backend/tests/integration/sandbox/test_transport.py`

- [ ] **Step 1: Write the failing transport tests**

Skipped on Windows with the reason in the skip message, because
`socket.AF_UNIX` does not exist there:

- a request round-trips and the Controller's answer comes back;
- a refusal comes back as a refusal, with its code, and not as a dropped
  connection;
- a malformed frame is rejected without killing the server;
- a request larger than the frame cap is rejected;
- the server handles two concurrent clients — the Worker and the Scheduler are
  both callers.

- [ ] **Step 2: Implement**

`asyncio.open_unix_connection` and `asyncio.start_unix_server`, newline-delimited
JSON. **No rule lives here.** The client is a dumb encoder; the server decodes
and calls the Controller. `sandbox/cli.py` becomes the
`tiny-hermes-controller` console script, matching how the Worker and Scheduler
are wired.

- [ ] **Step 3: Verify and commit**

### Task 10: The tool seam and `shell.exec`

**Files:**
- Create: `tools/domain/registry.py`, `tools/domain/shell.py`, `tools/application/execute.py`
- Modify: `agents/domain/models.py`
- Create: `packages/backend/tests/unit/tools/test_registry.py`, `test_shell_request.py`
- Create: `packages/backend/tests/integration/tools/test_shell_exec.py`

- [ ] **Step 1: Write the failing authorization tests**

Both steps of §10.2, separately, because they fail differently:

- an AgentVersion binding no tools produces an empty schema list — the model is
  never told `shell.exec` exists;
- an AgentVersion binding `shell.exec` produces exactly one schema;
- **a request for an unbound tool is refused at execution even when it is
  perfectly formed**, and the implementation is not called — this is the step
  that matters, because a model can ask for anything;
- a `cwd` outside `/workspace/data` and `/workspace/cache` is refused, including
  via `..` and via an absolute path;
- a `timeout_seconds` above the ceiling is refused rather than clamped.

- [ ] **Step 2: Write the failing execution tests**

Against a real container: a command's stdout comes back; a non-zero exit is
reported as a result rather than an error; a command that outruns its timeout
returns `command_timeout`; output beyond the byte cap is truncated with an
explicit marker saying so.

- [ ] **Step 3: Add the binding to `AgentSpec`**

`tools: tuple[()]` becomes a validated tuple of bound tool names. This changes
the normalized document and therefore the content hash — **unlike phase 3A's
model-policy widening, this one is not free.** Decide and record: either
`schema_version` becomes 2 with `Literal[1, 2]` on read and a normalizer per
version, or the field defaults in a way that leaves existing documents
byte-identical. Pin the phase-3A hash literal in a test either way, so whichever
path is taken is a decision and not a discovery.

- [ ] **Step 4: Verify and commit**

### Task 11: The Worker executes tools

**Files:**
- Modify: `runs/application/worker.py`, `runs/ports/store.py`, `runs/infrastructure/sql_store.py`

- [ ] **Step 1: Write the failing loop tests**

- a Run whose Agent binds no tools acquires no sandbox — assert no container is
  created, per §11.4;
- a Run whose Agent binds `shell.exec` acquires one before the first model call
  of each slice;
- a model round returning a tool call executes it and feeds the result back as a
  new round, and the transcript holds both blocks;
- `cache_state=reset` writes a `sandbox_cache_reset` event **and** prepends a
  protected runtime hint to that slice's first model call — assert the hint
  reached the provider, and that a later conversation turn cannot displace it;
- `cache_state=reused` writes no event and adds no hint;
- **a freeze that fails produces `interrupted`, never a requeue** — the rule from
  product design §16 that is easiest to get wrong, because the happy path looks
  identical;
- reaching `paused`, `waiting_*`, or a terminal state destroys the instance
  first, and a destroy whose result is unclear is `interrupted`.

- [ ] **Step 2: Implement**

Acquire before the first model call of a slice, freeze before releasing the
lease, destroy before any non-queued exit. The tool round joins the existing
slice transaction the same way the assistant message did in phase 3A.

- [ ] **Step 3: Verify the whole suite and commit**

## 3. Phase 3B completion checklist

- [ ] CI has run on a real remote, including Docker-in-Docker.
- [ ] A published Agent bound to `shell.exec` completes a Run whose model saw
      real command output.
- [ ] The created container is non-root, read-only, network-less, all caps
      dropped, and inside every ceiling — asserted from `inspect`.
- [ ] Nothing inside the sandbox can reach the network, by DNS or by literal
      address.
- [ ] An unbound tool is refused at execution even when the model asks correctly.
- [ ] A `cwd` outside the allowed directories is refused before the
      implementation runs, including via `..`.
- [ ] Two tool steps in one slice share one container; a new Run does not.
- [ ] `cache_state=reset` produces an event and a protected hint, and no marker
      file in `/workspace/data`.
- [ ] A failed freeze produces `interrupted`, never a requeue.
- [ ] `paused`, `waiting_*`, and terminal states leave no container and no
      reservation.
- [ ] A killed Worker leaks no container.
- [ ] `subprocess`, `os.system`, and `create_subprocess_*` are banned outside the
      sandbox module, proven by a test.
- [ ] `/var/run/docker.sock` is absent from the `api` and `worker` containers.
- [ ] `sandbox_instances` has no host path column.
- [ ] The `AgentSpec.tools` change is either a recorded `schema_version` bump or
      proven byte-identical for existing documents.
- [ ] All phase 1, 2A, 2B, 2C, and 3A checks pass unchanged.
