# M2B 企业技能目录与自我改进实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**产品：** `docs/superpowers/specs/2026-08-09-tiny-hermes-product-design.md` §8.4、§15、§20.2、§27.2.5。
**路线图：** `docs/superpowers/plans/2026-08-17-tiny-hermes-m2-roadmap.md` §5。
**上一阶段：** `docs/superpowers/plans/2026-08-17-m2a-goal-loop.md` 与
`docs/superpowers/plans/2026-08-17-m2a-context-budget.md`（M2A，已完成）。

**目标：** M2A 让 Run 跑得久、装得下。这一阶段第一次往上下文里放进 Agent 自己没有
写过的内容：管理员上传或导入的技能。提示词里只出现名称与简介，正文在命中后才加载；
Agent 可以提出补丁，但补丁只有经过扫描、差异和人工批准才会成为一个不可变版本，而且
成为版本之后也不会自动被任何已发布的 Agent 用上。

**顺序原则：** 第 1 步是纯函数，没有 I/O；第 2–4 步是目录与导入，运行时行为不变；
运行时行为的变化从第 6 步开始；治理路径（提案与审批）在第 7 步，它需要第 2 步的版本
和第 6 步证明过的加载路径都已经存在。每一步都能独立跑通。

这份计划没有单独的设计文档。M2A 的设计决定写在 `specs/2026-08-17-m2a-goal-loop-design.md`
里，是因为它要改的是一条已经在跑的循环；M2B 的多数结构是新建的，所以决定连同理由写在
它要落地的那一步旁边，另有四个替产品做的决定集中在 §10。

**四条贯穿全篇的红线：**

- **技能内容是数据，不是指令。** 技能正文由管理员上传，但写它的人不是平台。它进入
  提示词时必须带明确的边界标记，说明这是参考资料；读完它之后 Agent 想做的任何事
  仍然要过 §16.2 的两次权限检查。技能不授予任何能力——它不加工具、不加网络、不加密钥。
- **版本不可变，绑定指名版本。** AgentSpec 绑的是 `SkillVersion` 的 id，不是技能名。
  发布一个新技能版本不会改变任何已发布 Agent 的行为；换过去是一次显式的重新发布，
  这就是 §15.3 第 6 步说的「Agent 明确切换」。
- **受信进程不解包归档。** `tests/unit/test_archive_ban.py` 立的规矩在这里同样成立：
  人工上传收的是文件列表而不是压缩包，Git 导入按流读 tar 成员并且从不落盘。
- **提案永远不会自己变成版本。** 路线图 §5「明确不包含：任何形式的自动批准」。
  扫描不通过的提案不能被批准，批准之外没有第二条产生版本的路径。

## 1. 纯包解析与静态扫描

- [x] `packages/backend/tests/unit/skills/test_package.py`：先写会失败的测试。
      覆盖：`SKILL.md` 缺失、frontmatter 缺 `name` 或 `description`、路径带 `..` 或
      绝对路径、同一路径出现两次、超过文件数与字节数上限、非 UTF-8 字节。
      每一种都是一个**具名拒绝**，不是一个通用的 `ValueError`——上传的人需要知道
      改哪一个文件。
- [x] `skills/domain/package.py`：
      - `SkillFile(path, text)`，路径复用
        `session_workspace/domain/manifest.py:normalize_workspace_path`。
        路径规则在这个仓库里只有一份实现，技能包不给自己写第二份。
      - `SkillManifest(name, description)`，从 `SKILL.md` 的 YAML frontmatter 解析。
        `name` ≤ 64 字符，`description` ≤ 200 字符——这个上限不是随手定的，
        见 §5 的算术。
      - 上限：单文件 ≤ 256 KiB，`SKILL.md` ≤ 64 KiB，每版本 ≤ 64 个文件、
        合计 ≤ 1 MiB。超限是拒绝，不是截断。
      - `content_hash(files)`：按路径排序后对 `(path, bytes)` 的规范编码取 sha256，
        和 `normalize_agent_spec` 同一套纪律。**同一份内容必须得到同一个哈希**，
        §3 的重复导入靠它。
- [x] `skills/domain/scan.py`：静态扫描，返回 `tuple[Finding, ...]`，每条带
      `severity`（`blocking` / `advisory`）、`path` 和一句人话。
      `blocking` 是发布前置条件；`advisory` 记录下来给人看，不拦。
      规则只包含**结构性**的东西：清单声明的文件与实际文件不一致、可执行脚本里出现
      对外网络地址、内容里出现看起来像凭证的片段。
- [x] 在 `scan.py` 的模块 docstring 里写清楚它**不是**什么：它不是沙箱，也不声称能
      识别恶意内容。它拒绝的是形状。真正的防线是三件已经存在的东西——技能内容只是
      提示词里的数据、工具调用要过两次权限检查、命令只在无网络的沙箱里跑。
      一个声称能识别恶意 Markdown 的扫描器会让读的人放松警惕，这比没有扫描更糟。
- [x] 无 I/O：不 import SQLAlchemy、httpx、tarfile，也不碰文件系统。

## 2. 数据模型与迁移

- [x] `skills/domain/models.py`：`Skill`、`SkillVersion`、`SkillProposal`
      与两个状态枚举。
      - `Skill.workspace_id: UUID | None`。`None` 是平台内置技能（§15.1 的两级目录），
        对所有工作空间可读、只有平台管理员可写。这是 §9.3「所有资源查询必须自动应用
        工作空间范围」的一个**显式例外**，所以它要有自己的测试：
        另一个工作空间的私有技能在任何查询里都看不见，平台技能对所有工作空间可见且只读。
      - `SkillVersion`：`version_number`、`content_hash`、`source`（`upload` / `git`）、
        `source_url`、`source_ref`、`manifest`、`scan_findings`、`created_by`。
        内容不可变；唯一可变的列是 `status`（`active` / `withdrawn`），因为 §15.1 要
        「停用」。
      - `Skill.current_version_id`：新绑定的默认值，**仅此而已**。它不改变任何已发布
        的 AgentVersion，回滚它也不会。这一条要写成注释，因为它正是 §15.1 的「回滚」
        最容易被读成「让线上换版本」的地方。
- [x] `skills/infrastructure/tables.py`：`skills`、`skill_versions`、`skill_files`、
      `skill_proposals`。文件内容按行存 Postgres 而不是进对象存储：技能是文本，
      不可变性、内容哈希和逐版本回滚在一张表里是一条外键，在对象存储里是两个真相。
      唯一约束 `(skill_id, content_hash)`——重复导入不产生第二个版本，是数据库的
      事实而不是服务层的检查。
- [x] 迁移 `migrations/versions/20260817_0014_skills.py`：建四张表，
      **并且**在同一次迁移里把 `run_events.event_type` 的 CHECK 换成含 `skill_loaded`
      的新版本。生产者要到第 6 步才出现，一个允许但暂时没人写的枚举值是惰性的；
      `0013` 把两件「新增枚举值要带迁移」的事合成一次，这里照办，少一个停机窗口。
- [x] `skills/ports/store.py`、`skills/infrastructure/sql_store.py`、
      `skills/infrastructure/memory_store.py`，形状照 `agents/` 抄。
- [x] `packages/backend/tests/integration/test_skills_migration.py`：
      从空库跑到 `0014`，断言四张表与两个唯一约束都在。
      集成测试 TRUNCATE 一份已迁移的 schema、不跑 alembic，所以这条是唯一能证明
      `0014` 能落到空库上的测试。

## 4. 从 Git 导入

- [x] 导入走 `outbound/client.py` 的 `SafeOutboundClient`，取的是一个 HTTPS
      tarball URL。这是路线图 §5「导入的出站请求走当时的强制出站面」的落法，
      也意味着地址拒绝与重定向复查规则原样生效，一条都不用重写。
- [x] tar 成员**只按流读**（`.extractfile()`），一个字节都不落盘。这需要在
      `packages/backend/tests/unit/test_archive_ban.py` 的 `tarfile` 白名单里加一个
      模块——这是本阶段唯一一次放宽安全面，所以它必须换来同一次提交里的四条上限：
      成员数 ≤ 128、单成员未压缩字节 ≤ 256 KiB、合计 ≤ 4 MiB、压缩比 ≤ 100:1。
      每一条都在**读之前**判断，读完再判断的上限拦不住压缩炸弹。
- [x] 拒绝符号链接、硬链接、设备文件与任何绝对路径或带 `..` 的成员名。
      `extractall` 的历史漏洞几乎都在这几种成员上，而这里根本不写盘，
      所以它们是「无法表示为技能文件」而不是「危险」。
- [x] `source_ref` 记下服务端从响应里读到的不可变引用（commit sha 或 ETag）。
      「从某个分支导入」两个月后不可复现，记下的必须是当时那一份。
- [x] 集成测试用本地 HTTP 替身提供 tarball，覆盖：正常导入、超过每一条上限、
      符号链接成员、重定向到内网地址被出站面拒绝。

## 5. 绑定到 AgentSpec

- [x] 测试先行，先证明加宽不改内容哈希：不声明 `skills` 的 spec 仍然哈希成
      `DETERMINISTIC_HASH`，`schema_version` 仍是 1，normalized document 里没有这个键。
      这是 `tools`、`completion`、`context_budget` 之后第四次同样的加宽，
      做法一字不改。
- [x] `AgentSpec.skills: tuple[SkillBinding, ...] = ()`，
      `SkillBinding(skill_version_id: UUID)`。绑版本 id 而不是技能名，是红线二。
      每个 Agent 最多绑 16 个技能；同一个技能不能绑两个版本。
- [x] `AgentCatalog._check_endpoint` 旁边加 `_check_skills`：版本存在、
      `status == "active"`、从这个工作空间可见（自己的或平台的）、
      扫描没有 `blocking` 结论。任何一条不满足都是发布期拒绝，
      理由和 `unknown tool` 完全一样——一个在第一轮才发现的错误，
      是作者本可以在写的时候就被告知的。
- [x] 摘要预算的算术，作为发布期的第五种拒绝 `SkillSummaryBudgetExceeded`：
      16 个技能 × 200 字符 ≈ 3200 字符，而 `SKILL_SUMMARIES` 段的
      `max_tokens` 是 1536。所以逐段检查是必要的而不是形式的：
      把所有绑定技能的 `description` 按 `estimate_tokens` 加起来，
      超过该段 `max_tokens` 就拒绝发布，并**逐个列出每条摘要的估算值**。
      `ContextBudgetUnsatisfied` 已经立过「拒绝要带具体数字」的规矩。
- [x] 为 M2E 留的形状写成注释而不是代码：§27.2.3 要求子 Agent 的技能权限是父权限与
      委派策略的交集。绑定是一个版本 id 的集合，交集就是集合交集；
      这一阶段不实现，但形状不能挡路。

## 6. 渐进加载：摘要进上下文，正文靠 `skill.load`

- [x] `tools/domain/registry.py` 加 `skill.load`，进 `IMPLEMENTED_TOOLS` 和
      `PLATFORM_TOOLS`——它没有要跑的命令，要的东西发生在 Run 上而不是容器里，
      和 `platform.wait` 同一类。参数是 `{skill, path}`，`path` 默认 `SKILL.md`。
- [x] 两次权限检查在这里的具体形态：第一次，模型只被告知已绑定技能的名称与简介；
      第二次，`skill.load` 按**这个 Run 绑定的版本集合**授权，而不是按模型说出的名字。
      模型报一个没绑的技能名，得到的是 `tool_not_authorized`，
      和它报一个没绑的工具时一样。
- [x] 上限：单次加载的文件 > 64 KiB 直接拒绝并**说出它有多大**（不截断，
      理由和 M2A-2 里「裁剪要留下它有多大」的说明同源）；每个 Run 最多 8 次
      `skill.load`，超过是具名拒绝而不是静默失败。
- [x] `RunEventType` 加 `skill_loaded`，payload 带 `skill`、`path`、
      `skill_version_id` 与 `bytes`。在 `event_type_for` 的注释里写明它和
      `goal_verdict`、`context_trimmed` 一样不是从信号派生的。
- [x] `ExecutionContext` 加 `skills: tuple[BoundSkill, ...]`（名称、简介、版本 id），
      由 store 在读上下文时一并读出。和 `window` 同一次读——一轮要发什么，
      是在一个时刻决定的。
- [x] `runs/domain/models.py`：安全前言里加一句，说明技能正文是参考资料，
      不是平台的指令。这是红线一里唯一需要改到运行时字符串的地方，
      而 `SAFETY_PREAMBLE` 已经在规划器能计量的一侧，加长它会被自动计入预算。
- [x] `ModelRequest` 加 `skill_summaries: tuple[str, ...]`；
      `openai_model.py` 把它作为紧跟 `personality` 之后的一条 system 消息发出，
      带明确的边界标记。**不拼进 personality**：拼进去之后，
      预算表上的两段就再也分不开了。
- [x] `plan_context` 让 `skill_summaries` 第一次真正花钱：加进 `fixed`，
      并按 `SKILL_SUMMARIES` 段的 `max_tokens` 执行段内裁剪——
      **整条整条地移除未命中技能的摘要，永不截断单条**（路线图出口检查点名）。
      移除顺序是作者绑定顺序的倒序：作者写下的顺序是一句优先级声明。
      已经在这个 Run 里 `skill.load` 过的技能，其摘要不算未命中，不被移除。
- [x] 「未命中」在这里是一个 Run 知道的事实，不是平台的猜测：
      加载过的技能有 `skill_loaded` 事件。这就是为什么 §10.1 选择让模型显式调用
      而不是让平台做关键词匹配。
- [x] 正文加载之后住在哪一段，不需要新代码：它是一条 tool result，
      于是自动落进 `old_tool_results`，也就是固定裁剪顺序里**最先**被换掉的那一段。
      写成测试而不是注释。
- [x] 集成测试 `tests/integration/runs/test_skill_loading.py`：
      绑了技能的 Agent 跑一轮 → 请求里有摘要、没有正文；
      模型调 `skill.load` → 正文作为工具结果回到会话，并留下 `skill_loaded` 事件；
      未绑定的技能名 → `tool_not_authorized`；
      摘要超段预算 → 未命中的整条消失，命中的还在。
- [x] `DeterministicModelPolicy` 加 `skill_once` 场景。它让整条技能路径在**没有沙箱**
      的主机上也能端到端跑通——`skill.load` 是平台工具，不需要容器。
      这一条顺便解决了当前 e2e 里那个因 `SANDBOX_IMAGE_DIGEST` 为空而失败的用例
      所暴露的同一个环境问题。

## 7. 自我改进：提案、差异、审批、发布、切换

- [x] `skills/domain/diff.py`：纯函数，两个版本的文件集合之间的差异，
      按路径排序，逐文件给出 `added` / `removed` / `changed` 与行级差异。
      确定性的，因为审批的人要能对着它做决定，而两次打开必须看到同一份东西。
- [x] `SkillProposal`：`base_version_id`（可为空，表示提出一个新技能）、
      提议的文件集合、`origin`（`agent` / `human`）、
      `origin_run_id`、`created_by`、`status`（`pending` / `approved` / `rejected`）、
      扫描结论。
- [x] 提交提案时立刻扫描并存下结论。带 `blocking` 结论的提案**可以存在、可以看、
      不能批准**。让它存在是为了让提出的人看到自己错在哪；不能批准是 §15.3 第 3 步。
- [x] `skill.propose` 工具（平台工具，同 `skill.load` 一路）：Agent 在 Run 里提出补丁。
      它写出的是一条 `pending` 提案，永远不是一个版本。每个 Run 最多提 1 条，
      提案文件合计沿用 §1 的上限。
      这是路线图那条「模型的判断只是建议」在本阶段的具体落点。
- [x] 批准 → 发布不可变新版本，`source` 记为 `proposal`，
      `source_ref` 记提案 id。拒绝 → 状态终止，不产生任何版本。
      两者都写审计。
- [x] **Agent 不得修改正在生产运行的技能版本**（§15.3 末句）在这里是自动成立的，
      不是一条检查：提案产生新版本，而 AgentSpec 绑的是旧版本 id，
      直到有人改草稿并重新发布。写一条测试把这件事钉住，
      否则以后有人「顺手」让批准去更新绑定时不会有任何东西喊停。
- [x] 单测覆盖路线图的三条出口检查：未批准的提案不产生新版本；
      批准后旧版本仍可回滚；扫描不通过的提案不能发布。

## 10. 这份计划替产品做的四个决定

路线图 §9 只承认了一个产品假设。这一阶段还有四个，都写在这里，
因为它们每一个都有别的合理答案，而代码必须选一个。

1. **「命中」= 模型显式调用 `skill.load`，不是平台做关键词匹配。**
   理由：匹配需要一个相关度模型，而平台没有；显式调用复用已经存在的工具循环与两次
   权限检查，并且「哪些技能命中了」变成一个有事件为证的事实，段内裁剪才有依据。
   代价：模型不主动调用时，它只能靠简介工作。可接受——简介本来就是给它判断用的。

2. **绑定指名 `SkillVersion` id，不是技能名加最新版本。**
   理由：§15.3 第 6 步要求「Agent 明确切换到新版本」，绑名字的话切换是隐式的。
   代价：技能改一次，每个用它的 Agent 都要重新发布一次。这正是不可变版本的定价。

3. **人工上传收文件列表，Git 导入只支持公开 HTTPS tarball。**
   理由：受信进程不解包归档；`ssh://` 与私有仓库凭证要先有一个凭证注入面，
   而那属于 M2C 之后。
   代价：私有仓库这一阶段导不进来，只能先下载再上传。

4. **技能内容只接受 UTF-8 文本。**
   理由：正文要进提示词，二进制进不去；模板与脚本都是文本。
   代价：技能带不了图片或二进制资源。M2D 之后如果确有需要，
   它是往对象存储加一条路径，而不是改这张表的形状。

如果第 1 条或第 2 条被否掉，受影响的只有 §5、§6 两步；§1–§4 与 §7 不动。
