# 上下文压缩 v2（产品设计 v2.10 §7.4.2）

用户授权：按 2026-09-24 讨论定下的方案修改压缩机制。分支 `feat/compaction-v2`，不推送、
不合并，合并前按 CLAUDE.md 重新取得 compose-e2e 绿色结果。

## 这份计划替产品做的决定

讨论里说过、落到实现时改了的，逐条写明：

- **「清理后 ≤ 50% 就不做摘要」改为「清理后仍 ≥ 触发线才做摘要」。** 50% 那条线在实现时
  出了问题：清理是每轮从原文重算的，视图从 50% 慢慢涨回去的过程中，一越过 50% 就会做摘要——
  比 85% 的触发线还早。「仍然越线才摘要」与 Claude Code 文档的「先清旧工具输出，需要时再
  摘要」同义，也少一个常量。
- **「连续 2 次压缩后仍高于 70% 就停」改为无状态的「一次能省的少于
  `MIN_COMPACTION_GAIN_TOKENS` 就不做」。** 反复压缩只会在固定段或当前请求本身太大时出现，
  那时每轮能压的只有刚离开保留区的几条；按这一轮自己的收益判断就能挡住，不需要跨轮计数器
  和它的存储、清零时机。挡住之后若装不下，走已有的 `paused(context_overflow)`。
- **`skill.load` 的 8 次上限改为按不同技能版本计。** 同一版本再次加载不计数。计「版本」而
  不是「版本 + 路径」：现有 `loaded_skills` 只带版本 id，按版本计不需要改事件结构；一个
  技能包内多读几个文件本来就受每 Run 工具调用上限约束。
- **豁免清单放在工具注册表**（`tools/domain/registry.py` 声明，worker 传给规划器），
  规划器不按工具名硬写。
- **补回段、摘要前缀合成一条平台消息**（`author="platform"`，`role="user"`），与现在的
  摘要消息同一形态，不新增消息种类。
- **只把当前请求按原消息补回**，而不是「范围内最新的用户消息」；用户原话与技能正文的
  补回上限按输入额度的 1/8 算（见下节第 1 条）。
- **兜底一级可以动技能正文**（最后才动，存根明说被裁掉）：否则比窗口还大的技能文档
  只能让这一轮暂停。

## 实施中发现并修掉的问题

都是先写出能复现的红测试、再修的；按发现顺序：

1. **补回「范围内最新的用户消息」原文，小窗口上会压完还装不下。** 那条可能是一份被
   贴进来的长文档。改为只补回当前请求；原话与技能正文的上限取固定值与输入额度 1/8
   的小者（按额度而不是剩余空间，免得补回段每轮变、缓存每轮失效）。
2. **小窗口上保留区里一个大工具结果就能让这一轮暂停**，而旧级联会把它打成存根。加了
   兜底一级：工具结果换成不带开头的存根，技能正文最后。
3. **结构摘要都装不下时仍带着压缩记录返回**，Worker 会为注定暂停的一轮付摘要调用。
   改为返回原文、不带记录。
4. **最小收益 4,096 对小窗口太严**：1,000 token 的额度下省 1,200 也被拦，整轮暂停。
   改为只对「不压也装得下」的一轮设门槛，并取与额度 1/16 的小者。
5. **存根写的「全长」是入口限长之后的长度**（25121 而不是 40000）。改为会话记录里的
   原始长度。
6. **一份止于工具调用与其结果之间的存档摘要会让视图发出孤儿工具结果。** 这样的摘要
   不当作存档点。
7. **窗口越大越会暂停**（460、740 装得下，520–720 暂停）：跨过保留区目标的那一条若是
   比剩余空间还大的工具结果，整条计入保留区后就装不下。保留区改为不超过剩余空间的
   一半，那一条留给摘要；兜底存根也改为可在压缩前的视图上尝试。随后加了一条扫描
   窗口大小与历史形态的不变量测试。
8. **结构摘要的检索线索词没有长度上限**：一个 1,800 字符的连续单词说两遍，就原样进了
   每一份摘要。拉丁词线索加了 40 字符上限。
