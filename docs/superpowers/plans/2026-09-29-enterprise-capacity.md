# 企业容量方案：一台机器撑多少员工，往上走要改什么

日期：2026-09-29。依据是当天的五份验收记录：

- [并发探针](../verification/2026-09-29-concurrency-probe.md)
- [Worker 去掉飞书 SDK](../verification/2026-09-29-worker-without-feishu-sdk.md)
- [一个进程跑 K 个 Worker](../verification/2026-09-29-worker-concurrency.md)
- [公平领取与长任务](../verification/2026-09-29-fair-claim-and-long-tasks.md)
- 以及上面几份里的原始数据

本文把**实测**和**推算**分开写。推算都标了出来，也写明了还要测什么才能把它变成实测。

## 1. 结论

1. **不要按员工人数估算，要按「同一时刻正在执行的 Run 数」估算。** 等待审批、等待外部事件、
   暂停中的 Run，既不占 Worker，也不占沙箱（§12.3、§21.3）。员工数要换算成并发数，
   才能谈容量。
2. **单机档现在就能用，但有两个正确性问题要先修**（见 §5 的 P0）。修好之后，一台 8 核的
   机器，第一阶段的目标是**同时执行约 20 个带工具的 Run**。这是目标，不是实测结论：
   32 路时实测出现过一次死锁失败，每轮开销也放大了 8 倍。
3. **多机的最大障碍是沙箱，不是 Worker。** Worker 已经无状态、可以多开；但带工具的 Run
   要通过 Unix socket 找本机的 sandbox-controller，所以连 Worker 都没法放到另一台机器上。
4. **高并发下要让交互快，靠的是容量和优先级，不是排队顺序。** v2.13 的公平领取只给等待
   加了上界，实测短消息仍要等约 2 分钟。

## 2. 容量模型

**同一时刻正在执行的 Run 数 ≈ 交互部分 + 长任务部分**

- 交互部分 = 消息到达速率 × 每条消息的执行时长（利特尔法则）。例如 200 人在线、每人
  5 分钟发一条、每条执行 40 秒：200 ÷ 300 × 40 ≈ 27 路。
- 长任务部分 = 正在进行的长任务数 × 执行时间占比。执行时间占比，指去掉等待审批、等待
  外部事件、等待人回复之后，真正在执行的时间比例。**这个比例只能从试点部署统计**，
  文档里给不出。

### 每一路并发要的资源

这些数字都来自确定性模型：不走网络，每轮只跑一条 `printf`。

| 资源 | 实测 | 出处 |
|---|---|---|
| Worker 进程固定开销 | 约 96 MiB / 进程 | 飞书 SDK 那份记录 |
| Worker 每路内存 | 约 1 MiB | K=8 → K=32，合计只多 15 MiB |
| Worker CPU，不带工具 | 约 1.3% 个核 / 路 | K=32，25 路时 32.8% |
| Worker CPU，带工具 | 约 2.6% 个核 / 路 | 32 路时 81.7% |
| 数据库连接 | 约 1.2–1.6 条 / 路 | 32 路时 53 条 |
| 沙箱 | 每路执行中的 Run 1 个运行态；每个被切片、等下一轮的长任务 1 个冻结态 | 公平 A/B |
| 模型厂商并发 | = 同时执行数 | 按定义 |

**还不知道的**：真实模型每路要多少 CPU（流式解析、数 token）；真实工具的沙箱要多少内存。
这两个数决定了真实的单机上限，要在试点里测。

## 3. 部署档位

### A. 单机（现在就能用，修完 P0 之后推荐）

一台主机上跑全部服务。沙箱和 controller 必须在同一台机器上。

| 设置 | 建议 | 为什么 |
|---|---|---|
| `WORKER_CONCURRENCY` | 16 | 32 路带工具时，一个进程已经用到 82% 个核 |
| worker 容器数 | 核数 ÷ 4，至少 1 | 每个进程只能用一个核（GIL）。8 核给 2 个，就是 32 路 |
| 通道数（容器数 × K） | 大于同时推进的长任务数，再加交互那一份 | 通道被长任务占满时，短消息要等一个时间片（[单机档验收](../verification/2026-09-30-tier-a-acceptance.md)第 3 档：P95 31.6 秒） |
| `WORKER_MAX_SLICE_SECONDS` | 交互为主 15；长任务为主 30 | 新到的 Run 最多等「排在前面的数量 ÷ Worker 数 × 时间片」 |
| `SANDBOX_IDLE_TTL_SECONDS` | 默认 300；内存紧张时调低 | 轮转让每个在推进的长任务都拿着一个冻结的沙箱 |
| 沙箱内存预算 | 在推进、用过工具的 Run 数 × 每个沙箱常驻 ≤ 0.7 × 主机内存 − 基础占用 | 一比一占用，冻结的也算；8 核 / 7.8 GiB 的 VM 上约 2.9 GiB（[沙箱内存](../verification/2026-09-30-sandbox-memory.md)） |
| `AGENT_MAX_MODEL_CALLS` | 按长任务需要的轮数，外加余量 | 默认 20，一个长任务最多约 20 轮 |
| Postgres `max_connections` | 200（现状）；Worker 路数超过 100 就加连接池代理 | 每路约 1.5 条连接 |

验收方法见 §6。

### B. 多台机器跑 Worker（小改造，还没做）

API、Worker、scheduler 已经是无状态的，Run 的真相在 Postgres 里，领取用 `SKIP LOCKED`
加队首校验。唯一的阻塞：带工具的 Run 要通过 Unix socket 找本机的 controller。

要做的是：把 controller 的接口改成走网络（mTLS），Worker 按 `SandboxReservation`
记录的主机去找对应的 controller。冻结的沙箱留在哪台机器上，下一个时间片就要路由回
哪台机器。

### C. 沙箱主机池（结构改造，还没做）

多台沙箱主机，每台一个 controller。新建沙箱时挑一台负载低的；冻结、解冻都回到原主机。
工作区按版本存在对象存储里，所以冷恢复可以落在任何一台上，这是现有设计的长处。

### D. Kubernetes（放到最后）

§5 与 §6 不承诺 K8s。真要上的时候：

- Worker 按「可领取的 head Run 数」扩缩，不要按 CPU。
- 沙箱是一次性 Pod，放在专门的节点池里，用 gVisor 这类运行时。
- controller 改成调 K8s API。
- scheduler 先单副本；多副本要先确认它的扫描在并发下是安全的。

## 4. 调度与公平

已经做了：

- **v2.13**：按进入队列的时间领取。给等待加了上界，并去掉了等待随长任务总量增长的那部分。

还没做，按对交互体验的影响排序：

1. **每个用户、每个工作空间的并发上限。** 公平的粒度现在是 Run：一个人开 10 个长任务，
   就占 10 份轮转。
2. **交互优先。** 同步的 Chat Completions 和聊天渠道的消息，优先于后台长任务领取。
3. **时间片在 Goal 轮结束时切，还是只按时长切？** §21.3 写的是二者之一先到就切，实现只
   按时长。前者对交互更友好，但冻结、解冻更频繁。这需要在规格层面做决定。

## 5. 路线图

每一项都按项目的规矩做：先红测试，再实现，再有验收记录。

**P0：正确性，影响真实使用，应该最先修。**

1. ~~**租约续期和工作区提交会死锁**~~ **已修**（分支 `fix/lease-lock-order`，
   [验收记录](../verification/2026-09-29-lease-lock-order.md)）：`renew_lease` 改为先锁
   `runs` 再锁租约，与其他所有路径的顺序一致。强制复现的测试修复前 3/3 死锁，修复后
   5/5 通过。
2. ~~**在最后一次允许的调用里完成，却判为 `paused(limit)`**~~ **已修**（分支 `fix/limit-on-finishing-round`，[验收记录](../verification/2026-09-29-limit-on-finishing-round.md)，规格 v2.13 §12.3）：判为 done 或 failed 的一轮按判定结束，预算只挡还需要下一轮的轮。顺带发现有三个测试夹具依赖了这个 bug。

**P1：单机容量。**

3. ~~**controller 的线程池**~~ **已查清**（[记录](../verification/2026-09-29-round-overhead.md)）：线程池是次要因素，调到 64 个线程整轮只快约 10%。主要开销在「每轮提交一个工作区版本」：一次提交约 15 次串行往返，高并发下每一次都慢 5 到 15 倍。Docker 守护进程在这台机器上exec 吞吐约每秒 140 次封顶，是单机的硬上限。优化方向按证据排序写在那份记录里。
4. **每台主机开多个 Worker 进程**。现在就能做（`--scale worker=N` 配合 K），只差把建议值
   写进运维文档。
5. **SSE 改成 Redis 推送**。现在每个有人看的 Run，每 0.5 秒查一次库，还没测过。
6. **沙箱内存没有总量上限**（[记录](../verification/2026-09-30-sandbox-memory.md)）。
   每个沙箱上限 1 GiB，另外按 Docker 默认还能用 1 GiB swap；controller 不限制个数，也不看主机
   还剩多少内存。32 条通道全部用上时，理论上需要 32 GiB，而 7.8 GiB 的 VM 按 70% 线只能给
   沙箱留约 2.9 GiB。可选的做法：
   - controller 按「已建沙箱的内存上限之和」做准入，超过预算就让新沙箱排队；
   - 调低默认的内存上限和 tmpfs 大小；
   - 把 `memswap_limit` 设成等于内存上限，让压力留在沙箱里，而不是把整台主机推进 swap。

   选哪种要先知道超过物理内存时会发生什么，而那一步还没测。

**P2：公平与交互体验**：§4 里「还没做」的三项。

**P3：长任务能力（需要规格决定）。**

- `max_execution_seconds` 在代码里写死为 900 秒。
- 模型调用上限默认 20 次。

企业里跑几个小时的任务，是把上限放宽，还是拆成父子委派的多个 Run？这是产品决定。

**P4：多机**：§3 的 B、C、D。

## 6. 怎么验证一个档位

`scripts/concurrency_probe.py` 可以混合长任务和短消息，分组报告排队时间，并统计沙箱数：

```bash
# 例：单机档，2 个 worker 容器 × 16 路，交互加长任务混合
WORKER_CONCURRENCY=16 docker compose ... up -d --scale worker=2 --wait worker
uv run --no-sync python scripts/concurrency_probe.py \
  --rate 1 --seconds 120 --long-tasks 16 --rounds 15 --label tier-a
```

一个档位算「能支撑」，应该同时满足：

- 目标负载下，短消息排队 P95 在可接受范围内（比如 10 秒以内）；
- 长任务全部完成，没有死锁或中断失败；
- Worker CPU 低于 70%；
- 沙箱内存加上各服务的内存，低于主机的 70%。

这些阈值要在试点之后，写进规格 §24 的新门槛里。**现在它们只是建议。**

「Worker CPU 低于 70%」还缺口径：2026-09-30 的验收里每一档都有 2 秒采样超过 70%，
P90 却都不超过 51%。那一遍按 P90 判，这只是提议。

**2026-09-30 第一次整体验收**（[记录](../verification/2026-09-30-tier-a-acceptance.md)，
8 核 / 7.8 GiB 的 OrbStack VM，确定性模型）：

- 3 × 16 条通道时，同时执行 40 个 Run，四条标准都过。
- 2 × 16 条通道、32 个长任务时，第一条不过：短消息 P95 为 31.6 秒。
- 工具只是 `printf`，所以内存那条不能外推到真实工具。

## 7. 这份方案替产品做的决定

- 容量按「同时执行的 Run 数」来规划和承诺，不按员工人数承诺。
- 第一阶段只做单机档，多机从 Worker 能跨机器开始（B）。
- 在 P0 修完之前，不建议把 `WORKER_CONCURRENCY` 开到 16 以上用于生产。

## 8. 需要产品负责人决定的问题

1. 长任务的上限怎么定：放宽 900 秒和 20 次调用，还是要求拆成多个 Run？
2. 时间片按轮结束，还是只按时长结束？
3. 交互优先要不要做？怎么界定「交互」：同步接口、聊天渠道，还是某个 Agent 的属性？
