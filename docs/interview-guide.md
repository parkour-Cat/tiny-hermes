# 面试讲解手册

这份文档帮你在面试里讲清楚 tiny-hermes：它是什么、为什么这样设计、能撑多少人、数据从哪来、
哪些还没做到。尽量用大白话，每个说法都附上出处，被追问时能翻到原始记录。

技术细节以[架构说明](architecture.md)和[产品设计](superpowers/specs/2026-08-09-tiny-hermes-product-design.md)
为准；实测数据都在 `docs/superpowers/verification/` 下面。

---

## 1. 一句话、30 秒、2 分钟

**一句话：**一个给企业内部用的 AI Agent 平台：员工在网页或飞书里和 Agent 对话，Agent 可以调用
大模型、调用公司的接口、在隔离的沙箱里写代码跑代码；管理员能管权限、额度、密钥和审计。

**30 秒版：**

> 我做了一个企业级的 AI Agent 平台。难点不在调用大模型，而在「很多人同时用」时的三件事：
> 一是**任务调度**，长任务不能把短对话堵死；二是**安全隔离**，Agent 会执行代码、会访问
> 网络，必须关在沙箱里、出站只能走一个代理；三是**可靠性**，进程崩了任务不能丢。
> 我用 PostgreSQL 做任务队列、Docker 做沙箱、时间片轮转做调度，并且用真实模型压测过。

**2 分钟版**，在 30 秒版后面补三句：

1. **架构**：五种进程。api 收请求；worker 执行任务；scheduler 做定时清理和恢复；controller
   管沙箱；egress-proxy 是唯一的出口。状态全在 PostgreSQL，所以 api 和 worker 都可以随便
   多开、随便重启。
2. **容量**：我不按「多少员工」算，按「同一时刻有多少任务在执行」算。真实模型压测里，一条短
   对话平台自己只花 44 毫秒，其余时间都在等模型；一台 8 核机器上 40 路并发、480 多个任务
   全部完成。
3. **工程方法**：测试先行，每一项功能都有一份验收记录，并且必须写明「这一遍没能证明什么」。

## 2. 架构：打个比方

把平台想成一家**带厨房的外卖店**：

| 平台里 | 外卖店里 | 为什么这样分 |
|---|---|---|
| api | 前台，接单、告诉你进度 | 前台不做菜，接单再多也不会被做菜拖慢 |
| PostgreSQL 里的 Run 表 | 订单板 | 所有订单的状态只记在这一处，谁都能看，不会记两份对不上 |
| worker | 厨师 | 从订单板领一单就做，做一会儿把进度写回板上 |
| 时间片轮转 | 厨师每道菜做一段就放回去 | 一道慢炖的大菜不会让后面点凉菜的人一直等 |
| 沙箱 | 单独的操作间 | Agent 写的代码在里面跑，跑坏了也只坏那一间 |
| egress-proxy | 唯一的后门 | 所有出去的东西都要过这道门，门上有白名单 |
| scheduler | 店长巡店 | 厨师晕倒了（进程崩溃），他把那张单重新放回订单板 |

完整的图在[架构说明](architecture.md)「一条消息怎么走」。

**一条消息怎么走**：员工发消息 → api 在数据库里建一条 Run（任务）→ 通过 Redis 叫醒一个
worker → worker 领到任务，调用大模型 → 模型说要跑代码，worker 请 controller 开一个沙箱 →
结果写回数据库 → api 用 SSE 推给浏览器。

## 3. 「6000 个员工能不能撑住」怎么回答

这是你被问过的那道题。推荐的回答顺序是：**先纠正算法，再给数据，最后说瓶颈和扩容路径。**

### 第一步：不按人数算，按「同时在执行的任务数」算

6000 个员工不会同时发消息。就算发了，大部分时间也是在**等模型回复、等审批、等人看结果**，
这些时间不占 worker。

用排队论里的**利特尔法则**：同时执行数 = 每秒到达的任务数 × 每个任务执行多久。

> 举例：高峰时 10% 的人在线（600 人），每人平均 2 分钟发一条，每条执行 1.3 秒：
> 600 ÷ 120 × 1.3 ≈ **6.5 路**同时执行。
>
> 早先的估算更保守：假设 2% 到 5% 的人同一时刻都有任务在执行，就是 **120 到 300 路**。

### 第二步：给实测数据

| 测了什么 | 结果 | 出处 |
|---|---|---|
| 一台 8 核虚拟机、3 个 worker 进程，用假模型 | 40 路同时执行，482 个任务全部完成 | [单机档验收](superpowers/verification/2026-09-30-tier-a-acceptance.md) |
| 长任务把通道占满时 | 短消息只是排队（P95 31.6 秒），不会失败；加了「交互优先」后同样负载降到 10.9 秒 | 同上；[领取顺序验收](superpowers/verification/2026-10-23-claim-limits.md) |
| 真实模型（DeepSeek）短对话，每秒 1 到 4 条 | 420 个任务 0 失败，端到端 P95 1.6 秒；**平台自身开销中位数 44 毫秒** | [真实模型压测](superpowers/verification/2026-10-23-real-model-probe.md) |
| 每条短消息花的 CPU | 约 0.22 核·秒，即每秒 5 条消息约用 1.1 个核 | 同上 |
| 真实模型长任务 | 见下面第 4 节 | [长任务压测](superpowers/verification/2026-10-23-real-task-probe.md) |

### 第三步：说瓶颈在哪、怎么扩

- **worker 不是瓶颈**：它是无状态的，任务状态都在数据库，多开几台机器就行。这一步已经做了
  （B 档，worker 可以在多台机器上，通过双向 TLS 调沙箱主机）。
- **带工具的长任务，先撞墙的是沙箱主机**：沙箱现在只能在一台主机上，而且每个沙箱按固定内存
  预约。真实模型实测里，默认配置下一台 8 核机器同时只能开 3 个沙箱，详见第 4 节。扩法是做
  「沙箱主机池」（C 档），或者上 Kubernetes。我选 C 档，理由见第 5 节。
- **再往后是 PostgreSQL 的 CPU**：用假模型压到 40 路时峰值 224%；真实模型的长任务 20 个同时跑时
  只有 41%。到那一步要降每一轮写库的量，或者加连接池代理。
- **模型厂商的并发和限流**：这是外部限制，平台能做的是排队、按工作空间限额、失败自动切换到
  备用模型。

**一句总结：**「6000 人按利特尔法则算下来，高峰是几十到几百路同时执行。短对话平台自己只花几十
毫秒，worker 可以横向扩；真正先撞墙的是沙箱主机，其次是数据库，这两个都有方案和实测数据。」

## 4. 长任务：真实模型跑起来是什么样

**测了什么**：让真实模型（DeepSeek）在沙箱里用 bash 写一个「数字转罗马数字」的脚本，再写测试，
跑测试、出错就改，直到全部通过。同时开 5、10、20 个这样的任务。

**一个任务长什么样**：单独跑一个时，模型用了 21 轮、48 秒，自己发现并修掉了一个 bug，测试全部
通过。48 秒里：

| 等模型 | 沙箱里执行命令 | 平台自己 |
|---:|---:|---:|
| 44.4 秒 | 1.1 秒 | 2.5 秒 |

**同时跑 20 个时发现了真正的瓶颈：沙箱的内存预约。**

- 每个沙箱默认按 1 GB 内存「预约」，这台机器给沙箱的预算是 4 GB，所以同时最多 3 个沙箱。
- 第 4 个任务拿不到沙箱，就让出、回去排队，不会失败，但要等。20 个任务总共用了 85 秒。
- 可这些沙箱实际只用了几 MB 内存，预约量是实际用量的几百倍。
- 把预约量改成 256 MB 再跑：同时能开 12 个沙箱，**总耗时从 85 秒降到 25 秒**，排队时间中位数从
  37 秒降到 2.8 秒。

**面试时怎么讲这件事**：

> 平台按「预约」给沙箱分内存，不超卖，所以一台主机的沙箱数是硬上限。这是故意的：超卖了，
> 内存一紧，沙箱里的进程就会被系统杀掉，任务莫名其妙地失败，比排队更难排查。但默认 1 GB 对
> 写 bash 脚本的任务太保守了。真实的做法是按工作负载配置预约量，或者按实际用量超卖、内存紧张
> 时冻结或驱逐沙箱。后者要先拿到真实工作负载的内存分布，我没有凭空去做。

**顺带的一个教训**：第一次跑时 20 个任务挂了 19 个。原因是我为了省短对话的费用，把模型单次输出
上限设成了 256 个 token，模型一次写不完整个脚本就被截断。平台重试后判失败，这是按设计在工作。
所以测试脚本后来会把失败原因直接打印出来，不用再去翻数据库。

## 5. 高频追问

**问：为什么用 PostgreSQL 做任务队列，不用 Kafka 或 RabbitMQ？**

答：任务状态本来就要存在数据库里（暂停、审批、恢复都要查它）。如果再放一个消息队列，就有两份
状态，要处理「队列说发了、数据库说没收到」这种不一致。PostgreSQL 的 `SELECT ... FOR UPDATE
SKIP LOCKED` 能让多个 worker 并发领任务又不会领重。代价是数据库压力大，这正是实测里第一个
撞墙的地方。到了那一步，再考虑把「叫醒 worker」以外的部分拆出去。Redis 在这里只负责「叫醒」，
它挂了 worker 会退回轮询，不丢任务。

**问：多机部署为什么选自己做「沙箱主机池」，不直接上 Kubernetes？**

答：先看瓶颈在哪。worker 本来就是无状态的，已经能放在多台机器上；真正只能有一台的是沙箱主机。
自己做主机池要改的是：沙箱记住自己在哪台主机、新沙箱挑有空的主机、冻结的沙箱下次回到原主机、
主机坏了换一台从对象存储冷恢复。代码里「默认只有一台」的地方我列出来是 7 处。上 K8s 要把沙箱的
整个生命周期改成调用 K8s API，还要配 gVisor 和专门的节点池，再加上维护一个集群。按 6000 人的
规模算，几台机器就够了，K8s 的自动扩缩暂时用不上。等规模真的需要时，主机池的接口也能换成调 K8s。

**问：长任务会不会把别人堵死？**

答：三层保护。
1. **时间片**：一个任务最多连续跑 15 到 30 秒就让出，下一轮重新排队。
2. **交互优先**：聊天窗口来的消息先领；后台任务等太久（默认 120 秒）会被提上来，不会饿死。
3. **限额**：每人最多同时跑 3 个，每个工作空间可以设上限，API Key 调用不算在个人头上。

实测效果：同样的负载下，短消息排队 P95 从 39.2 秒降到 10.9 秒，长任务的完成时间没变。

**问：Agent 能执行代码，怎么保证安全？**

答：
- 代码只在 Docker 沙箱里跑，每个任务一个沙箱，有内存和进程数限制。
- 每个沙箱有自己独立的网络，沙箱之间互相看不到。
- 沙箱想上网只能经过 egress-proxy，它有白名单，并且会拦截访问内网地址（防 SSRF）。
- 平台自己的代码里，「直接发 HTTP 请求」是被 lint 规则禁止的，只能用经过代理的客户端。
- 还没做的：Docker 共享宿主机内核，隔离强度不如 gVisor 或虚拟机，这一项写在待办里。

**问：进程崩溃了，任务会丢吗？**

答：不会。worker 领任务时会拿一个租约，每一轮结束都把检查点写回数据库。worker 崩了，租约过期，
scheduler 发现后把任务放回队列，另一个 worker 从上一个检查点继续。这和「暂停」「等审批」是
**同一个机制**，不是另写的特例。

**问：多租户怎么隔离？**

答：两层。
- 应用层：查询都按工作空间过滤，权限范围在类型上就构造不出「所有工作空间」。
- 数据库层：PostgreSQL 的行级安全（RLS），应用用一个受限的角色连库，每个事务开头设好当前
  工作空间。就算应用层漏写了一个过滤条件，数据库也不会把别人的数据返回出来。

**问：密钥怎么存？**

答：信封加密。每个密钥用自己的数据密钥（DEK）加密，DEK 再用部署方保管的主密钥（KEK）加密。
数据库里只有密文，KEK 不和数据库放在一起，所以只拿到数据库备份解不出来。

**问：怎么知道线上出了什么问题？**

答：Prometheus 指标（任务数、排队时间、模型调用耗时、token 用量）、Grafana 看板、告警规则；
OpenTelemetry 链路追踪接到 Jaeger，一个任务从 api 到 worker 到模型调用是一条完整的链。生产采样
10%。真实模型压测里「平台开销 44 毫秒」这个数，就是从链路追踪里算出来的。

**问：登录被暴力破解怎么办？**

答：同一个账号 15 分钟内失败 5 次，之后的登录直接拒绝。失败记录存在数据库里，所以多个 api 进程
共享同一份计数；不存在的账号也照样计数，免得攻击者借此判断账号是否存在。控制台前面的 nginx
另有一层按来源 IP 的请求限速。

## 6. 可以讲的踩坑故事

面试官喜欢听「你遇到过什么难的问题」。下面几个都是真实发生、有记录的。建议用「情况 → 我做了
什么 → 结果 → 学到什么」来讲。

**故事一：测试全绿，第一条真消息就挂了（飞书接入）**

- 情况：接飞书长连接时，代码注释说 SDK 给的数据「就是飞书的事件格式」，实现照这句话写，测试
  也照这句话造假数据。注释、实现、测试三样东西建立在同一个错误的假设上，互相印证，全绿。
  评审了七轮都没发现。
- 怎么发现的：关掉内网穿透，发一条真消息，第一条就挂了。
- 学到的：跨进程、跨 SDK 的边界，测试数据必须用对方自己的类型来构造，不能手写一个「我以为
  对方会给的样子」。这条后来写进了项目规范。

**故事二：假模型压测出来的数字是错的**

- 情况：早先用「假模型」（不走网络、立刻回答）压测，算出每路并发只要 1.3% 到 2.6% 个 CPU 核。
- 换成真实模型（DeepSeek）后发现每路约 17%，因为真实调用要走网络、解析流式返回。
- 但反过来，真实模型大部分时间在等待，**每条消息总共只花 0.22 核·秒**。容量估算要用后一个数。
- 学到的：替身测出来的数字要标明「是替身测的」，拿到真实数据就更新，不要拿替身的数字下结论。

**故事三：一个看起来无害的正则误伤**

- 情况：项目用一条规则禁止归档相关的危险写法，结果这条正则把 OpenTelemetry 的
  `propagate.extract(` 也匹配上了，CI 红了。
- 做法：没有放宽规则，而是换了导入的名字，并且确保注释里也不出现被禁的写法。
- 学到的：安全规则宁可误伤再绕开，也不要为了让 CI 变绿去放宽它。

**故事四：行级安全上线，120 条测试一起红**

- 情况：给数据库加行级安全（RLS）后，120 条测试失败。原因是 SQL 里 `''::uuid` 在 `OR` 条件里
  被提前计算，空字符串转 uuid 直接报错。
- 做法：改用 `nullif(..., '')::uuid`，并补了一条专门的回归测试。

## 7. 主动说出来的局限

面试时主动说局限，比被问出来好得多。

- **只在一台 8 核虚拟机上测过**，不是正式的服务器；每档负载大多只跑了一次。
- **沙箱主机还只能有一台**，带工具的并发受它的内存预约限制；默认配置下只能同时 3 个。
- **长任务只测了一种**：bash 小脚本。装依赖、编译这类重的任务，沙箱要多少内存没测过。
- **Docker 隔离强度有限**，没有用 gVisor。
- **scheduler 的扫描是串行的**，一项慢会拖住后面的。
- 还没有在真实企业里试点过，「每个任务有多少时间真正在执行」这个比例只能从试点里统计。
